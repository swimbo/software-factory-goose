# Durable systems position: additive finalization with visible recovery

I support root-attested finalization in the same exclusive `ClaimLeaseJournal` object, with an additive operator read model and idempotent projection recovery in the first acceptance slice. Keep the launch reservation permanent and the legacy claim/receipt projection unchanged. The authoritative result is a new typed record; it is not promotion, a rewritten worker completion, or a statement that actual spend was zero.

Evidence is adequate to choose this boundary and insufficient to certify its runtime semantics. The live implementation does not yet have a root finalizer, an evaluator receipt authority, a finalization projection, or a demonstrated complete normal-generation cleanup. The current Restate documentation describes the general model; our lockfile pins Rust SDK 0.12.1, so the crash, replay and read-visibility claims must be demonstrated against the actual pinned stack rather than inferred from a current TypeScript example. [Restate handler semantics](https://docs.restate.dev/foundations/handlers), [pinned lockfile](../../../../../clean-room/Cargo.lock).

## 1. Include status and recoverable projection now

I concede operations' concern: a durable record that is inaccessible to the operator while the only CLI still shows an old leased claim is not a complete finalization slice. Include an authenticated, additive CLI status and an idempotent SQL reexport in the same acceptance gate. Present the legacy claim as a historical, separately labeled state. Show finalization outcome, evidence identity, unknown actual spend, projection state and promotion pending. A pass in this status means only that the named candidate passed the named independent evaluation; it does not mean the human approved, the system deployed, or the candidate was promoted.

The authoritative status should be readable from the claim object even if PostgreSQL is unavailable. An operator must see whether the SQL read model is pending, current or quarantined; a missing SQL row is not proof that the finalization does not exist. Reexport reads the durable authoritative event and redelivers exactly the stored payload using a stable event identity. The sink uses transactional insert-or-compare behavior: same key and bytes are idempotent, while same key with changed bytes is a terminal integrity conflict. Projection deletion followed by explicit reexport must rebuild the same status without any Docker, model, Git or approval effect.

I maintain that the decision and its pending outbox item belong in **one bounded, versioned state envelope** written by the exclusive finalizer. Restate documents exclusive mutations per key, but shared readers can run concurrently. Two separate `ctx.set` calls may be recovered in order, yet source comments and serial handlers alone do not prove atomic visibility to a concurrent shared reader. One envelope gives readers a single value to interpret; test its actual visibility and crash behavior with SDK 0.12.1. The existing [`persist_claim_transition`](../../../../../clean-room/crates/control-plane/src/workflow.rs) and [`projection.rs`](../../../../../clean-room/crates/control-plane/src/projection.rs) provide a useful idempotent outbox precedent, not proof that a new finalization event is already projected. [Restate services](https://docs.restate.dev/foundations/services), [durable steps](https://docs.restate.dev/develop/ts/durable-steps).

## 2. Unknown should be immutable and explicitly distinct

I concede operations' preference for an immutable terminal `unknown`, with one qualification: it records that the root authority could not establish the named outcome at the point of observation; it does not assert that execution completed, that containment succeeded, or that evidence is absent forever. A root-created unknown record should identify the generation, reservation binding, failure phase, and bounded reason code, including any established observations. It must never set `evaluated_pass` or mark a candidate approval eligible.

An identical retry of that record returns it. A changed retry conflicts permanently, including a later request trying to rewrite unknown as pass. Later recovery evidence may be appended as a separately typed, monotonically ordered observation with its own identity and an explicit link to the unknown record. It may report, for example, that exact engine cleanup was subsequently verified. It cannot silently change the original outcome or grant a fresh claim. Whether a later independently evaluated candidate can become eligible needs its own reviewed transition and user approval policy; it is outside this initial finalization slice.

This differs from leaving every uncertain case unfinalized. If the root authority cannot authenticate the caller, compare the reservation, or safely establish a bounded observation, it must still leave the journal unfinalized: no trusted fact exists to record. Once an authenticated, reservation-bound root observer can state a specific uncertainty, immutable unknown provides useful operational visibility without inventing success. A single `unknown` cannot certify cleanup, so its evidence schema must not imply a closed or empty cgroup when those facts were not verified.

## 3. Bind evidence to the full reservation and execution profile

Maintain the security review's hard boundary. The root-only listener receives only a fixed generation selector. Server-owned protected catalog data resolves task, repository and baseline, attempt, worker, cgroup and evidence paths. Verify the kernel UID on the accepted connection before reading the bounded request, and independently verify the actual serving process using protected systemd/PID/socket attestation. A root-created listener's apparent peer credentials are not independent proof of the currently serving process. Direct worker access to the underlying Restate handler must be denied, not merely discouraged by the front door. [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html), [root grant adapter](../../../../../clean-room/crates/control-plane/src/root_launch_grant.rs).

Under the same object's exclusive lock, compare the entire stored reservation and current claim: task, generation, spec, worker, attempt, token hash and immutable deadline values. Root must also derive and recompute the full launch binding from that reservation and the exact protected launch catalog and recipe; a caller-provided hash is not authority. Lease expiry after reservation does not erase the reservation or require reviving a worker capability. Reject missing reservation, mismatched binding, changed request, or a second differing finalization.

For `evaluated_pass` and `evaluated_fail`, require a root-owned immutable evidence envelope with the exact root closure, same-boot cgroup identity and verified frozen/empty observation, exact reconciled full IDs, terminal create/start operations and nonrestartable owned services/jobs, plus the independent evaluator's identity and receipt. Bind the root snapshot file hashes to the actual evaluated commit and verify committed blobs equal evaluated bytes. Both outcomes need evaluator provenance; failure must include the authenticated failing result, not a guessed verdict. Every root record must be opened without following links, checked for owner, mode, single link and ACL, bounded, and pinned across reading. If any mandatory proof is missing, record only a properly authenticated unknown or leave the task unfinalized; neither a worker claim nor a successful HTTP reply fills the gap.

For `unknown`, do not require an evaluator receipt or successful reconciliation that by definition might not exist. Require the full reservation/profile identity and a root-authenticated, immutable description of which bounded observations succeeded or remain unresolved. Never serialize absent fields as true or infer that a Docker object is gone from an empty listing. Unknown actual spend remains unknown for all three variants. The exact durability and authority of these evidence producers remains a gate, not an assumption.

## 4. Keep registry append outside finalization

Finalizing a previously reserved generation must work using its retained protected catalog and claim history even if no new registry entry can be added. Appending a future generation is a separate operation and cannot reset the old reservation, erase historical evidence or make an earlier unknown a pass. The current append validator is source-only; it neither authenticates scopes nor enforces admission. A shared root admission/upgrade lock, exact history retention, bounded-capacity behavior, journal replay, versioned deployment, and fresh process/socket attestation remain prerequisites. [Registry append proposal](../2026-10-29-nuc-root-supervisor/registry-append-protocol.md), [Restate deployment versioning](https://docs.restate.dev/services/versioning).

Before accepting this slice, use disposable Restate and Postgres to test expired-but-reserved finalization, wrong peer and direct ingress, substituted reservation/catalog/evidence, concurrent equal and differing requests, lost reply after journal commit, restart, SQL commit/lost acknowledgement, projection deletion and reexport, and continued worker mutation denial. Check earlier catalog histories through a distinct immutable SDK endpoint without force registration. A separate cgroup/engine and evaluator test must prove the concrete evidence producers; unit mocks of the journal cannot establish those host facts. Until those gates pass, this is a protocol decision, not a production completion claim.
