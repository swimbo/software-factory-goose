# Application security: exact root authorization at the journal

**Recommend the proposed protected authorization file**, conditional on the controls below. Under the stated trusted root, PID1 and SDK-code boundary, a create-only root-published digest of the exact canonical finalization request can authorize that one record even when another process in the private namespace can call the journal directly. It does not authenticate which local process delivered the record, prove root is uncompromised, authorize arbitrary future records, or approve promotion. Root publication is the authorization act: a previously queued or concurrent direct caller may deliver the same record as soon as publication completes. The operator must not treat the later socket call as a second required authorization.

The existing [claim handler](../../../../../clean-room/crates/control-plane/src/workflow.rs) and [reservation](../../../../../clean-room/crates/control-plane/src/launch_reservation.rs) serialize and fence claim mutation, but they currently do not establish root authorization against direct journal ingress. The [root evidence reader](../../../../../clean-room/crates/control-plane/src/root_finalization_evidence.rs) demonstrates descriptor-relative no-follow root-owned protected-file reading for mode 0600; the [native public canary](../../verification/2026-10-30-nuc-root-evidence-reader-canary.md) is bounded evidence for that reader, **not** proof for a new mode 0444 publisher or cross-UID authorization. A separate read-only 0444 implementation must preserve equivalent owner, single-link, mode, bounded length, no-ACL and nonwritable ancestor checks while allowing UID 2000 directory traversal. Root 0600 evidence and request bytes remain inaccessible to that UID. Linux path traversal itself depends on search permission for every ancestor ([path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)).

Before publishing, the root-only producer must independently authenticate the fixed generation and full reservation/catalog/recipe, root grant, and actual outcome evidence; the narrow unknown-cleanup implementation must deny pass/fail until their independent evaluator provenance exists. Resolve every path from fixed canonical generation, not caller-provided paths. Compute the request digest from the same versioned canonical encoding the journal uses. Create the bounded strict authorization file exclusively, verify root ownership/mode/link/ACL and exact task/generation/digest, fsync file and parent, and never overwrite, remove or reuse it. A partial publication or ambiguous fsync is not authorization: retain intent and fail closed until explicitly reconciled. Publication only after evidence verification is crucial because later direct callers can race the intended root delivery.

Inside the same exclusive claim-object handler, perform the protected fixed-path read in a durable step, bind the authenticated file's exact task, generation and digest to the request and stored reservation, and reject missing, unsafe, malformed, substituted or different bytes. Store the immutable finalization and outbox as the consensus envelope; retain the original launch fence and unknown spend. Exclusive handlers serialize on the same object key ([Restate handlers](https://docs.restate.dev/foundations/handlers)); the external filesystem read is nondeterministic and must be journalled for replay ([Restate durable steps](https://docs.restate.dev/develop/ts/durable-steps)). These current documents describe platform semantics, not an acceptance result for pinned Rust SDK 0.12.1; test that version. Define missing/invalid authorization as a terminal refusal rather than an indefinitely retried invocation that could awaken after later publication. An identical already-authorized request may return the existing record; changed replay conflicts. Direct `status` and reexport require separate disclosure, scope and idempotency checks and cannot grant eligibility by stale SQL.

A root-held signing key would provide portable offline verification, but introduces private-key storage, rotation, revocation and recovery dependencies. It does not improve this narrowly local boundary if root, the filesystem, PID1 and the SDK process/code are trusted. Conversely, network namespace membership or a shared-port firewall cannot distinguish an authorized handler request and does not close the bypass. If UID 2000 can replace the file, a parent, mount, binary or root publisher, or manipulate the canonicalizer, the digest scheme is insufficient and must remain disabled.

Before adoption, run disposable Restate/Unix tests proving: no file, unsafe owner/mode/ACL/parent/symlink/hardlink, malformed or duplicate JSON, wrong task/generation/digest, substituted evidence and direct forged requests all deny; a valid root-published file permits only its exact body both through root ingress and direct delivery; same concurrent requests converge, changed bodies conflict, and missing-auth requests do not later spring into success; publication crash and journal commit/lost-reply/restart preserve uncertainty and never repeat external effects. Verify UID 2000 can read only the public authorization and cannot mutate it or read root 0600 evidence, and verify old histories and permanent worker fences remain intact. These are required tests, not completed evidence. No authorization file is a promotion decision or permission to register, activate, or launch another generation.
