# Application-security position: root finalization

## Recommendation

Adopt the additive root-finalization protocol in the same exclusive claim object, with a single versioned state envelope containing the immutable decision and its pending outbox event. Keep the reservation permanently fenced and preserve the legacy claim and projection as historical records. Actual spend remains unknown where it has not been established. This is a protocol recommendation; the [evidence ledger](evidence-ledger.md) grades evidence adequate for a design decision and insufficient for production acceptance.

I **maintain** that only a fixed root-owned catalog and independently verified root evidence may establish the result. I **concede** the operations reviewer’s point that an invisible record is insufficient: the initial acceptance slice must include an additive, authoritative status command and idempotent SQL reexport. I also accept the durable reviewer’s single-envelope design, subject to tests against the pinned Restate server and Rust SDK. These changes do not make an evaluated candidate approved or authorize another generation.

## Status and projection

The existing [claim journal](../../../../../clean-room/crates/control-plane/src/workflow.rs) blocks worker completion, renewal and claim after a launch reservation. [The reservation](../../../../../clean-room/crates/control-plane/src/launch_reservation.rs) remains present after expiry. The old [receipt and projection](../../../../../clean-room/crates/control-plane/src/projection.rs) require numeric spend and bind an `Evaluating` stage to a successful receipt. Reusing them would either falsify a number, weaken the fence or invent a migration. Preserve their meaning.

The first slice should expose an authenticated CLI status that reads the root-finalization authority and clearly distinguishes `unfinalized`, `evaluated_pass`, `evaluated_fail`, `unknown`, and projection `pending` or `quarantined`. A pass says evaluation passed, actual spend is unknown, and promotion is pending the separate human action-bound decision. It must never present SQL alone as authoritative: SQL is a derived read model, and an absent, stale or conflicting row must be visible as such. An unavailable authoritative read is unavailable, not a negative or a pass. Preserve legacy claim status separately rather than silently replacing it.

One envelope should include the immutable finalization and its versioned pending outbox item. Deliver to SQL with stable event identity, payload equality checking, transactional idempotency and explicit conflict quarantine; reexport must reconstruct the same additive summary after projection loss. Do not wait for SQL to acknowledge before the journal can truthfully record finalization, and do not let a SQL timeout cause a second external effect. Restate describes serial exclusive handlers per object key, but shared handlers may run concurrently; use and verify one envelope rather than assuming two separate writes are externally indivisible. [Restate handler semantics](https://docs.restate.dev/foundations/handlers), [durable research](durable-research.md).

## Unknown, failure and replay

I **maintain** that unknown must never turn into success by changed replay. I **concede** the operations recommendation for an immutable terminal `unknown` record with separately appended recovery observations, provided those observations do not overwrite, reinterpret or promote the original. This gives the operator an honest status and prevents an ambiguous external effect from being silently converted into a completed one. Absence of an authorized finalization remains distinct as `unfinalized`: it means no record was accepted, not that cleanup or evaluation failed. An unavailable or mutable evidence source may therefore require remaining unfinalized rather than asserting even an unknown outcome as an established fact.

An identical replay must return the same canonical decision; a changed result, evidence, reservation or scope is a permanent conflict. Every recovery observation needs its own identity, provenance, time and digest, with no automatic transition to pass, release of the reservation or reopening of worker mutations. A new adjudication that would advance the pipeline needs a separately designed and authorized protocol. A legacy state migration is not implied.

Define the three records with different minimum evidence. All accepted types require authenticated fixed root ingress; exact stored task, generation, attempt, repository and baseline; recomputed complete reservation and root-grant/catalog binding; and a versioned root observation identifying its evidence and uncertainty. An `evaluated_pass` additionally requires complete immutable snapshot, independent evaluator receipt, exact committed blob hashes, verified closed same-boot/inode cgroup, both container IDs absent, terminal create/start and no restartable broker/relay jobs. An `evaluated_fail` requires an authenticated independent evaluator failure tied to the exact immutable candidate and the same verified shutdown/reconciliation; it need not contain a successful commit or passing metrics. If an evaluator never produced a trusted failure receipt, record unknown or remain unfinalized, never fabricate a failure. An `unknown` can omit candidate, evaluator and successful cleanup receipts, but must explicitly identify which facts are unavailable and cannot assert closure, successful evaluation or exact spend without evidence. The immutable record should encode these as typed options, not interpret missing fields as false, zero or success. A validator must reject a purported pass or fail whose mandatory evidence is missing.

## Authority and binding

The root request should carry only the fixed generation selector; catalog-selected paths and values must not be delegated to the peer. The accepted Unix connection must be checked for UID 0 before any bounded body read. Linux documents that `SO_PEERCRED` reports peer credentials associated with connection or socket creation, which is not proof of the current service behind an inherited listener. Require separate protected post-start process and endpoint attestation, and enforce private Restate ingress so a worker cannot call the new handler directly. [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html), [root launch adapter](../../../../../clean-room/crates/control-plane/src/root_launch_grant.rs).

The handler must compare the complete canonical reservation and active claim, including worker, attempt and token hash, and independently recompute the full root catalog/recipe binding. A caller-supplied digest by itself proves nothing. A persisted expired reservation remains valid for matching historical finalization but never grants a fresh lease. Evidence must be opened from protected fixed locations using pinned descriptors, no symlink following, regular single-link files, required ownership and mode, ACL rejection, and bounded content; verify producer identity and hashes against actual bytes. Root credentials and root-owned files are trust assumptions, not protection against malicious root or a compromised Docker daemon. Record no external Docker, Git, provider, approval or cleanup action inside the retryable finalization handler.

## Registry and release gates

I **concede** that registry append is not necessary to record the already reserved generation. It is a separate prerequisite before a new generation can be admitted, with historical entries retained and a separately reviewed admission lock, versioned deployment and fresh process attestation. Finalization cannot trigger registry append, restart, force registration, eviction or promotion. [Registry protocol](../2026-10-29-nuc-root-supervisor/registry-append-protocol.md), [Restate versioning](https://docs.restate.dev/services/versioning).

Before accepting this slice, use disposable pinned Restate/Postgres and distinct SDK URI to prove expired-but-reserved finalization, immutable unknown/failure/pass, wrong UID and direct-ingress refusal, complete binding substitutions, forged or mutable evidence, in-flight container operations, and worker mutation denial before and after finalization. Inject loss before and after journal acknowledgement and SQL commit, race identical and different finalizers, restart, delete SQL projection and reexport, and confirm old histories remain readable without force registration. Assert one envelope and event, exact replay versus changed conflict, no repeated external effects, and honest CLI pending/quarantine behavior. The scoped implementation remains blocked if root evidence or evaluator provenance cannot be demonstrated; existing fixtures do not satisfy that proof merely by returning success.
