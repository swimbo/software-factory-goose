# Durable systems research — root finalization

Recommendation: an additive, root-authenticated, single-use finalization on the **same exclusive claim object**, with one durable envelope containing both the immutable decision and its pending projection event. Keep the launch reservation permanently fenced. Do not call the legacy worker completion route, infer a zero spend, or authorize promotion. A separate durable history/projection type is necessary; the existing claim projection cannot truthfully express this result.

## Evidence

1. Restate documents Virtual Objects as isolated state per key with one writer; exclusive handlers serialize on a key while shared handlers may read concurrently. This supports a reservation/finalization compare under the task key, but concurrent shared readers mean two separate state writes should not be casually called one externally atomic update. Store the finalization and pending outbox entry in one versioned state value; test observed crash boundaries on the pinned server/SDK. [Restate services](https://docs.restate.dev/foundations/services), [handler concurrency](https://docs.restate.dev/foundations/handlers).
2. Local [`workflow.rs`](../../../../../clean-room/crates/control-plane/src/workflow.rs) has exclusive `ClaimLeaseJournal` handlers; `initialize`, `claim`, `renew`, and `complete` first call `ensure_launch_unreserved`. `reserve_current_launch` derives the lease proof from the journal and persists `launch_reservation_v1`; [`launch_reservation.rs`](../../../../../clean-room/crates/control-plane/src/launch_reservation.rs) binds task, spec, worker, attempt, token digest and expiry. A reservation is not a root consumption or cleanup receipt, and its persisted existence is not cleared on expiry. Finalization must compare the stored full reservation and preserve that fence.
3. The current root launch binding is stronger than journal scope alone: [`root_grant.rs`](../../../../../clean-room/crates/watchdog/src/root_grant.rs) binds the reservation to root launch catalog/recipe. A finalization that only compares task and generation would permit a receipt from a different execution profile. Bind the full canonical reservation plus exact root launch-catalog/recipe digest and evaluator evidence; recompute the full binding, rather than accepting a caller-asserted digest as proof.
4. The current source writes a bounded claim-event history and claim state within an exclusive handler, then awaits a journaled SQL delivery (`persist_claim_transition`); [`projection.rs`](../../../../../clean-room/crates/control-plane/src/projection.rs) detects idempotency-key/payload conflicts and version ordering. Restate documents that durable-step results are replayed and failures retry, not that an external SQL/HTTP effect executes physically once. Lost acknowledgement must be handled with idempotent destination insertion and conflict checks; an outbox record and its receipt must remain pending/unknown until verified. [Durable steps](https://docs.restate.dev/develop/ts/durable-steps), [Restate actions](https://docs.restate.dev/foundations/actions).
5. `ClaimLeaseState` and legacy completion demand a worker proof, unexpired lease and an existing receipt format; completed receipts include numeric spend. `complete` is deliberately blocked after reservation. Reusing that route would either require weakening a permanent fence, accepting an expired worker capability, or inventing a spend. An additive immutable root-finalization status is compatible with existing history; any later migration to `Evaluating` needs an explicitly reviewed unknown-cost schema and projection change.
6. Restate documents unique immutable endpoints for deployments and keeps in-flight invocations on their original version; forced same-endpoint re-registration can produce journal mismatches. [Restate versioning](https://docs.restate.dev/services/versioning). The repository locks `restate-sdk` **0.12.1** in [`Cargo.lock`](../../../../../clean-room/Cargo.lock); current web docs describe the current platform and use TypeScript examples, so they do not establish exact semantics of this historical pinned SDK/server combination. Verify source and disposable Restate replay before adoption.
7. A root-created Unix socket and `SO_PEERCRED` identify the connecting UID; a systemd-created listener's client-side peer can identify its creator, not the actual serving process. Preserve the existing manager/PID/socket attestation boundary; root-only listener is not a cryptographic signature over an arbitrary request. The journal itself must compare to its own reservation, not trust ingress-selected proof fields. Local root grant adapter [`root_launch_grant.rs`](../../../../../clean-room/crates/control-plane/src/root_launch_grant.rs) is the analogous fixed-scope boundary.

## Options

| Option | Benefit | Failure/constraint | Verdict |
|---|---|---|---|
| Add finalization and outbox in same task object | Preserves old claim/receipt shape and permanent reservation; supports exact replay | Needs new root listener, immutable evidence validation and separate projection | Preferred, gated |
| Change legacy `complete`/claim stage | Could feed existing projection sooner | Breaks reservation fence or invents missing cost; alters replay/schema and worker authorization | Reject for initial implementation |
| Write final result directly to Postgres | Simple reporting | Bypasses journal authority; lost ACK and forged projection can become apparent success | Reject |
| Separate root-only object | Independent schema | Cross-object atomic compare against claim reservation is not established; race and split authority | Reject without a proved protocol |

## Minimal protocol and discriminating tests

1. Root validates bounded, immutable, root-owned evidence for closed/frozen/empty same-boot cgroup, terminal producer and jobs, exact reconciled IDs, writer/relay closure, snapshot digests and evaluated commit/blob identity. The finalizer accepts only fixed catalog-derived generation; unknown result is recorded only as explicitly unknown, never a pass. Root process trust and independent evaluator identity must be separately proven.
2. On authenticated root ingress, the same exclusive task object reads the existing reservation and claim, compares task, repository/base, generation, attempt, worker and token digest, plus recomputed full binding and immutable evidence identity. It writes a single bounded envelope `{schema, reservation_binding, finalization, outbox_event}` in one state key. It does not use lease expiry to revoke an existing reservation. Identical replay returns stored result; any changed byte or mismatched digest is terminal conflict. No clearing handler or reassignment follows from this record.
3. Deliver projection separately using a stable event identity, transactional idempotency/conflict detection and explicit quarantine on integrity error. A lost delivery acknowledgement must replay exactly the same payload; no external side effect is retried merely because the caller timed out. Treat unknown completion as unknown until authoritative read-back. This additive projection is not the existing completion stage and does not claim spend.
4. Test root UID versus worker/wrong socket, missing reservation, expired-but-reserved finalization, altered scope/attempt/binding/evidence, duplicate equal and duplicate changed, concurrent finalizers, crash immediately before/after envelope write and SQL commit/ACK, cap exhaustion, restart and historical four-catalog replay in disposable Restate/Postgres. Observe shared-reader behavior during recovery, rather than assuming multi-key atomic visibility. Test no worker claim/renew/complete even after finalization and expiry.
5. Registry append is a separate prerequisite for a fresh generation. The current append proposal is pure validation only; the shared admission/upgrade lock, immutable historical registry publication, bounded 16-entry lifecycle, restart/replay and fresh process/socket attestation are not implemented. Never force-register over the live endpoint or infer that a new SDK revision proves prior invocation recovery. See [registry append protocol](../2026-10-29-nuc-root-supervisor/registry-append-protocol.md).

Open questions: how to make an evidence envelope non-substitutable between validation and journal commit; how to prove evaluator output/commit identity and all Docker operations terminal; whether the actual SDK and server give the single-key durability and visibility expected above; how to drain or retain older deployments; and how to archive bounded history without deleting evidence. None is solved by this research or by the earlier failed model launch.
