# Application-security response — round 1

## Failure evidence

I **maintain** the moderator’s proposed resolution: an evaluated failure requires an authenticated independent failure receipt bound to the exact immutable candidate snapshot, verified shutdown and exact-root reconciliation. A commit is optional for a failure; if one is supplied, its committed blobs must match that same snapshot. Requiring a successful commit or passing metrics to represent a failed evaluation would make a real failure unreportable and encourage fabricated evidence. A process failure or missing evaluator receipt does not itself prove an evaluated failure: it is `unknown` if the root observation is authenticated and sufficiently bound, or remains `unfinalized` when authority or the binding cannot be established. [Evidence ledger](evidence-ledger.md), [security position](security-position.md).

The root evidence validator must encode these differences explicitly. A pass needs its evaluated snapshot, independent pass receipt, matching committed blobs and complete shutdown proof. A failure cannot omit its actual failed snapshot or authenticated receipt, even when it has no commit. An unknown may identify unavailable evidence but must not populate missing fields with success-shaped defaults. An identical replay returns the original record; changed evidence conflicts. None of these records clears the reservation or gives the worker a new claim. The existing permanent fence and worker-completion check are in [launch_reservation.rs](../../../../../clean-room/crates/control-plane/src/launch_reservation.rs) and [workflow.rs](../../../../../clean-room/crates/control-plane/src/workflow.rs).

## Projection and eligibility

I **concede** that SQL pending alone need not block eligibility, provided the eligibility adapter reads and validates the authoritative immutable `evaluated_pass` and independently binds the exact generation, candidate, baseline and evaluation evidence. This is an eligibility determination only. A separate human action-bound approval is still required; neither pending delivery nor the finalization record is promotion approval or proof of pipeline completion. A stale or missing SQL row must never authorize eligibility. If the authority is unavailable or its binding cannot be verified, eligibility is unavailable.

A **known projection integrity conflict** must quarantine downstream advancement until it is reconciled. Pending delivery and a contradictory committed row are different states: the former can be tolerated when the journal supplies authoritative evidence; the latter is evidence that an integrity invariant has failed and cannot be ignored merely because one copy looks valid. The SQL exporter must use stable event identity and compare payloads on replay, retain pending or quarantined status, and support explicit reexport after deletion. SQL remains derived; it cannot manufacture a pass or override an authoritative unknown. [Durable research](durable-research.md), [operations position](ops-position.md).

## Remaining consensus and proof

I confirm the remaining protocol: one bounded versioned envelope in the same exclusive claim object, containing immutable finalization and pending outbox; the existing reservation and legacy state remain unchanged; actual unknown spend remains unknown. The root-only listener checks accepted peer UID before a bounded request, independently attests the serving process, resolves fixed catalog scope, and denies direct backend bypass. Peer credentials alone do not establish the identity of a process serving an inherited listener. [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html).

Recording an existing reserved generation does not require registry append. Admission of a fresh generation is separate and must preserve prior history and its own attestation and replay gates. The finalizer performs no Docker, provider, Git, cleanup or approval effects. A later schema migration is separate from this decision.

These are design conclusions, not acceptance evidence. Disposable pinned Restate/Postgres tests must still prove exact and changed replay, concurrency, lost journal and SQL acknowledgements, projection deletion/reexport/conflict, old-history readability, wrong peer and direct ingress, evidence substitutions, and continued worker-mutation denial. Tests must establish the actual single-envelope and outbox behavior; documentation of exclusive handlers is not proof of this implementation. [Restate handlers](https://docs.restate.dev/foundations/handlers), [moderator brief](disagreement-brief.md).
