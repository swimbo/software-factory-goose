# Durable review: exact root authorization amendment

Conditional support. A root-owned, immutable, per-generation authorization for the canonical request digest is sufficient to distinguish an exact root-approved payload from a changed direct private-HTTP call under the stated trusted-root, manager, journal-code and protected-filesystem boundary. Namespace membership alone is not sufficient. Publication is the authorization act; the direct client may at most deliver the same root-authorized record and cannot add human promotion approval. This is not a signature and does not resist a compromised root administrator or trusted journal code.

Before publication, root must validate the fixed catalog and full reservation/profile binding, all variant-specific immutable evidence and the exact canonical request bytes. The journal recomputes the digest from its received typed request, derives the canonical generation path itself, reads a strict bounded no-follow single-link root:root 0444 file with no ACL and trusted non-writable ancestors, and compares task, generation and digest. It must still validate against the stored reservation and claim inside the same exclusive object handler. File readability is not permission to publish or alter the authorization. The request and evidence stay private; only the digest record is group/world-readable.

Use a durable read step for the protected authorization and a terminal mismatch/absence result, without including nondeterministic filesystem reads directly in replayed logic. A journal retry of an already completed durable read may replay its recorded value; it must not be described as a fresh current filesystem check. A new invocation after publication can read the new authorization; an earlier terminal denial must not be silently rewritten by replay. Neither an unauthorized pending invocation nor its idempotency key may prevent a later valid root invocation indefinitely. Preserve the permanent `launch_reservation_v1` and one-envelope finalization/outbox conflict rules; identical authorized delivery returns the immutable result, changed delivery conflicts. [Restate durable steps](https://docs.restate.dev/develop/ts/durable-steps), [handler concurrency](https://docs.restate.dev/foundations/handlers).

Publish create-only, with bounded canonical bytes, fsync of the temporary file and containing directory, an immutable no-overwrite final path, and durable root publication intent. An exclusive publisher lock and shared journal-read lock should prevent a reader racing a partially written file. Crash and reboot are important: a root publisher may die between making a pathname visible and the directory fsync. Recovery must not infer a fully durable publication merely from a pathname, and it must never overwrite or delete the existing authorization. A root recovery step must validate the exact intent, payload and fixed evidence and finish or classify that state before admitting new requests. The implementation must specify how the reader distinguishes a publication whose final directory fsync was not acknowledged; absent that proof, report the gap and fail closed rather than claiming crash-atomic authorization.

Required disposable tests: wrong UID/direct HTTP before publication with a syntactically valid forged request; mutated outcome/evidence/digest after publication; exact authorized direct delivery; competing equal and differing calls; root publisher death before file fsync, after file fsync, after link/rename and before directory fsync, and after durable publication; journal commit/lost response and process restart; symlink, hard-link, ACL and overlength controls; and a new invocation following an earlier denied invocation. Test the pinned Rust SDK/Restate implementation and actual native permissions. Verify that no raw request, evidence or credential reaches logs and that a successful authorization cannot alter promotion or clear a reservation.

The authorization mechanism is a necessary admission check, not a substitute for proving the root finalizer, evaluator, exact cleanup or independent brake. No production adoption or activation follows from this review.
