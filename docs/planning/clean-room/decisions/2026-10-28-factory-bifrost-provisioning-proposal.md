## Exact intended delta (semantic, not an executable API payload)

For each newly approved task and attempt, a trusted operator-side broker would create **one new virtual key** with a unique factory/task/attempt identifier, expiry no later than the earlier of 15 minutes or the current lease deadline, no generic provider/MCP/admin access, and a key-level budget of at most `$0.75`. Its key value stays in a protected broker-owned secret store and is sent only by the trusted gateway process; it is not passed to Goose, command lines, logs, Git, or the user. Stop, lease revocation, task completion, or expiry revokes that key. Renewal requires a fresh authorized credential issuance and must draw on the same non-resetting task ledger; it must never create a new $0.75 allowance.

Add exactly **three new virtual-key-scoped rules** under the new key, with request model match `model == "auto"` only and the same tier ordering and primary models shown above: COMPLEX first, MEDIUM second, then unconditional auto default. Use the same ordered fallback set only after every fallback is reviewed against the same bounds below; until then the new rules must have no fallback and inference stays disabled. No factory rule may match the desktop key, and no existing desktop key, route, priority, target, fallback, provider credential, or context-relay configuration is edited. Configure the new key to allow only the explicitly reviewed primary/fallback provider/model combinations and the single intended inference API; deny all other models, provider routes, admin/governance endpoints, MCP, and direct provider egress.

The exact deployed-version API payloads, policy field names, expiry semantics, route-target ACL semantics and `auto` precedence still need verification against the running image's API schema. This semantic delta is intentionally **not** a copy-and-paste command or an assertion that the newest upstream API matches the current image. The upstream [Bifrost v1.5.0 release notes](https://docs.getbifrost.ai/changelogs/v1.5.0) describe evolving virtual-key and routing semantics; establish the deployed version and schema first.

## Mandatory spend and routing contract

The existing atomic factory reservation authority must remain the sole per-task ledger, using integer microdollars and a non-resetting `750000` microUSD total. Before every provider call, reserve a conservative upper bound derived from a reviewed contract covering **every primary and enabled fallback**: aggregate maximum billable input, output, reasoning, cache/routing surcharges, fixed charges, request size and the exact output-token limit accepted by each endpoint. A virtual-key budget is defense in depth, not proof that concurrent/in-flight calls cannot overspend. Ambiguous or lost provider responses retain their reservation; no automatic retry after a possibly accepted call. If any model price, token limit, output-cap semantics, route selection, fallback, or accounting authority cannot be proved, fail closed before calling the provider. Current `ReviewedModelContract` accepts one exact requested model and text-only messages; `auto` routing and Goose tool calls require a reviewed extension that handles all possible served models and payloads, not a substituted price estimate.
