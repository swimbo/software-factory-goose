# Linux response, round 1

I agree with all four moderator decisions and maintain the Unix-admin plus old-endpoint retirement direction, conditional on the bounded pinned-binary experiment. I have no remaining high-severity disagreement for that experiment.

1. **8080 and endpoint retirement.** Agree. A synthetic same-UID invocation that produces an old-SDK effect through 8080 before retirement, followed by independently verified old endpoint retirement and failed direct and forwarded effect attempts, is the relevant falsifiable control. Include an existing connection and an accidental descriptor-leak control; do not require installing a hypothetical nft policy merely to reproduce this route. The negative must observe the effect marker and endpoint state, not interpret an HTTP failure or timeout alone as proof. Test the full set of old endpoints in the later real plan; the two-SDK canary proves its fixture only. [Operations position](ops-position.md); [Restate versioning](https://docs.restate.dev/services/versioning).

2. **UID2004 fixed administration.** Agree. PID1 may execute a fixed root-owned, digest-pinned operation as the trusted UID2004 journal identity, with the protected data tree and socket permissions unchanged. This is root-mediated authority executed as UID2004, not proof of a UID0 connection. Inputs are limited to immutable root-selected operations and protected records; no caller-selected address, SQL, HTTP body, command or file descriptor. Require actual peer/UID, capability-empty and `NoNewPrivileges` observations, bounded output, create-only root intent and receipt, and a negative UID2000 direct-socket control. No new group, broad capability or arbitrary persistent admin daemon is necessary for the canary. UID2004 and root are in the stated trust boundary; accidental descriptor transfer remains a test. [unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html); [Restate server security](https://docs.restate.dev/server/security).

3. **One disposable canary.** Agree. One new factory-owned namespace, fresh data root and two synthetic SDKs can cover actual Unix path, inode, modes and ACLs; TCP-admin refusal; valid fixed UID2004 administration; same-UID direct and 8080 forwarding positive and post-retirement negative controls; classified old-pinned, queued and unpinned work; one non-force registration and a lost-reply case; and restart of the owned fixture. Positive effect controls must run before the negative assertion. Exact resources and processes must be recorded and cleanup limited to those resources after terminal confirmation. No shared namespace, existing database or existing service is changed. Host reboot, real namespace loss, full production workload and live endpoint retirement are later gates, not demands on this spike. If the exact Unix configuration or permissions fail, preserve its evidence and reconsider nft as a fallback. [Pinned listener configuration](https://github.com/restatedev/restate/blob/v1.8.0/crates/types/src/config/common.rs); [durable position](durable-position.md).

4. **Live cutover conditions.** Agree. A root-owned persistent closed intent precedes any live action; retain a recoverable journal backup, deployment histories and old unit definitions. Fence each old service and socket with exact no-job, no-process and no-surviving-listener evidence, plus restart-safe refusal, before observing the decisive work classification. Unresolved nonterminal old work blocks normal completion unless it is explicitly and immutably quarantined as unavailable and the actual admission policy enforces that quarantine. Bind the single registration to the server-minted ID; validate the new process and replay all prior histories before reopening. Preserve unknown registration or effect; never silently cancel, force-register, remove history or restore an ungated endpoint after new admission. Failure or lost acknowledgment retains the closed marker and exact evidence. [systemctl 257](https://www.freedesktop.org/software/systemd/man/257/systemctl.html); [operations position](ops-position.md).

A successful canary selects a direction for a reviewed implementation; it is not a live transition, production acceptance, candidate promotion or evidence that the existing journal has drained.
