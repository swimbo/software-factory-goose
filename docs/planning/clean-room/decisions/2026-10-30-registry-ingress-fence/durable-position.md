# Durable-runtime position: fence admission before measuring drain

## Decision

Use a disposable copy of the pinned Restate executable and fresh data to test **root-mediated admin plus retirement of every ungated SDK endpoint**, including an explicit fence on the 8080 invocation path during the transition. Do not choose a live firewall change or a Restate restart yet. If the exact binary demonstrates that admin can be configured Unix-only while keeping required ingress and fabric connectivity, prefer a protected Unix admin socket with a fixed root operation broker. If that test fails, compare a narrowly scoped namespace output policy plus the same broker; the policy must close admin, direct SDK access, and forwarding through 8080. Neither alternative can establish a fence by itself while an ungated handler remains reachable.

The immediate discriminator is not which mechanism has fewer configuration lines. It is whether any old invocation can still reach an effect after the fence is declared, including through an already established or transferred connection, while the journal and old histories remain intact. Root, PID1, Docker daemon and Restate UID 2004 are trusted for this scoped decision. The tests must still detect accidental inherited or passed descriptors; that is an operational leak test, not a claim of resistance to compromise of a trusted principal.

## Why the order matters

The installed factory topology sends SDK and helper traffic through the private namespace: Restate ingress is 8080, admin is 9070, and active old SDKs use separate listener ports. The root transition lock is observed by participating code only. It cannot stop the older listeners or an independent admin caller. [Installer](../../../../../clean-room/deployment/nuc_private_runtime_install.py); [transition gate](../../../../../clean-room/deployment/nuc_registry_transition_gate.py); [brief](brief.md).

Restate's own documentation states that self-hosted admin does not authenticate its callers at the application layer. Its request identity feature establishes a different boundary, from Restate to an SDK, and is not a protection for the admin API. [Server security](https://docs.restate.dev/server/security); [service security](https://docs.restate.dev/services/security). A filter that denies direct UID 2000 access to admin and SDK ports, but still allows that UID to invoke through 8080 while UID 2004 can reach old SDKs, leaves a forwarding route to the ungated handler. This is a source-grounded inference, not a claim that an exploit has already been run. The first synthetic negative control should demonstrate the route, and the selected fence must then prevent its counter from changing.

Freeze admission first, then inspect durable work. Acquire the root exclusive gate and fsync the transition intent; pin boot, namespace, expected listener and service identities, and the exact preexisting policy. Establish the independent fence, eliminate or account for preexisting accepted connections and manager-held activation sockets, and keep verifying the fence while collecting journal evidence. Only then can a drain query be interpreted. A SQL zero taken before that point can become stale immediately. The installed schema exposes deployment attribution, but schema availability is not proof that all queued, scheduled, suspended, in-flight and unpinned cases are correctly classified. [Schema probe](../../../../../clean-room/deployment/nuc_registry_drain_schema_probe.py); [Restate 1.8.0 tree's 1.7.4 notes](https://github.com/restatedev/restate/blob/v1.8.0/release-notes/v1.7.4.md).

A true zero means the tested classification found no relevant pending or active work after a sustained, verified admission fence. Retiring an old endpoint while a pinned invocation remains outstanding produces a different outcome: **retained but unavailable**, not drained. Restate's documented versioning associates a retry with its original deployment; stopping that deployment does not migrate the work. [Service versioning](https://docs.restate.dev/services/versioning). Preserve its deployment ID, invocation and queue state, and never treat cancellation acknowledgement as proof that an external effect was undone. If any unresolved old invocation could still affect a scope that would be admitted under the new revision, keep that scope and transition closed until an explicit reconciliation proves safety. A separately justified partition may remain closed while unrelated work is admitted only if the implementation actually enforces that partition; no current evidence establishes such a partition here.

## Smallest decisive spike

Create a task-owned private namespace and fresh disposable Restate state, using the exact pinned executable and two fixed synthetic SDK revisions. Give one handler a durable counter and another a controlled barrier so the test can distinguish an accepted request, an in-flight effect, a queued request and a terminal result. Record exact server-minted deployment IDs and create old-pinned, unpinned and completed histories. Establish observable positive controls before relying on any zero.

First reproduce the suspected bypass: block UID 2000's direct access to the old SDK and admin, keep 8080 and Restate-to-old-SDK reachability, and show whether the counter can still change through ingress. Then apply the candidate closure and show that fresh calls, a connection established before the fence, and a descriptor intentionally passed or inherited across the roles cannot produce another effect. Cover IPv4, IPv6, alternate loopback addresses, unrelated benign traffic and both packet directions. Preserve allowed UID 2004-to-required-service traffic only where that permission cannot dispatch to an ungated old effect. Verify any nft rule ordering and counters, rather than assuming connection tracking handles established flows. Linux's `skuid` matches the originating socket's UID; it does not by itself identify the present process using a passed descriptor. [nftables metadata](https://wiki.nftables.org/wiki-nftables/index.php/Matching_packet_metainformation); [Unix descriptor passing](https://man7.org/linux/man-pages/man7/unix.7.html).

In the same disposable boundary, separately test the 1.8.0 per-service Unix admin configuration, actual socket path/mode/peer credentials, TCP-admin refusal, fixed root broker operation, and the existing SDK's ingress/fabric connectivity. The installed binary's help confirms unix/tcp/all; the pinned source defines common and per-service listener options. [1.8.0 common listener configuration](https://github.com/restatedev/restate/blob/v1.8.0/crates/types/src/config/common.rs); [admin configuration](https://github.com/restatedev/restate/blob/v1.8.0/crates/types/src/config/admin.rs). This does not authorize changing the real service. Test exact old service stop and restart fencing, including socket activation, existing clients, a manager restart and namespace loss. Preserve locally installed unit definitions; do not assume that masking an existing local unit or a runtime mask survives reboot. [systemctl 257](https://www.freedesktop.org/software/systemd/man/257/systemctl.html).

## Registration and recovery

After the verified fence and work classification, permit one root-authorized non-force registration of the new SDK. Fsync the registration intent before the POST, bind the actual returned server deployment ID to the immutable transition plan, and independently inspect its URI, handlers and process attestation. Validate every prior catalog and durable state against captured hashes and exercise exact idempotent replay, including a lost-ack control. Recheck the same fence, boot, namespace, unit and deployment identities before any transition completion or reopening.

A timeout is an unknown registration outcome, not a reason to issue the POST again. Reconcile the exact recorded attempt by read-only admin inspection and journal evidence; if uniqueness, source or effects cannot be proven, keep the marker and all old data. Crash controls must cover loss before fence confirmation, during an active old call, after registration dispatch, after acknowledgement and before completion publication. No recovery may remove a shared table, reset a claim, delete history, or silently revive an ungated SDK. Cleanup is limited to exact fixture-owned resources after their terminal state is proven.

I reject the marker plus count-only approach, direct UID filtering that leaves the 8080 forwarding route open, and stopping SDK4 while overlooking SDK1–3. I also reject adopting Unix admin based on documentation alone. The preferred Unix-and-retirement direction remains conditional until the pinned-binary canary proves the actual listener controls, retained-work semantics, and bounded recovery path. A green synthetic spike is evidence for that fixture, not production activation or approval to promote a candidate.
