# Round 1 response — Rust operations

Date: 2026-10-26. Inputs: [moderator brief](disagreement-brief.md), [ledger](evidence-ledger.md), and [previous position](position-rust-ops.md).

**I maintain my position on conservative startup refusal.** The isolated spike should create a fresh, private temporary directory, verify its owner and mode, and bind a new socket name. Any existing endpoint—including a socket presumed stale—causes refusal. Regular files, symlinks, duplicate listeners, unexpected parent ownership, and unsafe parent modes are explicit negative cases. No unlink-to-retry branch belongs in this experiment. Stale recovery adds liveness and race questions without improving proof of transport feasibility.

**I concede that my earlier cleanup wording was too absolute.** “Cleanup cannot delete a replacement endpoint” needs a threat boundary. Record the socket's file type, owner, device and inode after binding. Before removal, inspect without following symlinks; remove only when those attributes still match. If the path is absent or changed, leave it alone and report the mismatch. This is a proposed conservative rule, not an atomic kernel guarantee against a hostile same-UID process swapping the path after inspection.

The controlled replacement test is precise: create listener A and record its identity; rename A's pathname to a separate fixture pathname; bind listener B at A's original path; invoke A's cleanup; verify B's pathname remains and B accepts a connection. A second case substitutes a symlink or regular file before cleanup and verifies preservation. Clean fixture artifacts explicitly afterward. These tests prove replacement-before-check behavior. They do not prove resistance to an adversarial rename between metadata inspection and unlink, inode reuse, or same-UID compromise. A private directory constrains other principals; it does not exclude its owner. [Ledger identity limits](evidence-ledger.md).

**I maintain that direct client-side peer verification should remain explicitly deferred for this inert reqwest spike.** Inspection of pinned reqwest 0.12.28 found `unix_socket(path)` configuration and an internal Tokio `UnixStream::connect`, but no `peer_cred` API or credential propagation in that path. Its response `remote_addr()` returns an optional network address, not Unix credentials. Sources: [connector](/Users/bo/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/reqwest-0.12.28/src/connect.rs:709), [response](/Users/bo/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/reqwest-0.12.28/src/async_impl/response.rs:116). Tokio itself exposes peer credentials; an explicit UnixStream/Hyper client could inspect the actual connected stream, but that is a different client path requiring its own proof.

For this experiment, client assurance is limited to the verified private directory and expected socket ownership. Do not pretend a separate preliminary connection's credentials authenticate the subsequent reqwest connection. Record same-UID service substitution as unsupported. If AppSec requires actual same-connection server credentials before any future integration, that becomes a separate integration gate, not a reason to claim it exists now.

**I maintain the narrow acceptance vocabulary.** Report `transport_spike: passed`, `peer_mismatch: synthetic`, `peer_read_error: synthetic`, and `privileged_operations: unavailable`, plus explicit lifecycle results. Cap total experiment runtime and client request duration; use one bounded sequential test client. Production idle-connection, request-size, concurrency, and hostile availability guarantees remain unverified. The decision grade stays ADEQUATE for the experiment and INSUFFICIENT for privileged authorization, deployed identity isolation, or independent-brake readiness.
