# Application security response — round 1

Date: 2026-10-26. Scope remains the inert Unix-socket experiment described in the [moderator brief](disagreement-brief.md). No code or deployed authority changes are proposed here.

**Maintain:** the experiment must identify its trusted-directory assumption explicitly. The harness creates a fresh private directory, verifies its expected ownership and restrictive mode, refuses any preexisting endpoint, and retains control of that directory for the experiment. Server-side kernel credential checks remain mandatory, including denial on lookup failure. Their supported meaning is OS-principal identification, as recorded in the [shared ledger](evidence-ledger.md); they do not establish a particular human or distinguish same-UID processes.

**Concede:** client-side kernel peer-credential validation is not mandatory for this particular inert experiment. Protected-directory ownership checks and a harness-owned server are sufficient for its narrow feasibility claim, provided the result explicitly states that authenticated service identity over the client's actual request connection was not proven. I am not asserting that reqwest exposes or lacks a particular credential API; Rust operations owns that source-backed determination. Requiring a replacement client stack now would exceed the demonstrated need.

A separate client-side peer check, if easy with the pinned stack, would add useful evidence. However, checking a separate connection would not prove the identity of the connection carrying the HTTP request. Before integrating a real sensitive interface, the design must decide how the CLI authenticates the service endpoint and what same-UID compromise means. This remains an open design issue, not a blocker to inert diagnostics.

**Maintain:** cleanup must refuse to remove an endpoint whose recorded identity differs from the one created by this instance. Test a controlled sequence: create the original socket, replace its pathname with a separately created endpoint, invoke cleanup, and confirm the replacement survives. Also test ordinary cleanup and repeated cleanup. These are engineering acceptance criteria, not a claim of an atomic platform primitive.

**Concede:** that test proves only the exercised ordering. A pathname inspection followed by deletion does not, by itself, prove resistance to every intervening replacement. The accepted wording should be “controlled replacement preserved under the private-directory assumption,” not “race-free cleanup.” Active same-UID interference and comprehensive pathname-race resistance remain unproven. Conservative refusal or leaving an uncertain artifact for inspection is preferable to speculative deletion.

For availability, require finite experiment lifetime, finite client request deadlines, bounded request-body handling, and a bounded number of fixture connections. Concrete experimental defaults can be 30 seconds overall, two seconds per request, 1 KiB request bodies, and at most four fixture connections. These numbers are proposed test controls, not externally prescribed security limits. The server must not panic when credentials are unavailable. Sustained malicious-client resistance, production concurrency admission, and complete slow-client handling can remain explicit production gaps; the spike makes no availability certification.

**Maintain:** the result must separate local transport success, synthetic UID-denial coverage, and unavailable privileged functions. No successful diagnostic request can unlock promotion, dispatch, credentials, budget changes, or worker-result ingestion. Actual cross-UID denial, trusted human authorization, durable single-use approvals, and the independent brake remain open. With these limitations recorded, I support the bounded spike and do not request another architecture round.
