# Recovery position: independent brake caller

**Choose B conditionally:** introduce a clearly named production policy for the existing `bo` operator UID and a separately provisioned brake bearer, with the separately supervised nonroot brake frontend and stop-only root backend. Retain the existing `BrakePolicy` unchanged for consumers requiring a distinct ordinary operator and brake-caller UID. This is a proposed scope amendment, not authorization to install the frontend or a claim that any runtime gate passed.

R9 requires an independent brake key that remains inaccessible to an agent that only stole the operator token, and a watchdog usable despite ordinary control and database failure. The subsequent O4 decision specifies a distinct local human operator and action-bound approvals, explicitly without MFA or same-UID-compromise claims. Neither requires a new human SSH key. [R9](../../consensus-plan.md#r9--kill-switch--kill--pgid--an-out-of-band-brake-key), [O4](../2026-10-26-operator-auth/consensus-plan.md#post-debate-user-selection). Bo is an actual existing operator UID, while control, worker, evaluator, journal and brake frontend use separately provisioned UIDs. A separate random brake key and a root-owned private socket can enforce the specific credential-theft boundary if those other principals cannot read the key, become bo, replace the endpoint or use the root backend.

The distinction matters. Existing [`BrakePolicy::new`](../../../../../clean-room/crates/watchdog/src/lib.rs) explicitly enforces pairwise UID separation, including the ordinary operator when supplied correctly. Calling it with bo as brake UID but silently omitting bo from the exclusion list would evade its documented invariant. B is not that policy and must not be presented as satisfying it. It needs its own constructor/type, clear applicability and negative tests; old consumers retain the existing stronger contract. If the team decides that distinct operator and caller UIDs are a deployment requirement in addition to R9/O4, B cannot satisfy that requirement and A or another genuinely distinct-identity mechanism is necessary.

B adds no new privileged executable. The bo process still cannot stop using only an approval bearer: the frontend checks the actual kernel socket peer and a separate stop key, then the root backend independently admits only the frontend UID and a fixed stop/status operation for a registered opaque target. Provision the brake key separately from approval credentials. Limit directory traversal, key permissions and inherited descriptors so the worker, evaluator, journal and control identities cannot obtain it. Check wrong key, wrong and forged peer, duplicate credentials, unregistered targets, arbitrary paths/PIDs/verbs, ordinary bearer replay and root-backend bypass. Socket file permissions alone are not a bearer or human identity proof. [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html).

This recommendation makes no claim that a malicious process already running as bo is blocked from bo-readable keys or the client; bo's existing Docker group is root-equivalent administrative authority. [Docker security guidance](https://docs.docker.com/engine/install/linux-postinstall/). Two credentials accessible by the same compromised OS principal are not two independent factors or proof of human presence. The relevant narrower test is whether a compromised non-bo agent with an exfiltrated approval token can obtain or invoke the brake. If the agent can run as bo or read bo's brake key, the R9 scenario is not satisfied; quarantine production admission and revisit custody rather than relabeling the compromised bo threat as harmless.

Option A, a fixed root-owned setuid client that permanently drops into a distinct brake caller, preserves the present strict UID contract and could prevent ordinary bo processes from directly reading the root-held secret. It also adds a root-executed program, separate account and privileged transition; the first instructions, dynamic loader, environment, inherited descriptors, group clearing, saved IDs and capability drop become part of the trusted computing base. Linux documents that `no_new_privs`, `nosuid` and tracing can suppress a setuid transition, and that descriptors generally survive exec. [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html), [setresuid(2)](https://man7.org/linux/man-pages/man2/setresuid.2.html). A bo process able to invoke the fixed client can still request stop, so A does not establish a human-intent or complete bo-compromise guarantee. Choose A only if its stronger distinct-peer/key-custody property is required and the operational and privilege-drop canaries succeed; do not assume setuid mode or installation alone proves it.

Option C can potentially provide a narrowly mediated stop-only broker, but generic systemd unit-management or transient-unit authority is broader than a fixed target/verb. Polkit and system bus add dependencies to an emergency path; polkit's documentation notes that an SSH session may have no authentication agent. [systemd manager API](https://www.freedesktop.org/software/systemd/man/257/org.freedesktop.systemd1.html), [polkit application guidance](https://www.freedesktop.org/software/polkit/docs/latest/polkit-apps.html). It is not preferable without proving exact action, unit and property confinement, noninteractive usability and behavior when those services are unavailable.

A deployed result still requires actual UID/key/socket checks and an allowed bo request against the real private frontend and root backend. Stop must operate without the main control plane, journal, database, gateway or Docker client; a deliberately unavailable fixture endpoint is a simulation, not a daemon-crash proof. Unknown accepted launches stay frozen and closed through helper failure and restart. On the same target, verify closed, frozen, killed, observed empty and engine reconciliation separately. Neither a successful frontend call nor an empty cgroup sample proves delayed daemon activity has ended. [Kernel cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).

**Hard positions:** do not silently weaken `BrakePolicy`; do not allow a stolen approval bearer to substitute for the brake key; do not grant model-facing access to the key, bo account or Docker socket; and do not equate separate same-account bearer files with MFA or protection against compromise of bo. The review supports building the bounded policy and test path only. Production brake acceptance, broader task admission, daemon/host recovery and human promotion remain separate gates.
