# Brake caller amendment: security response, round 1

I **maintain** conditional support for the moderator's B: a separately named `OperatorBrakePolicy` that accepts the configured bo peer and an independently provisioned stop bearer, while the existing strict `BrakePolicy`, its consumers and tests stay unchanged. This is an explicit change in caller identity semantics. Shared transport may implement both policies, but must not represent B as an instance or proof of the strict policy. The current frontend draft cannot be deployed by omitting bo from the ordinary-UID exclusion list. [Moderator](moderator-brake-round1.md), [evidence ledger](brake-evidence-ledger.md).

I **concede** the operations reviewer's original point: A provides a stronger distinct-caller-UID contract and could keep the bearer unreadable to ordinary bo processes. If that property is separately required, B is insufficient and A or another genuinely distinct broker must be tested. I agree with operations' revised assessment that the setuid client does not prove human presence or prevent full bo compromise: a process able to invoke the fixed client can request a stop, and bo's existing Docker authority is root-equivalent. A also introduces privileged transition, group, inherited-descriptor and environment obligations. [Operations position](position-brake-operations.md), [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html), [Docker security guidance](https://docs.docker.com/engine/install/linux-postinstall/).

I agree with recovery that separate bearer files alone do not prove R9. The narrower claim is that an agent possessing only the ordinary approval bearer cannot obtain the independent brake credential or use the stop path. That depends on actual role isolation and custody: no model execution as bo; no worker, control, evaluator, journal or gateway access to bo's credential, bo identity, Docker socket, or root backend. A bo-process compromise remains outside O4's stated scope. Neither peer credentials nor two same-account secrets establish MFA or human presence. [Recovery position](position-brake-recovery.md), [R9](../../consensus-plan.md#r9--kill-switch--kill--pgid--an-out-of-band-brake-key), [O4](../2026-10-26-operator-auth/consensus-plan.md#post-debate-user-selection).

I maintain the moderator's actual deployment gates: the authorized bo peer and stop key must work end to end; approval bearer alone, wrong key, wrong peer, duplicate credentials and unknown targets must fail without target disclosure or root mutation. Verify actual filesystem permissions and distinct UIDs, not merely policy configuration; also verify frontend restart and lost acknowledgement without replaying uncertain effects. Root accepts only UID 2003 and fixed stop/status with an opaque canonical generation target from its protected catalogue. Its result separates permanent closure, same-inode kernel freeze and emptiness from engine reconciliation. The recent native held-launch-lock canary demonstrates one independent kernel-stop case, but no frontend, delayed Docker completion, host-loss or production acceptance. A disposable unavailable endpoint is not proof of a shared-daemon or host crash. [Kernel cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).

There is **no remaining material disagreement on the conditional policy choice** among the three reviewers. The critical open issue is evidentiary: actual key custody, approved human invocation, frontend/backend integration and recovery must pass before deployment. If an agent can assume bo or read its bearer, or the old distinct-caller property is declared mandatory, this consensus does not apply and admission must remain closed. No adoption, provisioning or promotion follows from this response alone.
