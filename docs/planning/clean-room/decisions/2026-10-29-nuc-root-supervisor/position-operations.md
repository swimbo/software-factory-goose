# Operations position: root-owned supervisor with durable closure

## Recommendation

Choose a narrow root-owned supervisor running as a systemd service **outside Docker and outside each worker subtree**, with per-task root-owned catalog, durable admission closure and fixed operations. Retain network-none, distinct-UID Docker workloads where their bounded behavior is proved; use a separate non-root private control service and separate evaluator and worker identities. This is a decision to implement a small guarded boundary, not a production acceptance claim. The [evidence ledger](evidence-ledger.md) now grades the first-instruction canary adequate for that limited implementation; it does not prove all races or restart classes.

The actual owned-slice positive control wrote its marker. In the frozen control, the exact accepted Docker scope became populated and frozen under the same parent, but did not write the first-operation marker before removal; the pending start returned an error after recursive kill. A prior unknown was reconciled while frozen using the exact identified Docker version's remove/start behavior. This is useful host evidence, not proof that every runtime, daemon restart or cgroup transition is safe ([canary record](../../verification/2026-10-29-nuc-late-start-freeze-canary.md)). Keep every unresolved task closed and frozen until the exact operation is reconciled; never treat a timed-out Docker client or an empty snapshot as cancellation of an accepted daemon request.

## Operational contract

1. A root-owned immutable catalog binds an opaque task/generation to fixed image digest, command, role UIDs, allowed mounts, cgroup identity and durable journal scope. No request from a worker, model, or ordinary API chooses a PID, path, executable, unit, mount or Docker option. Validate root-owned ancestors, no symlinks/unsafe ACLs, size and content digests, and the actual object used. Keep worker and evaluator credentials, host network and Docker socket outside the untrusted container.
2. Before any effect, fsync the one-use launch intent and its task binding. Create stopped, persist exact ID and labels, seal the fixed workload family, then start only under that family. Persist permanent admission closure before stop work begins. An acknowledgement lost before the durable receipt is **unknown**, not a failed no-op. On restart, read closure and intents before admitting requests; inconsistent or missing records stay closed.
3. Stop must work when the control plane, Restate, gateway and Docker client are unavailable. The independent authority resolves only a catalog-owned target, closes admission, freezes the exact root-owned task subtree, verifies the same inode and `frozen 1`, recursively kills, and observes the subtree. Report closed, frozen, killed, empty and unresolved distinctly; do not manufacture a verified stop while daemon work remains in flight. [Kernel cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) documents asynchronous freeze, recursive kill and the ability of authorized processes to move across frozen groups. An ancestor freeze protects descendants only while the verified ancestor persists and cannot be bypassed by unauthorized migration.
4. Use systemd to supervise the root process and provision narrow socket activation; configure process and cgroup lifecycle explicitly. [systemd.kill 257](https://www.freedesktop.org/software/systemd/man/257/systemd.kill.html) describes unit cgroup termination, not automatic cleanup of a separately managed Docker subtree. [systemd resource controls](https://www.freedesktop.org/software/systemd/man/257/systemd.resource-control.html) provide `Slice=` and delegation, but avoid delegating a migration-capable subtree to the worker. Check the documented automatic-thaw behavior whenever a unit job or Docker operation could touch the frozen ancestry.

## Identity and integration

The existing `bo` UID 1000 can be the local human operator if it remains distinct from newly provisioned non-root control, worker and evaluator UIDs, uses the existing access path, and presents a durable one-use authorization bound to the exact action and evidence. No new SSH key or MFA claim is needed. This does **not** establish independence from a full `bo` compromise: its existing Docker-group access is root-equivalent. The emergency brake needs separately protected credential custody; two bearer files readable by `bo` do not prove independence from theft of that account. The brake must remain independently available even when approval or normal runtime state is unavailable.

The existing [brake transport](../../../../../clean-room/crates/watchdog/src/brake_authority.rs) offers peer-authenticated bounded requests and a `StopAuthority` seam, but its [policy](../../../../../clean-room/crates/watchdog/src/lib.rs#L74) demands a distinct non-root service UID. Adapt it as an unprivileged frontend to a tightly scoped root backend; do not weaken its checks or pretend it already installs a root supervisor. The [broker](../../../../../clean-room/crates/watchdog/src/broker.rs#L1), [atomic peer gate](../../../../../clean-room/crates/control-plane/src/atomic_peer_gate.rs#L1) and [Batch fixture](../../../../../clean-room/tests/fixtures/docker_batch_guardian.py) provide seams and scoped evidence, not a deployed authority.

Connect the private runtime under its verified root-owned configuration and isolated service network namespace. Authenticated UDS intake must reach the catalog-bound intake/qualification journal; that journal publishes only its exact approved task to the same queue/claim authority. Workers in network-none namespaces must not reach Restate or invoke scheduler methods directly. Bind the actual pinned Goose launcher, provider gate and isolated wall to that claim and receipt. Production budget and credential boundaries remain mandatory outside the user's uncapped experimental run; do not create a second independent ledger. Exact-revision promotion still consumes separately authorized human approval.

## Remaining release tests and hard stances

Before opening production admission, demonstrate helper SIGKILL and restart before/after intent, accepted start, closure, freeze and cleanup; duplicate and forged IDs; rejected cgroup migration; lost responses; and independently authenticated stop while the Docker-facing control path is unavailable. After every run verify exact owned root identity and retained closure; exercise a positive marker and a deliberate thaw negative control. The scoped canary is not host-power-loss, systemd-manager-loss or real Docker-daemon restart evidence. Those claims require a separately controlled equivalent or maintenance window, never a shared-service restart by inference.

I reject Docker-only cleanup as the final independent brake, reset of an ambiguous admission to make progress, unreviewed broad root APIs, and claims that a test UID proves human login. Root and existing Docker-group administrators remain trusted; their compromise is not contained by this design. Preserve all existing Hermes, Bifrost and Stapled resources and the original inert Created container. Production activation and INT-LOOP acceptance follow only after the connected boundary and its remaining gates pass.
