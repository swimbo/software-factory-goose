# Security position: guarded root supervisor

## Recommendation and confidence

Select a narrowly scoped **root-owned supervisor outside Docker and outside all workload cgroups**, supervised by systemd, with root-owned task records and a dedicated task subtree. The same authority must mediate fixed launch and stop operations; a separate unprivileged brake frontend may expose the operator protocol, but the root backend independently validates its identity and target. Do not authorize arbitrary Docker arguments, PIDs, paths, shell commands, units or mounts from any peer. The implemented system must remain fail-closed until its deployed integration and recovery controls pass.

The shared [evidence ledger](evidence-ledger.md) is now adequate for guarded implementation, not production acceptance. The owned canary observed a real late Docker child scope populated and frozen beneath a frozen parent, with no marker during sampling; its pending start later returned an error, and exact-ID non-force removal and same-inode empty observation supported scoped reconciliation. [NUC canary evidence](../../verification/2026-10-29-nuc-late-start-freeze-canary.md) That is stronger than a configuration-only claim and narrower than proof for every Docker start, process migration, daemon failure, or host restart. Systemd can automatically thaw a unit before a job, so a retained freeze must be observed and protected, not inferred from a previous command. [systemctl freeze](https://www.freedesktop.org/software/systemd/man/255/systemctl.html#freeze%20PATTERN%E2%80%A6)

## Fixed authority and protected state

A provisioned catalogue maps opaque task and generation IDs to a fixed approved image digest, executable, mounts, environment, constraints and protected cgroup identity. Pin installed executable and catalogue provenance; open trusted files and cgroup directories with no-follow semantics and validate owner, mode, device, inode and expected filesystem before use. A pathname, transient systemd unit name, PID or container label alone is not authority. Record exact full Docker IDs, labels and daemon identity only after validation; retain pre-create intent when an ID is unknown. Do not place the helper, its journal or its operator channel inside the worker subtree.

Before any external effect, durably record the exact one-use launch admission and task/attempt identity; fsync the record and its containing directory. Close admission durably before stopping. Record states such as admitted, create unknown, started/unknown, closed, frozen, killed and verified empty separately; a timeout or local client death cannot become a success or reset a token. On helper restart, reject all admission until each known generation is reconstructed from protected records and ambiguous effects remain closed. Missing, malformed, truncated, replaced, stale or conflicting state is a quarantine, not an empty catalogue. Preserve previous unknown fences and the old Created/PID 0 Docker object; do not claim their effects are reconciled by a new generation. The observed lost-create case demonstrates why. [NUC create-unknown record](../../verification/2026-10-28-writer-synthetic-create-unknown.md)

## Stop protocol and pending operations

The independent stop path must work without the control plane, journal service or gateway. Authenticate a local peer before parsing an authorized, bounded request and check a separately protected stop credential; resolve the opaque target against the root catalogue. Socket owner, mode and parent directories are part of that boundary. The human approval channel for promotion or budget changes is action-bound and distinct from emergency stop; it does not imply MFA. A wrong UID, stolen approval token, wrong stop credential, unrelated task or replay must cause no target mutation.

The stop sequence closes admission, validates the exact protected subtree, requests freeze and observes completion on the same inode, then kills the recursive subtree and observes `populated 0`. Keep the freeze and closed state when an accepted Docker create/start, manager action or teardown is ambiguous. A one-time `cgroup.kill` or empty sample cannot prevent a late start. Worker containers must be nonroot, network-none, capability-restricted and have no Docker socket, writable host cgroup hierarchy, privileged helper, operator credential or control-plane authority. Verify that a real worker cannot migrate outside the protected subtree; `setsid` alone does not establish escape from a cgroup. [Kernel cgroup-v2 controls](https://docs.kernel.org/admin-guide/cgroup-v2.html#interface-files)

For the pinned daemon, the audited Moby code serializes a same-container start and removal under its state mutex and rejects removal-in-progress/dead starts. A successful non-force removal of the validated full ID, exact-ID absence and an independently frozen/empty same inode support reconciliation of that specific ID under the unchanged daemon and trusted-administrator assumptions. [Source audit and limits](../../verification/2026-10-29-nuc-late-start-freeze-canary.md#exact-id-removal-source-audit) A failed, timed-out or conflicted removal remains unknown. Do not generalize this inference to arbitrary external processes, containerd cleanup errors, another daemon version, host loss or every delayed launch. Do not thaw or delete an unknown subtree just to restore availability.

## Principal and recovery limits

Existing `bo` can be the distinct local human operator relative to newly separated service, worker and evaluator UIDs, using the existing login; no new SSH key is required merely to test that interpretation. But `bo` currently has Docker-group root-equivalent authority. A malicious `bo` process can bypass this supervisor, and two secrets readable by that same account are not independent against its compromise. [Recovery research](research-recovery.md#existing-bo-account-as-operator) Full host/root/Docker administrators are explicitly trusted; an independently held brake credential and custody model remains necessary for the stronger compromised-operator requirement. Do not describe synthetic UID 1002 Docker clients as a provisioned human brake.

A systemd-supervised root helper offers a smaller lifecycle and recovery surface than a bespoke unsupervised root daemon. Docker-only cleanup cannot satisfy a stop path during Docker unavailability; current `live_restore=false` also makes a Docker-contained guardian dependent on the daemon. [Operations research](research-operations.md#options-and-recommendation) Systemd itself is still a dependency. Restart-before-ack, helper crash loop, manager loss, daemon restart and host reboot require distinct proof; an endpoint outage simulation does not establish those cases.

## Required integration and discriminators

Before enabling authoritative admission, exercise disposable actual supervisor binaries and task-owned resources with: correctly authorized and forbidden peer calls; altered catalogue and inode; duplicate launch IDs; helper death before and after each intent/closure transition; an accepted start with withheld/lost acknowledgment; worker `setsid` descendants and denied cgroup migration; and independent stop while a disposable Docker endpoint is unavailable. Include a first-observable-operation positive marker and a negative case that demonstrates the test would detect escape or thaw. Observe the exact subtree and preserve unknown records. Never restart shared Docker or systemd to approximate these tests.

Connect the existing private intake/queue/claim and lease authority to the **same** server-owned task/generation record and one-use root launch, rather than maintaining a second independent identity or budget ledger. Bind the actual Goose worker, gateway dispatch, result receipts and isolated wall to that record; test crash and lost-response handoffs through the real registered adapters. Final promotion remains human action-bound against the evaluated exact revision. No synthetic success, fixture ledger or this architecture decision completes those integrations.

**Hard stances:** no generic root command service; no worker access to Docker or writable cgroup control; no success on an unresolved start or lost receipt; no automatic reset or thaw of unknown state; no claim of compromised-operator independence from two same-account secrets; and no production activation until the cross-boundary and recovery gates pass. The per-task monetary waiver does not alter production budget rules.
