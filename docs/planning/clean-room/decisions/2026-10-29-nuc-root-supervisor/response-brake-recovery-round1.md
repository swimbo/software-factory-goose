# Recovery response: brake caller amendment

**I maintain** the recommendation for the explicitly named operator-caller policy B, with bo's actual kernel UID, a separately provisioned stop bearer, a distinct nonroot brake service UID, and a root backend that permits only that service UID to request fixed stop/status for a registered opaque target. This meets the selected threat model only when the worker and other service UIDs cannot access the stop key or become bo. The ordinary operator bearer alone must never work. The old `BrakePolicy` must retain its distinct ordinary-caller invariant and must not be invoked with an incomplete exclusion list.

**I acknowledge operations' concession** from its initial preference for a setuid distinct-caller client: the extra setuid-root code adds privileged parsing, descriptor and credential-transition risks but does not prove human presence or defend against full compromise of bo, which already has Docker-root authority. [Operations research](research-brake-operations.md), [Linux execve](https://man7.org/linux/man-pages/man2/execve.2.html). **I agree with security** that B is a different, explicitly reviewed policy rather than a successful use of the stricter constructor; only actual cross-UID key-custody and denial tests can establish the R9 stolen-token boundary. [Security research](research-security-brake.md).

The independent frontend and stop-only backend must remain usable without ordinary control, journal, database, gateway or Docker client availability. Disconnecting an owned fixture endpoint is a simulation; it is not proof of shared Docker, systemd manager or host failure. Unknown Docker operations must remain closed/frozen, and kernel containment must not be misreported as engine reconciliation. No MFA, same-UID compromise resistance or human-presence claim follows from two credentials accessible to bo. [R9 and O4](../../consensus-plan.md).

**Remaining material disagreement: none.** This resolves the policy design only after moderation. It does not establish installed credential isolation, actual human invocation, root backend availability, production admission, promotion, or completion of the implementation. The tests specified by the moderator remain required before activation.
