# Brake caller amendment: recovery and usability research

**Recommendation: B, as an explicit new production policy only after a reviewed amendment.** Preserve the existing `BrakePolicy` and its ordinary-UID exclusion unchanged. Under the selected O4 scope, the existing human `bo` UID may invoke a separately authenticated brake endpoint with an independently provisioned stop bearer; control, worker, evaluator, journal and the brake frontend remain distinct nonroot UIDs. This is adequate for a testable least-privilege design, not evidence of deployed authorization or a claim that a compromised `bo` account cannot stop workloads.

## Controlling requirements

- [R9](../../consensus-plan.md#r9--kill-switch--kill--pgid--an-out-of-band-brake-key) requires a separately supervised brake and independent credential, not dependent on the ordinary operator token: an agent possessing only an exfiltrated operator token must not access the brake key. It also requires the stop path to remain usable without the main service and database. The user subsequently selected a separate local operator and action-bound channel, expressly without MFA or same-UID-compromise resistance. [O4 selection](../2026-10-26-operator-auth/consensus-plan.md#post-debate-user-selection).
- The current [`BrakePolicy::new`](../../../../../clean-room/crates/watchdog/src/lib.rs#L83) deliberately rejects any overlap among brake UID, service UID and *all supplied ordinary UIDs*. Passing bo as brake UID while omitting the actual bo operator from that set misrepresents and defeats that contract. A separate named policy with an explicit changed principal rule can be reviewed; silently weakening this one cannot.
- On the current host, bo's Docker group membership grants root-equivalent administrative power; a malicious bo process can bypass local controls. The user-specified scope does not claim resistance to that. [Docker security guidance](https://docs.docker.com/engine/install/linux-postinstall/). No new SSH key, sudo entry or group membership is needed to use an existing bo login.

## Comparison

| Option | Recovery/usability and security | Assessment |
| --- | --- | --- |
| **A: setuid-root fixed client drops to distinct caller** | Keeps existing strict `BrakePolicy` and can keep a root-held brake key unreadable by bo's ordinary processes. A root-owned setuid executable becomes a new privileged attack surface, can be invoked by bo processes without proving human presence, and has operational failure modes under `nosuid`, `no_new_privs`, tracing, UID/GID changes and inherited descriptors. | Plausible if distinct peer identity or bo-unreadable key is a separately required goal. Not currently established to be least privilege for selected O4; no installation without separate implementation review and actual tests. |
| **B: new explicit bo-caller policy + separate random key** | Removes a new setuid-root executable and reuses the actual human login, while retaining an independent nonroot brake service and distinct root stop authority. New policy changes the strict caller exclusion and must say so; kernel peer bo + stop-only bearer must be checked before bounded fixed requests. | Preferred for the stated threat model only if the agent cannot read the brake key or invoke as bo. Two bo-readable secrets are not independent against bo compromise, are not MFA, and must not be described as such. Existing strict policy stays unchanged. |
| **C: narrowly scoped polkit/systemd broker** | Can delegate an exact stop operation to a separate principal if its policy, unit/method/arguments and caller are tightly constrained. | Adds system bus, polkit authority and potentially an authentication agent to emergency response; policy may accidentally authorize broad unit actions. SSH sessions may lack an agent. Exact noninteractive usability, verb confinement and unavailability behavior are not proved, so do not adopt merely because a unit can be started. |

Setuid facts: Linux [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) documents that `nosuid`, `no_new_privs` or tracing can suppress setuid transitions and that file descriptors generally survive exec. [`setresuid(2)`](https://man7.org/linux/man-pages/man2/setresuid.2.html) describes real/effective/saved UID changes; group IDs and supplementary groups require their own handling. A reviewed A client must validate real caller identity and executable/key/socket provenance, close inherited FDs, clear supplementary groups, permanently set and verify all UID/GIDs, clear capabilities, prevent dump/trace exposure, use a fixed target and stop/status protocol, and fail closed on every failure. A UID transition alone is not a security proof. [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html).

Polkit's own [application guidance](https://www.freedesktop.org/software/polkit/docs/latest/polkit-apps.html) states an SSH-launched application may lack an authentication agent; its [architecture](https://www.freedesktop.org/software/polkit/docs/latest/polkit.8) depends on the system message bus and authority. Do not infer a no-prompt stop from a generic systemd capability or reuse general `StartTransientUnit` authority.

## Acceptance and unresolved questions

1. The new B policy must explicitly name bo as permitted caller while still requiring a distinct frontend service UID and excluding every generator, evaluator, control and journal UID. Validate the actual kernel peer on the accepted Unix socket and separately compare a distinct root-issued stop key; do not derive it from an approval token. Secure socket parent and key file permissions, preserve an out-of-band issuance/recovery path, and never log the key.
2. Actual distinct-UID tests must reject a correct approval bearer without the stop key; the stop key from any excluded worker/control/evaluator/journal UID; a forged peer header; wrong or duplicate stop credentials; arbitrary PID/path/operation and cross-task target; and unauthorized attempts at the root backend. Prove an allowed `bo` caller can request only fixed stop/status for an owned task. Test role isolation and inherited FD/environment paths; a key stored where a worker can read it fails R9 even if the router rejects its first request.
3. Test an independent frontend/root backend when the control plane, journal, database, gateway and a fixture Docker endpoint are unavailable. The stop side must not call Docker to freeze/kill/observe the already owned cgroup, and an uncertain pending engine operation stays closed/frozen. A simulated disconnected endpoint does not prove an actual shared-daemon crash or host restart.
4. A single stolen operator token is not the same as complete `bo` account or root compromise. With B, an attacker running as bo can access its bo-readable brake key, so do not claim independent custody against that stronger attack. An attacker with only the ordinary token and no bo peer or stop key must fail; a compromised worker must have neither access to the key nor ability to assume bo. If the intended agent threat includes arbitrary execution as bo, B does **not** meet the R9 key-separation premise and the boundary must be redesigned or the assumption revisited.
5. No option is a production pass until deployed socket ownership, role identity, immutable task binding, stop behavior, lost-ack/restart recovery and unavailability controls are verified end to end. If a separate reviewed policy is not accepted, retain the current stricter policy and implement/test A or a comparably narrow alternate caller instead; do not game the constructor's exclusion list.
