# Consensus: explicit operator brake policy

CONSENSUS_REACHED on guarded implementation. Three primary-source research briefs, three independent positions, moderator round one and three explicit round-one responses agree on B. Operations concedes its initial preference for a setuid caller. Security and recovery retain A as a fallback if a distinct caller identity becomes a required boundary. Root moderated because no specialized moderator tool is available. No material design disagreement remains under the controlling O4 scope.

Introduce `OperatorBrakePolicy` and a specifically named production router. Existing `BrakePolicy`, constructor exclusions, consumers and tests retain their stronger distinct-ordinary-operator contract. Do not construct the new policy by silently omitting an ordinary UID from the strict constructor. The production policy admits only the configured kernel human peer and independently provisioned stop bearer; control, worker, evaluator, journal and frontend identities remain distinct. Both stop and status require the same checks. The backend authenticates only frontend UID2003 and resolves opaque generation IDs through root-owned catalogues.

Bo UID1000 is the existing human operator relative to the five service accounts. Existing Docker-root authority remains trusted. This decision does not claim human presence, MFA or resistance to a full bo account compromise. It addresses stolen approval-bearer substitution and untrusted service/model access. No untrusted model process may run as bo, read either operator key or reach root launch authority. Avoiding a new setuid executable reduces privilege surface within that scoped threat model; it does not prove any custody property by itself.

Acceptance remains blocked until actual host-peer and credential tests pass: correct human peer plus independent key; wrong peer/key and approval bearer denied; duplicate/malformed credentials and unknown target denied; isolated service UIDs cannot read the key or bypass the frontend. Verify live fixed root stop, socket activation/restart/lost replies, held launcher lock, unavailable disposable control/journal/gateway/Docker endpoints and retained permanent closure. Keep kernel stop, historical observation and engine reconciliation separate; Pending never means verified teardown. Existing native V2 canary is bounded evidence, not a frontend or full outage pass.

Implementation is authorized by the user's existing scoped NUC host-administration and implementation instruction. This decision authorizes no human promotion or general production acceptance. Actual dependencies, daemon/host failure recovery, integration loop and remaining verification gates remain open.
