## research-security.md

# Linux containment and security research

**Evidence grade: sufficient to design a disposable discriminating canary; insufficient to declare the proposed freeze barrier or production containment proven.** A root-owned, independently supervised narrow helper paired with a dedicated task subtree is the strongest candidate on this host, conditional on proving late-start containment and recovery. This is not a recommendation to install or activate it before the remaining debate and tests.

## Primary evidence and current host observations

1. The [kernel cgroup-v2 interface](https://docs.kernel.org/admin-guide/cgroup-v2.html#interface-files) says `cgroup.freeze=1` recursively freezes a cgroup and descendants, with asynchronous completion reported by `cgroup.events`. An ancestor freeze keeps a descendant frozen. The same documentation explicitly allows processes to enter or leave a frozen cgroup and allows cgroup tree changes. Therefore freeze is not an immutable membership boundary; it works only if worker escape and privileged migration are separately prevented.
2. The [kernel cgroup-v2 interface](https://docs.kernel.org/admin-guide/cgroup-v2.html#interface-files) specifies that `cgroup.kill=1` recursively sends SIGKILL to the subtree, handling concurrent fork and protecting the kill operation against migrations. `cgroup.events` reports recursive `populated`, but `populated 0` alone is a momentary observation: it does not rule out an accepted or later launch. Keep admission closed and any pending start unresolved while the freeze fence is maintained.
3. [systemctl's freezer documentation](https://www.freedesktop.org/software/systemd/man/255/systemctl.html#freeze%20PATTERN%E2%80%A6) says a unit is automatically thawed before systemd executes a job against it. Docker here uses the systemd cgroup driver. Whether a Docker start or scope job can cause the relevant target or an ancestor to thaw, bypass, or run before containment is installed is **unproven**. Neither a successful `freeze` command nor Docker parent configuration suffices as a late-start proof.
4. Read-only NUC inspection for this research: kernel `6.12.107+deb13-amd64`, systemd `257.13`, Docker server `29.8.0` commit `3ce5872`, systemd cgroup driver/v2, AppArmor and default seccomp, daemon PID 2145, `live_restore=false`, Docker service `KillMode=process` and `Restart=always`. The task worker subtree's `cgroup.freeze` and `cgroup.procs` are root:root 0644, `cgroup.kill` is root:root 0200, `cgroup.events` is root:root 0444; the cgroup2 mount includes `nsdelegate`. At inspection its events were `populated 0`, `frozen 0`. This is a read-only snapshot, not a reservation or readiness verdict.
5. The retained original exact Docker object remains `/sf-owner-224a71d2db764249aa6cade3c1b39c80`, Created/PID 0 at inspection. Its conditional inert-name fence and fsynced reconciliation are recorded in [the create-unknown evidence](../../verification/2026-10-28-writer-synthetic-create-unknown.md). Do not start, rename, remove, prune, or use that object as a test resource; a daemon/name/state change invalidates its prior fence.
6. Current [kernel namespace/delegation guidance](https://docs.kernel.org/admin-guide/cgroup-v2.html#delegation) explicitly requires controlled access to cgroup files for migration and warns against exposing an external hierarchy inside a container. A cgroup namespace by itself is a view, not a security guarantee. `setsid` escapes a process group, not its cgroup; test the actual workload's inability to migrate out or alter the subtree rather than assuming it from a UID or configuration.
7. The [systemd service documentation](https://www.freedesktop.org/software/systemd/man/257/systemd.service.html) provides service lifecycle and restart machinery, not an automatic proof that a separate Docker-managed child is contained or that a journal survives a host power loss. A trusted root service can be placed outside Docker and the workload subtree; it must rebuild a fail-closed view from protected durable records before admitting a new request.
8. [Docker's live-restore documentation](https://docs.docker.com/engine/daemon/live-restore/) describes daemon termination and the configurable survival behavior. On this host it is disabled. An independently braking helper must not itself depend on a Docker container or a newly created Docker operator client to survive/use a daemon outage. No shared daemon restart, reload or configuration change is justified by these facts.

A root helper needs a narrow peer-authenticated Unix protocol with separate service, worker, evaluator and operator principals; opaque task/generation IDs, exact authorized operations, protected catalogue and append/fsync-before-effect admission/closure records. A peer-provided path, PID, command, environment, mount or target cgroup must never determine a privileged operation. A separate local operator and action-bound approvals were selected; no MFA claim or silently provisioned SSH key follows. The daemon, root helper, manager and protected catalogue are in the trusted base. A worker must not have host cgroup writes, Docker socket or an operator credential. Root-issued file descriptors must still be checked for fixed filesystem, inode, task identity and lifetime; a replaced, removed or recreated cgroup is not the original target.

## Discriminating owned canary before adopting freeze

Use **new, uniquely named disposable** task-owned resources, never either existing task slice or retained original. A root-supervised fixture outside the test subtree records and fsyncs the unique catalogue, exact Docker intent and a deliberately paused start reservation. A worker container runs nonroot, network-none, cap-dropped and without a daemon socket; a task-private marker is its only test output. Prove a no-freeze positive control actually creates that marker. Then close admission and freeze the exact protected parent, confirm the same inode and `cgroup.events` reports completion, and release a previously accepted or deliberately delayed Docker start. Attempt to create a descendant and start a fixed payload while retaining the parent freeze. Observe through an independent supervisor whether systemd or Docker thaws/recreates/migrates the scope and whether **any payload instruction/marker runs**. Inspect the task-owned cgroup hierarchy and frozen state, not merely Docker's status or client return. Treat unavailable evidence or a start timeout as unknown and keep the subtree closed and frozen.

Within that unique subtree, a positive `setsid`/fork descendant canary must first prove it would survive a process-group-only stop. The helper then uses the fixed subtree's kernel kill operation and checks same-inode recursive empty state, with negative controls for worker attempts to move into an outside cgroup or write control files. Kill/restart the task-owned supervisor before and after closure/fsync and while start is pending; after restart the authority must refuse admission and must never claim cleanup while a late operation remains unresolved. Test an unavailable Docker endpoint without stopping the shared daemon: disable access only inside the disposable client namespace or use a dedicated fake socket, then demonstrate the independent root helper's operator stop path and retain unknown engine outcome. This simulates an unavailable client path, not an actual dockerd crash.

The test coordinator must retain exact-ID/name/intents on any ambiguous create, never signal unowned processes, and remove only proven-owned resources after independent confirmation. Keep the test cgroup frozen until all pending operations are resolved, and do not automatically thaw or delete it on a failed canary. Include owner-loss, forbidden peer, stale inode/ID, wrong operator and replay controls. Retain output and the actual event sequence; configuration, an empty observation before releasing start, or a dead CLI is not enough.

## Remaining proof and scope

A passing canary shows only the tested host/kernel/daemon conditions. Independent manager failure, root service crash before record sync, actual daemon and host restart, reboot ordering, power-loss persistence, daemon accepted RPC after client loss, rollback without affecting unrelated resources, and protected operator account provisioning remain separate. ## research-operations.md

# Operations research: NUC root-owned supervisor

Research date: 2026-10-29. Read-only host check: Linux `6.12.107+deb13-amd64`, systemd `257.13-1~deb13u1`, Docker `29.8.0` server commit `3ce5872`, unified `cgroup2fs`; Docker, Hermes gateway and dashboard were active. This inventory does not prove installation authority, persistence after restart, or the security of shared Docker. No service or host configuration was changed.

## Material facts

1. In cgroup v2, writing `1` to `cgroup.freeze` freezes the group and descendants asynchronously; completion is reported by `cgroup.events` `frozen 1`. A process moved into a frozen group stops, but an authorized mover can move it out; a frozen empty cgroup can be deleted and children created. `cgroup.kill` kills the subtree and handles concurrent fork/migration, but a kill at one instant does not prevent a later accepted start. Keep the ancestor identity and freeze in place, prohibit untrusted migration, and prove the specific Docker/systemd late-start path. [Linux cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html).
2. systemd 257 documents `Slice=` hierarchy, `Delegate=` and unit resource limits; delegation changes who can manage a subtree and is not automatically safe for an adversarial worker. A unit stop with `KillMode=control-group` acts on its own cgroup; a separately managed Docker child under another slice cannot be assumed to be covered by the supervisor service's stop. [systemd.resource-control 257](https://www.freedesktop.org/software/systemd/man/257/systemd.resource-control.html), [systemd.kill 257](https://www.freedesktop.org/software/systemd/man/257/systemd.kill.html).
3. Docker `create` creates a stopped container and supports `--cgroup-parent`; `start` is a separate operation. A client timeout is not a daemon cancellation receipt. The project has already observed a timed-out create appear later, so preserve its intent and treat unresolved daemon work as unknown. [Docker create](https://docs.docker.com/reference/cli/docker/container/create/), [observed created original](../../verification/2026-10-28-writer-synthetic-create-unknown.md).
4. Linux Unix-domain `SO_PEERCRED` yields kernel peer credentials for a connected peer; filesystem socket permissions and trusted ancestor directories remain separate. UID proves the local process identity in its namespace, not human presence or approval of a specific action. [unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html). The existing [brake authority](../../../../../clean-room/crates/watchdog/src/brake_authority.rs) authenticates bounded requests and delegates opaque targets; its [policy](../../../../../clean-room/crates/watchdog/src/lib.rs#L74) explicitly requires a **non-root** service UID, so it cannot simply be run as root unchanged.
5. [Broker](../../../../../clean-room/crates/watchdog/src/broker.rs#L1) is an unregistered trusted-launch seam, not a production daemon; its `Registry` closes in-process family admission but does not itself persist a root-owned cross-restart authority. The [Batch fixture](../../../../../clean-room/tests/fixtures/docker_batch_guardian.py#L142) durably records intents and closes admission but is Python/test-scoped and relies on Docker for its existing cleanup. The [control-plane entrypoint](../../../../../clean-room/crates/control-plane/src/main.rs#L110) registers only the workflow and budget diagnostic objects; the peer gate is explicitly [experimental](../../../../../clean-room/crates/control-plane/src/atomic_peer_gate.rs#L1). None constitutes the requested installed supervisor.

## Options and recommendation

**Recommend a systemd-managed, minimal root supervisor outside Docker, with root-owned persistent catalog and cgroup ownership, plus a separate unprivileged authenticated brake frontend.** Use fixed systemd service/socket identities and task slices; resolve opaque, one-use IDs against server-owned immutable specs. Never accept a model-chosen executable, PID, cgroup path, mounts or Docker arguments. A protected root helper must independently verify the frontend's peer identity and scope; the current non-root `BrakePolicy` cannot provide that root authority by configuration alone. Keep operator access separate and do not silently provision an SSH key. The user-selected operator/action approval contract is distinct from emergency stop.

A custom root process without systemd could implement the same kernel controls, but loses the existing manager lifecycle and requires its own independent restart mechanism. Docker-only fixture continuation retains the daemon and owner process as a common dependency for cleanup, so it cannot establish the requested independent brake. Transient systemd units are useful for workload subdivision, but neither unit creation nor Docker's cgroup-parent flag alone proves complete containment or closure after a timed-out start.

## Discriminating proof gaps

- Before accepting a late-start guarantee, use a **new owned** task slice and controlled blocked Docker create/start. Persist closure, request freeze, verify the same cgroup inode and `frozen 1`, release the blocked RPC, and test whether the proposed workload can perform a preselected external observable action before freeze applies. Test start-before-freeze, freeze-before-start, child creation and namespace/cgroup movement. A zero `populated` snapshot alone is not a fence against a future accepted start. Retain frozen/closed state on uncertainty.
- Kill and restart only the new supervisor unit during pending create, pending start, and completed stop; verify persistent intent/closure causes startup refusal and that an independent root-owned stop endpoint can still freeze/kill/observe without Docker, Restate, gateway or the workload owner. Test daemon-unavailable through an owned endpoint fault or suspended fixture path; do not restart shared Docker. Full Docker daemon crash, systemd manager loss and host reboot recovery remain unproved without their own controlled maintenance experiment.
- Test peer UID spoofing and same-UID threat assumptions, root-owned catalog/path replacement and symlinks, duplicate action IDs, interrupted fsync and conflicting scope. Socket authentication must precede request body processing and include bounded connection/body limits. An installed root socket's absence of a public listener does not prove catalog provenance.
- Preserve the existing exact-name created container and previous unknowns. A same-daemon name fence is conditional, not a reboot or daemon-replacement proof. Do not clear it to demonstrate an unrelated successful run.

## Minimal integration sequence

1. Inventory proposed factory-prefixed UID/GIDs, root directories, socket, slice and unit names; reject collisions and partial state. Pin installed binary and trusted manifest; make rollback remove only resources proved created by this installation. The user has authorized scoped administration, not a new operator login key or changes to shared deployments.
2. Implement the supervisor as one small owned service with immutable catalog, durable one-way admission closure, explicit unknown state and inode-bound subtree operations. Adapt the existing non-root brake frontend to call a narrow root-owned backend; do not weaken `BrakePolicy`'s identity exclusions or register generic Docker authority. Run the late-start and restart discriminators above before opening the admission path.
3. Connect the already implemented private intake/worker adapter and journal authority to the **same** task/lease identity and the supervisor's single-use launch, with task/attempt/result provenance. Reuse the worker adapter and `StopAuthority` seams; do not create parallel budget or claim authorities. Existing Restate feature bindings must be deliberately migrated and privately provisioned before use; verify lost acknowledgement and retained-state recovery.
4. Connect the pinned Goose/gateway and isolated wall via that launch and receipt path, then the existing exact-revision, action-bound promotion path. Keep first promotion pending the separate human action. A successful one-task live fixture and scoped uncapped budget override do not close production authority, normal budget rules, or the full INT-LOOP.

The evidence supports a bounded implementation and decisive canaries, not a claim of complete supervisor, host-loss recovery, or production readiness.

# Recovery and operator-usability research

**Reviewer:** contrarian recovery/usability. **Evidence grade: insufficient for production late-start closure or independent human brake.** Candidate is worth a narrowly owned canary; neither a systemd unit nor a durable marker alone establishes the full property. No accounts, services, files on the NUC or shared resources were changed for this research.

## Verified evidence

- Read-only `ssh -o BatchMode=yes -o ConnectTimeout=8 hermes-control` on 2026-10-29 reported Linux `6.12.107+deb13-amd64`, systemd `257.13-1~deb13u1`, Docker server `29.8.0`, cgroup v2/systemd driver and `live_restore=false`. Current login UID is 1000, its groups include `docker`, and `sudo -n true` fails. This reports the selected host and moment only. Docker itself documents that membership in its group provides root-level privileges: [Docker Linux post-installation](https://docs.docker.com/engine/install/linux-postinstall/). Thus a root helper cannot protect against a malicious actor with Docker-group authority; the security claim must explicitly trust and exclude that actor and ensure worker, evaluator, and operator do not receive it.
- Linux cgroup v2 documents asynchronous freeze completion (`cgroup.events`), inherited ancestor freeze, creation of new child cgroups while frozen, migration into/out of a frozen subtree, and fatal-signal killing of frozen processes. `cgroup.kill` handles concurrent forks and protects against migrations during the kill; this is not a perpetual admission barrier to a later daemon RPC. `populated 0` describes the currently observed subtree, not future starts. [Linux kernel cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).
- `systemctl freeze` documents automatic thaw immediately before a job on that unit, including stop: [systemctl documentation](https://www.freedesktop.org/software/systemd/man/251/systemctl.html). A stop sequence must not assume a systemd freeze survives a subsequent systemd job on the same unit. Verify parent/child job behavior on the deployed version, and use an explicitly observed ancestor freeze only if tested; do not assume systemd cannot alter its lifecycle.
- Linux `fsync` of a state file does not itself persist the containing directory entry; the containing directory also requires fsync: [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html). An acknowledged fsync ordering test is not evidence that the filesystem, storage hardware, abrupt power loss, incomplete writes, or corrupted state all recover correctly.
- Systemd socket unit defaults are permissive: `SocketMode=0666`, `DirectoryMode=0755`; explicit restrictive ownership/mode plus kernel peer identity and an independent stop credential are needed. Socket permissions alone are not human authentication. [systemd.socket](https://www.freedesktop.org/software/systemd/man/255/systemd.socket.html). The chosen separate local operator account is not a human login method: no approved SSH key or human-presence mechanism is established.
- Docker's `--restart=no` is its documented default; restart policies and external service managers may otherwise conflict. [Docker restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/). Docker documents daemon and live-restore behavior separately, but no shared-daemon failure test is authorized in this scope: [Docker live restore](https://docs.docker.com/engine/daemon/live-restore/).
- Current NUC evidence covers a task-owned user-systemd guardian, manifest and pre-create intent, including a crash after create and non-force cleanup; it explicitly leaves Docker/manager failure, ambiguous start, root identity, restart and power loss open. See [guardian recovery](../../verification/2026-10-28-nuc-systemd-docker-recovery.md) and [precommit](../../verification/2026-10-28-nuc-systemd-precommit-intent.md).

## Proof gaps and minimum design constraints

1. **Late RPC execution:** `frozen=1` followed by `populated=0` does not prove future lack of execution. Runtime creation may happen outside the frozen task subtree before attachment; if so, even a later freeze does not disprove earlier code execution. A lost client response or local client termination is not a daemon cancellation. Every unresolved create/start remains durably closed and quarantined; do not recycle an ID, remove the ancestor, thaw, infer absence from Docker timeout, or send arbitrary PID signals.
2. **Crash and power:** helper death at every boundary—before and after intent fsync, request acceptance, freeze, signal, and response—must cause restart to refuse new admissions until the exact task identity is reconciled. A separately supervised stop-only component can improve availability but is itself a dependency and requires a demonstrated failure path. Test helper crash independently from systemd manager crash, daemon restart and host reboot; the latter three are not proved here.
3. **Operator usability:** a distinct peer UID and secret can demonstrate process identity and possession. Before claiming an operable human brake, prove how the authorized person starts a client as that UID without Docker group, general sudo, unapproved credentials or a new silently installed SSH key. A synthetic cross-UID test is not human login. State whether lack of that channel requires fail-closed deployment and record any separate human decision; no MFA claim.
4. **Root authority:** constrain helper operations to exact preapproved opaque task IDs, root-owned immutable catalog and task cgroup identities; reject arbitrary units, paths, executables, PIDs and Docker options. Validate no-symlink ownership and content provenance and pin the object actually used, not just a path checked earlier. Avoid handing worker any daemon socket, host network, writable catalog or broad cgroup delegation. Treat privileged Docker users and root as trusted administrative principals; the design cannot prevent them overriding containment.
5. **Stop truth:** report closed / frozen / killed / observed empty / unresolved separately. A successful local request and an empty cgroup are not proof that pending daemon work can never run. Do not silently reset quarantine or advertise a bounded SLA when the helper, kernel or manager is unresponsive.

## Minimal actual canary before selecting the boundary

Use unique task-owned root-controlled units, socket paths, cgroup subtree, files and labelled network-none throwaway containers, with no existing shared daemon restart, reboot, key or service changes. Inventory exact disposable resources and cleanup/retain conditions in advance. Only touch the named owned objects; keep ambiguous cases frozen and quarantined.

1. Establish an end-to-end positive control: a fixed workload's first guest instruction writes a nonce marker to a narrowly scoped, fixture-only host-observed file; without a freeze the marker must appear. Use a distinct account fixture with an authenticated stop-only socket; assert wrong peer, wrong secret, arbitrary path/PID/launch and replay attempts fail. A root-run UID switch tests kernel identity, not a human login.
2. Freeze the exact persistent task ancestor and wait until `cgroup.events` reports frozen. Send the actual fixed Docker create/start through a fixture-owned controllable proxy which forwards the start, then deliberately withholds/drops its response. Independently record whether the daemon accepted the request, exact container ID, hierarchy/inode, `frozen`/`populated`, and marker from an observer outside the subtree. Confirm neither the guest marker nor any earlier fixture-defined side effect can occur while the closure is in force; bounded timeout or no observable acceptance is **inconclusive**, not a pass. Include negative controls for a thaw and, separately, a systemd job on the relevant unit to detect unexpected automatic thaw. Verify worker cannot migrate itself outside the subtree.
3. In separate runs kill only the owned helper before and after durable closure, start acceptance, freeze and kill. Restart that owned helper, then release a held acknowledgement and exercise stop from the separate UID while the launch-side Docker client/proxy is unavailable. Check no new task admission, no duplicate launch, retained closure, no marker and exact subtree identity, with unrelated canary workloads unchanged. Test fatal kill and absence of all contained descendants; observe rather than assume full cleanup. A dropped response is not proof of rollback.
4. Record exact binaries/versions, IDs and timestamps, outcomes, bounded timeout, observed `cgroup.events`, negative-control markers, and any remaining owned container/cgroup. If manager, daemon or host failure is simulated by disconnecting a fixture proxy, label it simulation. Do not change shared Docker/systemd to test these failures; real manager/daemon reboot or power-loss evidence requires an isolated equivalent or separately authorized maintenance window. If no verifiable human access path exists, record the brake as not human-usable and leave the gate open.

## Existing `bo` account as operator

The user-selected O4 wording requires a **separate local operator account**, not a particular account name or a newly issued login key. The already existing `bo` UID 1000 can serve as that local operator identity if the deployed service, generator and evaluator all run as different UIDs, socket admission checks actual kernel credentials, the authorized human uses the existing login, and action-bound approvals have authoritative task/evidence binding, expiry and durable one-use consumption. A host `sfctl` client can use restricted root-owned Unix sockets and read separately issued operator/brake credentials from a private `bo`-owned location without invoking Docker or sudo. Do not change existing SSH keys, Docker membership or sudo to make this work; no MFA or human-presence claim follows. Existing fixture UID 1002 does not select an operator identity.

This is conditional on an explicit trust boundary. Current `bo` belongs to Docker and is therefore a trusted root-equivalent host administrator ([Docker security warning](https://docs.docker.com/engine/install/linux-postinstall/)); a malicious process running as `bo` can use that authority to bypass or alter the helper. Two different secrets readable by `bo` prevent accidental cross-use when the server validates them, but a `bo` compromise can read and exercise both. The prior [operator-auth decision](../2026-10-26-operator-auth.md) asks how the brake stays independent of compromised operator credentials. Separate bo-readable files alone do **not** prove independence against compromise of the account or endpoint; independent availability from the control plane/Docker is a different property. A distinct separately protected brake custody/channel would be needed to prove that stronger property, or the gap must remain explicit. No new human SSH key is necessary merely to test this existing-account interpretation.


## native-option.md

# Native launcher fallback: research only

**Status: unselected, unimplemented, unverified on the NUC.** If the accepted Docker-start race cannot be contained, a small native launcher with `clone3(CLONE_INTO_CGROUP)` deserves a discriminating canary. It is a different execution and sandbox architecture, not a patch that automatically preserves Docker's isolation or the verified Goose image.

## Evidence and proposed topology

- Linux `clone3` has supported `CLONE_INTO_CGROUP` since 5.7: an open cgroup-v2 directory FD selects the child's cgroup at creation; documentation expressly describes creating a child in a frozen cgroup. See [clone(2)](https://man7.org/linux/man-pages/man2/clone.2.html). The observed NUC Linux 6.12/cgroup v2 is newer, but kernel version alone does not prove the syscall, specific cgroup permissions, seccomp allowance or configured controllers work. A denial, unsupported syscall or unavailable exact cgroup must fail closed, without a fork-then-migrate fallback.
- **Inference:** direct birth inside the frozen task group removes the specific gap where a privileged Docker daemon might execute a process before moving it into a target cgroup. Unlike Docker, there is no separately accepted create/start RPC that can outlive the local launcher. This does not eliminate races with an already accepted native clone, cgroup destruction/recreation, helper death, a privileged actor moving a process, or a flawed recovery protocol.
- Systemd [delegation documentation](https://systemd.io/CGROUP_DELEGATION/) assigns `Delegate=yes` to service or scope units, **not slices**. It documents that systemd owns the delegated unit itself while a service owns sub-cgroups, and systemd may create `.control` for unit control processes. `DelegateSubgroup=` is available starting with systemd 254 to place the main service process below the delegated root; observed NUC is systemd 257. Use manager-provided `ControlGroup`, never guess a path from the unit name; test what actually occurs. The systemd `Delegate=` service would host the supervisor in a dedicated control subgroup and place task ancestors in **sibling** subtrees it owns. The independent brake must not freeze the supervisor, its control subgroup, or the whole service. A service-level stop/restart can kill the helper and its descendants and may change freezer/lifecycle state; keeping a parent alive across such a job is **not established**.
- A worker subtree must remain exclusively writable by a trusted supervisor; no workload cgroup delegation or privileged external actor may migrate it out or thaw it. Linux documents that processes can be moved out of a frozen cgroup and run; freezing and one-time `cgroup.kill` do not permanently close future admission. [Kernel cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html). Bind a held directory FD plus inode/mount identity to the immutable task and check that the parent is the owned delegated tree. After helper loss, old FDs and pidfds are not persistent. Recreate or reattach only after explicit identity/recovery proof; no numeric PID kill or silent reset.

## Process isolation is still the hard part

Direct cgroup placement proves neither hostile workload isolation nor launch identity. A native root supervisor would have to create required namespaces and mounts, set cwd, clear inherited environment and unapproved file descriptors, clear supplementary groups, drop real/effective/saved UID and GID, remove permitted/effective/inheritable/ambient/bounding capabilities, apply no-new-privileges, and install an independently reviewed syscall/security policy before any untrusted executable runs. All failures are terminal and closed. UID changes do not alone prove capability removal: Linux documents multiple capability sets and exec transformations in [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html); [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html) documents no-new-privileges effects. Test the actual sequence and child-observed IDs/caps, not a parent-side intended configuration.

A mount namespace and `RootDirectory=` can present a fixed filesystem; [systemd.exec](https://www.freedesktop.org/software/systemd/man/256/systemd.exec.html) states `RootDirectory=` uses pivot_root or chroot. **Chroot itself is not a sandbox** and does not close already-open descriptors or change cwd: [chroot(2)](https://man7.org/linux/man-pages/man2/chroot.2.html). The exact rootfs, mount propagation, proc/sys/dev, device nodes, external file descriptors, writable paths, seccomp, privilege escalation and escape negatives need independent review. A separate network namespace requires testing; systemd documents that `PrivateNetwork=` leaves filesystem-addressed Unix sockets accessible if their paths are available ([systemd.exec](https://www.freedesktop.org/software/systemd/man/258/systemd.exec.html)), so it does not replace socket/mount exclusion.

An OCI/Docker image is not a safely usable native root directory by itself. OCI layers encode whiteouts, links, modes, ownership, extended attributes and device entries, and applying layers is not a plain tar extraction: [OCI image layer specification](https://github.com/opencontainers/image-spec/blob/main/layer.md). Image configuration has executable and environment metadata in addition to the filesystem: [OCI image configuration](https://github.com/opencontainers/image-spec/blob/main/config.md). Safely materializing, pinning, authenticating, and immutably mounting a rootfs—with traversal, symlink, hardlink, setuid, file capability and device-entry defenses—needs an established reviewed tool and separate tests. Reading a trusted prebuilt immutable rootfs may reduce work but its provenance, libraries, entrypoint and equivalence to the tested Goose image remain unproved. Do not extract untrusted layers as host root or improvise OCI parsing in the privileged helper.

# Recovery and usability position

## Recommendation

Proceed with a **guarded implementation** of the smallest root-owned supervisor managed by systemd and running outside Docker and all workload subtrees. It should have a narrow launch authority and a separately authenticated stop-only path, immutable server-owned task records, one-way admission closure, and a persistent task cgroup identity. The source, socket directories, catalogue and journal must be root controlled. A nonroot frontend may serve the operator, but the root backend must independently authenticate that frontend and the requested fixed operation. Never expose an arbitrary Docker command, PID, path, mount, cgroup or systemd unit.

Evidence is **adequate to implement and test** this candidate and **insufficient to accept it for production**. The actual NUC canary observed a Docker child scope populated and frozen below the frozen parent, with no first-operation marker during sampling. It also reconciled an exact ID through non-force removal while the same parent inode was frozen and empty. That result is valuable, and it does not prove absence of transient thaw, delayed acknowledgement, supervisor loss, escaped descendants or host restart. [Evidence ledger](evidence-ledger.md), [actual canary and Moby source audit](../../verification/2026-10-29-nuc-late-start-freeze-canary.md).

## Why this design and not the alternatives

Docker-only supervision cannot furnish a brake that remains available when Docker is unreachable. A custom unsupervised root process retains the Docker late-start problem and introduces its own restart machinery. Systemd supervision makes a narrow host helper plausible, but it is itself a dependency: the helper can be dead, wedged or restarted, and a systemd job can automatically thaw the affected unit. Freeze must be verified on the same protected subtree identity at the time it matters, not treated as a durable property of a remembered unit name. [Operations research](research-operations.md), [systemctl](https://www.freedesktop.org/software/systemd/man/255/systemctl.html#freeze%20PATTERN%E2%80%A6).

The native `clone3(CLONE_INTO_CGROUP)` fallback is worth a canary if the Docker barrier fails: it can create a process directly inside the target frozen cgroup and avoids an independently queued Docker start. It also requires rebuilding and proving namespace, filesystem, credential, syscall and image isolation. It is not a drop-in replacement for the pinned Goose container or an established production alternative. [Native option](native-option.md), [clone(2)](https://man7.org/linux/man-pages/man2/clone.2.html).

## Recovery and stop behavior

Persist a task/attempt/generation-bound intent before create; persist its exact full Docker ID and immutable catalogue binding before permitting start; persist admission closure before stopping. Sync both file and containing directory. These are ordering requirements, not proof of disk power-loss durability. [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html). On restart, malformed, missing, conflicting or partially written records mean quarantine; the helper must not admit work based on an empty in-memory map. Preserve original unknown fences.

The stop operation has distinct results: **closed**, **freeze requested**, **frozen**, **kill issued**, **observed empty**, and **unresolved**. Authenticate and resolve the task before acting; freeze the exact recorded subtree, wait for `frozen 1`, use recursive kill, then observe the same subtree identity and `populated 0`. Never signal caller-selected numeric PIDs. A frozen empty subtree is a current observation, not proof that an already accepted daemon start cannot arrive later. Keep admission closed and the ancestor frozen when the outcome is ambiguous. The kernel describes `cgroup.kill` handling concurrent forks and migration during the kill, not an everlasting launch barrier. [Kernel cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).

For this pinned daemon, same-container Moby start/removal serialization plus a successful non-force full-ID removal, exact-ID absence and same-inode frozen/empty observations support **conditional reconciliation of that exact fixture object**. Failure, timeout, mismatched daemon identity, or unresolved lower-level cleanup remains unknown. This source reasoning is neither a cancellation primitive nor proof for a changed daemon, its crash, host loss, or arbitrary already-running effects. The protected state must encode those limits, and a restarted helper must never thaw an unknown generation for availability.

## The operator and brake

The existing `bo` account may serve as the selected separate human operator **relative to newly provisioned distinct service, worker, evaluator and journal UIDs**. Existing SSH access can launch a host `sfctl`; ordinary approval and brake use should not require Docker, sudo, a new SSH key or a shared service restart. The root endpoint must check the actual peer UID, independently verify authorization, and bind approval to exact action, evidence, expiry and one-use consumption. No MFA or proof of human presence is claimed. [Operator decision](../2026-10-26-operator-auth.md).

There are two different independence claims. A distinct brake bearer must not be interchangeable with an operator approval bearer; its stop path must also remain functional when the control plane, database, gateway or Docker client endpoint is unavailable. Those are testable without changing bo's login. But two secrets readable by bo cannot resist compromise of the bo account, and bo's existing Docker-group membership is host-root-equivalent authority. [Docker documentation](https://docs.docker.com/engine/install/linux-postinstall/). Root and existing Docker administrators are therefore trusted. A separately held brake credential/custody path is required for the stronger compromised-account threat; until that is selected and proved, record it as an open security property rather than inventing a new human login key or claiming two bo-readable files solve it.

## Gates before admission

1. Review the separate identity install plan for collision, filesystem ownership, non-secret backup, ACL and partial-failure behavior. New accounts must be locked/nonlogin and distinct from bo; no existing account, login key, group or sudo policy changes. Installer tests are local only and do not prove a host installation. Do not treat fsync ordering as a host power-loss test.
2. Run actual owned-helper negative controls for peer spoofing, wrong credentials, cross-action replay, cgroup path/inode replacement, catalogue substitution and worker attempts to migrate or reach Docker. 3. Kill the owned helper before and after durable intent, accepted create/start, closure, freeze and kill; restart and check that admission remains refused, pending responses do not produce duplicate launches, and the exact task stays frozen/closed until verified reconciliation. Demonstrate separately authenticated stop with an unavailable fixture Docker endpoint; label this a simulation, not a dockerd crash. Include a live positive marker and a deliberately failing or thawed control so the detector is demonstrably capable of detecting escape.
4. Connect authoritative intake, claim, queue and lease to the *same* protected task identity, actual Goose and gateway dispatch, receipt and independent evaluator. Exercise lost responses and crash recovery across these boundaries. A task-local canary or the monetary test waiver does not establish the full INT-LOOP or production budget policy. Promotion remains a distinct human action bound to the evaluated revision.

**Non-negotiable:** no root generic-command endpoint; no automatic thaw or reset of an unknown launch; no success based on an empty sample alone; no claim of human-brake or account-compromise independence from a synthetic UID test; and no broad deployment acceptance from the finite canary.
