# Recovery response to moderator, round 1

## Operator and brake

**I concede** that stronger resistance to compromise of the entire `bo` account should not be introduced as a new O4 acceptance condition. The user-selected O4 expressly excludes same-UID compromise resistance and MFA claims; it requires a separate local operator account and action-bound channel. [O4 post-debate selection](../2026-10-26-operator-auth/consensus-plan.md). Existing `bo` UID 1000 qualifies relative to newly provisioned, genuinely distinct nonroot control, worker, evaluator, journal and brake-frontend UIDs. Its existing human login avoids a new SSH key, group or sudo change. Existing Docker-group authority makes `bo` and its processes trusted administrative principals capable of overriding the root helper; this scope is explicit, not a tested safety property against `bo` compromise. [Docker security warning](https://docs.docker.com/engine/install/linux-postinstall/).

**I maintain** that the tested brake must use a separately supervised nonroot frontend UID, an independently authenticated stop-only root backend, and a distinct stop bearer with separately controlled custody. A stolen ordinary approval bearer, missing the required actual peer identity and brake bearer, must not authorize stop or launch; an approval bearer must not substitute for a brake credential. Do not claim either resistance to total same-UID compromise or MFA merely because secrets differ. A stronger separately human-held custodian is a possible future security choice, not an unapproved MVP prerequisite. Independent availability during control-plane, journal, gateway and Docker-client unavailability remains required; an actual daemon crash is a different, unproved test.

## Frozen pending launch

**I maintain** the root helper, not the model, owns immutable task/generation records and one-use launch and stop operations. The current [NUC freeze canary](../../verification/2026-10-29-nuc-late-start-freeze-canary.md) supports a finite observed-child result and a source-audited, pinned-daemon exact-ID reconciliation. It does not prove an arbitrarily delayed RPC cannot execute, that all lower-level cleanup succeeded, or that systemd and daemon restart preserve the barrier. `frozen=1`, recursive `cgroup.kill`, and `populated=0` are separate observations; a later accepted start can change the outcome. Kernel documentation permits cgroup membership changes and treats kill as an operation on the current tree, not a permanent admission fence. [Linux cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).

A submitted start whose effect or completion is uncertain remains durably closed and frozen. Reconciliation must use the exact protected ID, pinned daemon identity, verified successful non-force removal and same-inode empty observation under the stated assumptions. A failed operation, stale identity, manager action or unavailable engine retains unknown status and is not permission to delete, thaw, retry under a fresh identity, or report complete. Systemd documents automatically thawing a unit before a job on that unit; a helper must not perform a stop/restart that implicitly defeats an unresolved ancestor freeze. [systemctl](https://www.freedesktop.org/software/systemd/man/255/systemctl.html#freeze%20PATTERN%E2%80%A6).

## Installation and gate scope

**I accept** creating only the reviewed, uniquely named nonlogin identities and root-owned directories after exact host PLAN, collision checks, verified capability scope and explicit source provenance, without enabling services or issuing credentials. The local installer tests are not host verification; metadata inventory excludes recorded other-device mountpoints and cannot assert universal absence of orphan owners. File and directory fsync orders are not power-loss proof. Account and path collisions or any partial action must leave records retained and prevent a blind rerun or global account-database restore.

**I maintain** a single exact greenfield recipe is a bounded first integration, not general decomposition or production readiness. The pre-admission gates must include actual helper crash/restart at intent and external-effect boundaries, lost or held start acknowledgement, deny-by-default peer and migration controls, exact cgroup identity, and a positive/negative observable marker. Stop via the distinct brake while a fixture Docker endpoint is unavailable is a useful simulation; neither that nor owned-service SIGKILL proves shared Docker failure, systemd manager failure, host reboot or power loss. No shared restart or human promotion is authorized by this debate.

**Remaining HIGH disagreement:** none with the moderator's proposed MVP scope. The unresolved production recovery and integration gates remain HIGH risks, not claims that the architecture already passed them. Implementation permission and identity-only provisioning do not confer production admission or completion of the full INT-LOOP.
