# Operations response — round 1

**Maintain** the root-owned, systemd-supervised narrow authority outside Docker, with fixed catalog operations, per-generation persistent closure and an independent stop path. The observed frozen-parent test is enough to implement and test that bounded candidate, not to declare all daemon or restart paths safe. The [canary evidence](../../verification/2026-10-29-nuc-late-start-freeze-canary.md) demonstrates a particular accepted start and first-operation control under the tested kernel and Docker version; it does not establish a universal late-start guarantee.

**Concede** the operator scope as clarified: existing `bo` UID 1000 can be the human operator, distinct from newly provisioned non-root control, worker, evaluator, journal and brake-frontend identities. The resolved O4 decision excludes a same-UID-compromise resistance and MFA claim; it does not require inventing a new human SSH key. Root and Docker-group administrators remain trusted, and existing `bo` groups and access remain unchanged. A separate stop bearer and dedicated brake frontend must not be interchangeable with an approval bearer. The server must require the appropriate kernel peer and action scope; possession of only a stolen approval bearer is insufficient for stop. This is a separation of authority and independent availability, not a claim that compromise of the entire `bo` account cannot reach bo-readable credentials.

**Maintain** a split between the non-root [brake frontend](../../../../../clean-room/crates/watchdog/src/brake_authority.rs) and narrowly scoped root stop backend. Its existing [policy](../../../../../clean-room/crates/watchdog/src/lib.rs#L74) requires distinct non-root identities and must not be silently weakened by moving that frontend to UID 0. The root backend accepts only immutable catalog targets and fixed operations. It must remain independently usable when the control plane, database, gateway and Docker-facing launch client are unavailable; a request timeout reports unknown, not verified stop.

**Concede** that same-inode `frozen 1`, recursive kill and `populated 0` can be reported as separate kernel observations while engine closure remains unresolved. They must not be collapsed into a claim that no accepted Docker operation can later run. [Kernel cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html) describes asynchronous freeze and permits authorized cgroup moves; [systemd kill semantics](https://www.freedesktop.org/software/systemd/man/257/systemd.kill.html) do not automatically govern a separate Docker-managed subtree. Retain permanent closure and freeze when intent, daemon identity or response is ambiguous. Do not thaw an unresolved generation through a manager job.

The new private runtime is a limited implementation path: protected catalog, separately authenticated intake and worker sockets, exact one-recipe handoff and private service namespace. It still needs actual root-owned catalog, namespace and socket canaries, private Restate registration and proof of exclusive journal genesis or migration. A single greenfield recipe is not a general spec-driven cascade or the complete INT-LOOP. Existing Bifrost configuration and the uncapped exception apply only to the named experiment.

No major design disagreement remains for implementing the candidate. **HIGH release gates remain:** actual owner-loss/restart at admission and closure boundaries; held/lost start and denied migration; stop with Docker/control/database/gateway unavailable; protected identity and catalog provisioning; and connected journal/worker/wall/approval behavior. A task-owned simulated outage or supervisor SIGKILL must be labeled as such; it does not prove a real shared daemon, manager, host reboot or power-loss recovery. Installation can prepare reviewed factory-owned resources without activation; production admission waits for these results and explicit remaining recovery gaps. No promotion approval follows from this debate.
