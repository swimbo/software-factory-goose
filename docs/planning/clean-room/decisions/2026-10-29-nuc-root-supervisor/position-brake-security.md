# Brake caller amendment: security position

I recommend **B, a separately named production policy admitting the existing bo operator UID and a separately issued stop bearer**, conditional on explicit adoption of that change and verification of credential isolation. Preserve the current `BrakePolicy` unchanged. Its documented ordinary-operator exclusion is a stronger caller-identity contract that B does not satisfy. Passing bo as the brake peer while omitting bo from the list of ordinary identities would conceal the change and is unacceptable.

This recommendation addresses the threat the user actually selected. O4 requires a separate local operator and action-bound approval, without an MFA or same-UID-compromise claim. R9 additionally requires an independent brake credential: an agent possessing an exfiltrated ordinary operator token must not obtain the stop key, and the brake must remain available when the main service and database are unavailable. These are distinct requirements, not permission to make both credentials available to an agent. [O4 decision](../2026-10-26-operator-auth/consensus-plan.md), [R9](../../consensus-plan.md#r9--kill-switch--kill--pgid--an-out-of-band-brake-key).

On the NUC, bo has Docker daemon access. Docker documents that this group grants root-level privileges. A process that fully controls bo can therefore access a bo-readable brake bearer and can bypass host controls; B makes no claim against that event. This does not excuse exposing the bearer to an agent, worker, evaluator, control service, journal or gateway. If the actual runtime runs untrusted agent code as bo, or can read or pass bo's key, B fails the R9 isolation premise and must not be deployed. [Docker post-install security](https://docs.docker.com/engine/install/linux-postinstall/), [recovery research](research-brake-recovery.md).

The new policy should name the allowed operator explicitly, use kernel Unix peer credentials, and require the separate stop bearer for both stop and status. The frontend remains UID 2003 and the root backend accepts only that peer. Requests carry only a canonical opaque generation identifier and a fixed operation; the root backend resolves immutable protected catalogue data, never caller-supplied PIDs, paths or commands. Backend responses distinguish durable closure, kernel frozen and empty observations, and unresolved engine reconciliation. The launch lock must not delay kernel stopping; a separate stop lock serializes stop operations. An independently issued operator-held bearer must never appear in arguments, environment, logs, prompts or worker mounts. `SO_PEERCRED` authenticates the peer process credentials, not the human or a second factor. [unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html).

The operations reviewer favors A because it preserves the existing caller exclusion. That is a real advantage, and I agree it is necessary if the deployment requires the original policy as an invariant rather than accepting a reviewed amendment. But a root-owned setuid client and a new UID add a privileged executable and lifecycle that the stated O4 scope does not itself require. The client cannot establish human presence: any process capable of invoking it as bo can request the operation. It must prove authentic real caller, fixed endpoint and protocol, safe inherited descriptors and environment, cleared supplementary groups and capabilities, permanent UID/GID transition, and failure under disabled transitions. Linux documents that `nosuid`, `no_new_privs`, and tracing can suppress set-ID transitions and that descriptors ordinarily survive exec. These are real implementation obligations, not reasons to silently reduce the old policy. [operations research](research-brake-operations.md), [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html), [setresuid(2)](https://man7.org/linux/man-pages/man2/setresuid.2.html).

C could provide a distinct caller via a narrowly fixed broker, but generic systemd transient-unit and property privileges are broader than a stop-only API. A polkit path also adds authority, system bus and possibly authentication-agent dependencies to emergency response. It needs actual method, unit, caller and headless availability proof before it can be preferred. [systemd manager API](https://www.freedesktop.org/software/systemd/man/257/org.freedesktop.systemd1.html), [polkit application guidance](https://www.freedesktop.org/software/polkit/docs/latest/polkit-apps.html).

Acceptance of B requires actual host-UID tests, not configuration alone: correct bo peer and stop bearer stop the exact registered generation; approval bearer alone and wrong peer or key fail; worker/control/evaluator/journal cannot read the secret or reach a successful stop even with the bearer; unknown targets and malformed or duplicate credentials fail without disclosing target state. Exercise a held launch lock and deliberately unavailable disposable Docker/control/database/gateway dependencies while an owned workload is stopped. Verify closure persists, the same protected cgroup is frozen and empty, and engine cleanup remains pending until independently reconciled. Test socket activation, backend restart and lost acknowledgements separately, and preserve unknown outcomes. A root backend canary or synthetic outage does not prove host failure recovery.

My hard stances are: keep the existing `BrakePolicy` and its tests intact; adopt no frontend using the misleading omitted-operator list; provision and test independent secret custody before activation; make the scope and bo-compromise limitation explicit; and select A or another narrow distinct-principal broker if the stronger ordinary-caller exclusion is mandatory. Neither B's two credentials nor A's UID transition is MFA. No production acceptance follows from this position paper.
