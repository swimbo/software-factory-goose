## Concrete blockers and assumptions

- Current source rejects A: `root-launch-host.py:195` and `nuc_relay_systemd.py:67-69` require UID2000/0700; `nuc_registry_launch_prepare.py:111` creates that ownership. Changing a directory alone breaks readiness/relay startup. Upgrade creation, helper validation and relay validation together, plus all pinned hashes/installed package manifests and affected tests. Keep the private **fence** UID2000/0700: it is a different directory and the launcher does not read it in `validate_inputs()`.
- UID2000 search permission is sufficient for current listener validation: `_open_path_dir()` uses O_PATH, `_no_acl_pinned_dir()` checks through `/proc/self/fd`, and `os.stat(..., dir_fd=...)` needs search. It need not list/open the parent for reading or connect to the root:2001/0660 socket; the listener is inherited. Prove this exact chain under the installed Linux filesystem, proc restrictions and service context. A future O_RDONLY directory open would fail and must fail visibly.
- Root ownership is insufficient if UID2000 can rename an ancestor, has an ACL write grant, or has CAP_DAC_OVERRIDE/CAP_FOWNER or equivalent administrative access. Validate every ancestor, access/default ACLs, exact groups and capability sets. Root:2000/0710 denies UID2001 host traversal only if it has no supplemental GID2000 or privilege. O_PATH opening the parent itself may succeed without traversal permission; denial controls must attempt lookup/connect of the child, not merely O_PATH open of the parent.
- UID2000 must be unable to create/unlink/rename a child or rename the parent. The root socket service remains trusted to recreate the socket; exclude stop/rebind during validation-to-Docker-create, or pin/recheck socket identity around creation. Root ownership closes the untrusted relay race; it does not prove identity across trusted manager lifecycle changes. Docker mount-path equality alone is not inode equality.
- B is not a fallback for callback substitution or ptrace-gated `/proc` checks. Ambient CAP_DAC_READ_SEARCH reaches ordinary helper/CLI descendants; NNP and environment clearing do not remove it. A privileged Docker launcher already belongs to the root/Docker administrator TCB, but avoiding this extra direct filesystem authority reduces mistakes and disclosure exposure. Neither design strengthens ordinary operator authority or removes independent braking.

## Safe upgrade and acceptance controls

Use a fresh unclaimed generation and a reviewed before/after plan; leave old closed generations and running shared units intact. Before replacement, capture exact root-owned versioned backups of each owned helper/package metadata file, including bytes, digest, mode, owner, ACL state and expected device/inode. Reject drift, symlinks, unexpected links and occupied backup/version paths. Stage verified replacements on the same filesystem, fsync files/directories, and publish atomically while admission is fenced. Multiple atomic renames are not a package transaction: prohibit launch while versions disagree; interruption leaves durable intent and requires reconciliation, never automatic retry or rollback of consumed authority. Preserve old artifacts for exact recovery and never restore old grant/deadline/closure state.

Readiness must execute the real fixed helper's non-effecting preflight in the **native** root context with E/P/I/B/A capability sets all empty, NNP=1, fixed argv/env and manager/process attestation. Retain bounded stderr so the next failure is attributable. Require exact helper/catalog/recipe/unit identities; all actual read/open checks; registry and ptrace-sensitive checks; no grant request, lock/deadline consumption, Docker creation or provider effect from readiness.

Use isolated scratch callback/fence fixtures for UID2000 positive O_PATH/stat/inherited-listener validation, UID2000 mutation denials, UID2001 child traversal/connect denial, and cap-empty root input checks. Verify UID2001 can use only its intended container-bound socket while host traversal remains denied. These are namespace/group-sensitive controls. Separately verify the independent ordinary-operator brake and direct-kernel deadline, full container IDs and pending-start/unknown-outcome closure before any separately authorized launch. Passing these checks does not prove host/daemon-loss recovery, human presence or MFA.
