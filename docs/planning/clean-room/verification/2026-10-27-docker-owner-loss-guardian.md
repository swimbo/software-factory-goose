# Disposable Docker controller-loss guardian

`clean-room/tests/fixtures/docker_owner_guardian.py` owns its freshly created, uniquely named and labelled container. It records the full engine ID, rechecks ID and random label before engine mutations, and closes admission before cleanup. Controller-pipe EOF, unexpected data or a bounded 12-second wait initiates cleanup: inspect, request Docker kill if still running, inspect stopped state, remove, then check that the ID is absent. A repeated cleanup only returns success after a verified removal receipt; a consumed or closed owner cannot start again. Timeout, failed kill, unknown status, identity mismatch and disappearance without an owned removal receipt remain errors. This is fixture-only code; it is not connected to production workers.

`python3 clean-room/tests/fixtures/test_docker_owner_guardian.py` passed three tests on the existing OrbStack engine and pinned local image. In the actual test, a parent owns both the external controller and the separate host guardian. The container's own inner guardian spawns a child which verifies its new session; a pipe handshake confirms the child remains active after the inner guardian is killed and reaped. The parent then kills and reaps its owned external controller. EOF reaches the surviving host guardian, which reports removal only after its Docker checks; a separate inspect sees the ID absent. The test's finalizer can clean only the exact test token and ID. The no-kill escaped-child control is recorded in [the prior spike](2026-10-27-docker-owned-escape-spike.md). Mock controls reject wrong label or full ID without issuing a kill or removal, and injected kill timeout leaves admission closed and the owner unresolved. The real guardian calls cleanup twice and rejects a subsequent start.

The first run removed its container but returned unresolved because OrbStack spells its missing-object error in lowercase; this was corrected and the tests rerun. No unrelated container, image, volume, network, VM, or service was changed. After tests a label-filtered inventory must be empty.

This improves behavior only when the outer host guardian and Docker engine remain responsive and the controller pipe is not leaked. Inner-guardian death and external-controller death are distinct from **host guardian death**, which remains unresolved. A kill timeout can take effect after the client returns, so the guardian deliberately does not infer a successful outcome. Engine stopped/removed status is not independent proof of cgroup emptiness or of hostile descendants unable to escape the container. The signal/inspect operations have separate steps, same-user engine access can tamper with or delete resources, watchdog launch and container creation can fail ambiguously, and daemon failure/restart, sealed executable identity, distinct authority, networking, and durable recovery remain unproved. The production containment gate remains closed.
