# Disposable Docker escaped-session spike

Read-only inventory found the existing OrbStack Docker context reports cgroup v2 with cgroupfs, an already-local Python image, and unrelated running and stopped containers. No unrelated container, image, network, volume, VM, account, or service was changed. The fixture uses the pinned local image ID with pull disabled; each test container has a random name and label, no network or host mounts, a read-only root, a nonroot UID, dropped capabilities, no-new-privileges, and bounded PIDs, memory and CPU. Cleanup checks the unique label and removes only the exact owned container. The benign workload has a finite lifetime even if the controller fails; ambiguous engine or identity errors are reported rather than targeting another object.

`python3 clean-room/tests/fixtures/docker_owned_escape_spike.py` passed. Its child verifies that it is its own session leader. A pipe handshake ensures the guardian is killed and reaped before the escaped child reports a heartbeat. In a no-kill positive control the child later emits its marker. In a separate lane, an external test controller invokes Docker kill after the heartbeat, Docker reports the container stopped, and no later marker appears in its logs during the observation window. Both fixture containers were removed; a label-filtered inventory showed no remaining matching container. The guardian failure did not automatically stop the child; cleanup was explicitly requested through the engine.

This tests a benign marker and the observed Docker API/log behavior, not independently observed cgroup emptiness. Missing logs could have causes other than termination, and Docker's [kill documentation](https://docs.docker.com/reference/cli/docker/container/kill/) explicitly describes signalling the container's main process rather than certifying all cgroup descendants. No host cgroup mount, PID-namespace observer, automatic independent brake, daemon failure test, hostile migration test, filesystem/network isolation proof, or production workload was used. Engine exit status is not an independent teardown proof; guardian/engine failure, reliable task identity and recovery remain open. Production stays fail-closed.
