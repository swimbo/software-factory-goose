# AppArmor target-only ptrace boundary

**A target-only AppArmor profile did not provide the required same-UID boundary.** On `hermes-control` (Linux 6.12.107 x86-64), a disposable, network-disabled container created a uniquely named AppArmor policy namespace. A target executed under an enforced fixture profile denying `tracedby`, with dumpability 1. An unconfined sibling with the same UID and zero effective capabilities successfully duplicated its open descriptor using `pidfd_getfd` and attached using `ptrace`. The same operations succeeded against an unconfined positive-control target. Root executable inspection also succeeded. The fixture namespace was unloaded and its exact absence verified after the run.

The container disabled its outer AppArmor and seccomp profiles to avoid masking the attack, used no-new-privileges, and had no network. The fixture profile is deliberately broad and is **not** a production policy. It does not exercise the actual gateway, its socket, real credentials, or a production route. The [upstream AppArmor task implementation](https://gitlab.com/apparmor/apparmor-kernel/-/blob/apparmor-next/security/apparmor/task.c) contains an unconfined-tracer exemption in its tracee permission check, consistent with the observed result; that upstream source is explanatory, not a verification of the installed kernel build.

This rules out treating a target-only AppArmor `tracedby` denial as proof against an unconfined same-UID process in this environment. Qualify a different post-exec custody boundary before allowing handed-socket cleanup or production launch. No paid calls, production policy changes, candidate activation, or benchmark attempts occurred; **0/120** attempts remain.
