# INT-LOOP routed inference integration contract

This is an implementation boundary and test plan, not permission to dispatch a live inference. The factory must submit `model: auto` to the existing Bifrost router and let that router select the model and reasoning according to task complexity. No manually selected substitute model is authorized by this contract.

COMPLEX selects `deepseek-v4-pro:0813`; MEDIUM and default select `deepseek-v4.1-flash:1017`. The key metadata shows no expiry and no key or linked-provider budget. The task credential file has been inspected for ownership and mode, but its value has not been matched to the database key. Do not print or copy the credential; the trusted host-side gate must read it into memory only after its file and scope are verified. No inference has been sent.

The published model-family prices do not prove the exact version-tag billing, route-wide surcharges, provider-added context, hard output and reasoning ceilings, or task-key accounting. The local Bifrost pricing table has no exact provider/model rows for the two selected tagged targets. The contract fails closed until these limits and their evidence are bound to the approved route policy, along with the full task and daily spend scope. A key-level cap, if later added, is defense in depth and does not replace a serialized factory reservation.

## Intended connected flow

1. A protected launcher creates one scoped worker and an immutable binding to the actual task, lease token, attempt, reviewed route policy and approved tool schema. Goose runs with no Bifrost or administrative credential and no direct route to Bifrost. A local HTTP shim may relay its protocol to a private Unix gate, but the shim and request body are untrusted.
2. The gate authenticates the kernel peer, enforces bounded request and response sizes and deadlines, accepts only the reviewed `auto` route and exact approved tool schema, and rejects ambiguous JSON, unsupported message forms and unauthorized fields. The current `goose_protocol` validator recognizes only the two canned fixture shapes; it is not a general conversation validator.
3. Trusted conversation state binds each new request to the prior provider response and trusted, masked tool result, rather than accepting worker-supplied tool history as authority. A persistent per-call identity must bind task, lease/attempt, sequence, exact request digest, route policy and price review. The identity is assigned or verified by the trusted authority, never freely selected by Goose.
4. In the same serialized task authority, calculate and reserve a conservative integer microUSD upper bound across every eligible primary and fallback outcome, including all billable input/output/reasoning and fixed or routing charges. Admission must check the current lease and revocation atomically with the single-use dispatch transition. There must be one non-resetting task ledger and the required aggregate daily limit; ambiguous acknowledgements or provider results remain charged and unknown, with no automatic redispatch.
5. Only after the authority returns a unique successful begin may the trusted gate forward once to the verified loopback relay, with the scoped virtual key supplied only in gate memory. It must bound and validate streaming responses, preserve tool-call correlation, and keep credential or provider response content out of error messages. Responses and tool results needed for the next turn must be recorded or otherwise attested by the same trusted boundary.

The existing `AtomicInferenceFixture` demonstrates only a fresh, unregistered namespace. The current `GatewayClient` reserves independently in `BudgetCounter`, accepts text-only non-streaming messages and does not support `auto` tool conversations. Wiring both as spending authorities would violate this design. Migration must inventory, reconcile and fence preexisting task and daily budget state before any production namespace changes; a new fixture ledger must not reset an existing allowance.

## Falsification gates before external inference

- Against disposable Restate and the actual Linux Goose/MCP candidate, exercise a synthetic routed upstream with two or more distinct possible served models and verify the reservation is at least the reviewed maximum for either. Unknown route, missing review, expired lease, wrong task/attempt, untrusted key scope, oversized/malformed stream or unavailable ledger must produce zero upstream requests.
- Race identical requests, drop reservation and begin acknowledgements, restart the gate and journal, and replay an exact request. Demonstrate one or zero provider dispatches and no reset/refund of ambiguous reservations. Different payloads or reused sequence IDs must conflict.
- Try forged provider responses, tool-call IDs and tool results; direct worker access to the gate's credential, Restate and provider must fail. Verify the independently authenticated brake and supervisor cleanup while a real Goose/MCP descendant is active.
- Verify key-file-to-virtual-key association, bounded validity and revocation, actual `auto` classifier behavior and all eligible provider billing/output contracts. Uncertainty in any required bound denies inference. The observed non-expiring, uncapped key is not itself proof of a safe task budget.
- Complete intake→qualification→queue ownership, distinct worker/evaluator boundaries, holdout 2-of-3 evaluation, action-bound human approval and exact-ref promotion before claiming INT-LOOP.
