# NUC systemd-driven Docker guardian recovery fixture

On the authorized NUC, `python3 clean-room/tests/fixtures/nuc_systemd_docker_recovery_spike.py` passed three times against the two existing task-owned slices. A random transient user service owns a disposable, labelled Docker container. The guardian creates the container without starting it, writes an exact full container ID, random token, label, worker-slice name and inode into a mode-0600 temporary manifest, fsyncs the file, atomically renames it, and fsyncs its containing private directory. A test-controlled gate independently checks the manifest and confirms the container is stopped before allowing start. This tests call ordering and the observed barrier; it does not establish power-loss durability.

The nonroot, capability-dropped, networkless, read-only worker uses no user host mounts or Docker socket. Its `setsid` child reports after its inner guardian is killed and reaped; it also reports denial when writing to its visible `cgroup.procs`. With that worker alive, the test asks systemd to SIGKILL the main process of the exact random fixture unit. The user manager starts the unit's independent `ExecStopPost` process, which reads the committed manifest with `O_NOFOLLOW`, checks its owner/mode and expected token, label, full ID, slice and inode, verifies the engine's label and configured slice, kills/removes only that container, and reports success only after reading `populated 0` on the same persistent worker-slice inode. A separate observer also checked container absence and that inode (`6882200`) and `populated 0`; the task-owned parent anchor kept the hierarchy observable. All three runs completed; the [final run log](2026-10-28-nuc-systemd-docker-recovery.log) records the result. The prior [slice control](2026-10-27-nuc-docker-slice-spike.md) supplies a no-kill delayed marker.

`python3 clean-room/tests/fixtures/test_nuc_systemd_manifest.py` passed three tests. Missing manifests and tampered token, label, full-ID format or slice were rejected; an injected engine ID/label mismatch also failed before the mock cleanup mutation sentinel. A local ordering control observed `PREPARE`, file fsync, directory fsync, then `LAUNCH`. `python3 clean-room/tests/fixtures/test_docker_owner_guardian.py` passed four tests, including an injected engine timeout that kept admission closed, retained unresolved ownership and permitted an explicitly retried cleanup. The existing NUC controller-loss and independent-coordinator guardian-loss fixture modes were rerun successfully after splitting container prepare from start.

The test-owned transient user service, anchor and worker containers were removed. The two previously documented system slices remain empty and active because a scoped stop required interactive authentication; no unrelated service, account, container or data was changed. A main-process SIGKILL is not systemd manager loss. If the guardian dies after container creation but before manifest commit, this fixture's `ExecStopPost` reports unresolved and a stopped container may need reconciliation by its protected task token; no automatic recovery for that crash window is claimed. A failed Docker call, user-manager or Docker-daemon loss, leaked authority, same-user tampering, prior migration out of the subtree, authenticated independent braking, restart recovery, power loss and hostile workload isolation remain open. Production remains fail-closed.
