# Disposable Restate restart verification — 2026-10-27

Built the loopback-only fixture with `cargo build -p control-plane --example restate_replay_fixture --features restate --locked --offline`, then ran `python3 tests/fixtures/restate_replay.py`. The locally installed `restate-server` reports 1.8.0; the installed launcher SHA-256 is `6093cfe1554d83f64de30ab21947e08380fc6c4c3f5f46ef6aea70e4781980bf`. The script resolves the bundled native binary via the existing Node installation and launches that binary directly; its SHA-256 is `ddb96e2ef0ce15628eaf4ce51361177aa9a08b568b823bf34e6271a122f806ec`. This identifies a tested environment, not a chosen or validated deployment version.

A disposable local PostgreSQL 17.9 instance with pgvector 0.8.2 ran with trust authentication, an isolated temporary data directory and a random loopback port. The fixture-only SDK example applied migrations there; this is a test environment, not a decision to change the planned PostgreSQL 16 deployment. A new Restate server ran with a fresh temporary base directory, random TCP ports bound to loopback, a unique node name and scrubbed environment. A separate loopback SDK endpoint registered budget, synthetic approval, claim and worker queue objects. The fixture reserved 200,000 microdollars, denied a 600,000 reservation, verified legacy/integer mode mixing was denied, ran ten concurrent 100,000-microdollar reservations with exactly seven accepted, rejected an altered approval candidate, issued and consumed an action-bound synthetic approval, stopped the server gracefully, restarted the same node and storage directory, reserved the remaining 550,000, denied another microdollar and rejected approval replay with HTTP 409. It additionally scheduled the same task twice, retrieved the identical fenced pull twice, completed it with a failed receipt, rejected a forged lease, and observed exactly three projected claim events. A second pull discarded the acknowledgement after the first response byte; querying the actual lease and retrying the same request recovered one attempt and an identical receipt. After the clean restart both pulls and the completion were idempotent. It then sent SIGKILL to that disposable native server process, restarted the same storage again, and confirmed the exhausted budget, consumed approval, pull receipt and completion still held. Result: **PASS**. Both processes terminated and the temporary directory was removed. No existing service, account, credential, production data or Bifrost endpoint was used.

This verifies acknowledged-state persistence across clean and SIGKILL restarts and a replay denial through actual Restate and pinned SDK for these bounded objects and their SQL projection. It does **not** prove recovery from a crash during an in-flight write or from client loss before the server begins a response, authenticated ingress, process isolation, in-flight queue/outbox recovery, the worker, actual promotion, or a full factory loop. The fixture approval handler is intentionally exposed only to its disposable loopback server and must never be registered in the deployed application.

The first version of the status probe sent JSON null; actual Restate returned HTTP 400 because the no-argument handler requires an empty body and no content type. A prior mock had accepted null; the worker adapter is being corrected to the observed contract. An early attempt that closed the connection before a response did not establish a completed invocation; it is not counted as replay proof.
