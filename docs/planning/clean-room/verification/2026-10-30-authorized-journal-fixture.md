# Disposable journal with root authorization

The synthetic direct-journal test passed on the NUC with the actual mandatory authorization reader. It used a fresh UID 1000 PostgreSQL data root and disposable Restate, and a systemd-managed UID/GID 2000 SDK with empty capabilities and no-new-privileges. The SDK was built locked/offline with `--no-default-features --features restate,root-authorization-canary`; it did not include `registry-sidecar`. Synthetic task and generation were `01ARZ3NDEKTSV4RRFFQ69G5FAM`.

The fixed runner first obtained a 403 for the unpublished request. A fixed synthetic root publisher then computed the exact request digest and created the actual root authorization. The runner observed successful exact delivery, three concurrent identical replays and lost-ack replay; changed payload returned 403. It also checked worker mutation denial, sanitized status, SQL reexport after deletion, persistent conflict quarantine, prior claim history, and identical replay and unchanged state digests after restarting the owned SDK and Restate. The logged result is `/tmp/sfactory-finalization-authorized-run.log`; the runner source SHA-256 was `e3c49654b5100d4e0453c69055fb401240680776904f049869c03492ee209c55`. The SDK binary was `a7f180b77005563106bf630a6b7d5708f358edb12b85ac27f1e61d7c4cd8cf72`; the separate synthetic publisher was `a4b538b4f9837d2b596b97aa667b0601890e79ffa3dcc33a70ae3cb5b712919c`.

The first start attempt failed its immediate process identity check before creating the unit record. The later correct UID2000 observation is consistent with a startup credential transition, but the initial status values were not retained. A separately reviewed recovery, bound to boot `98b86bb5-c04c-46f5-951d-22e497102f29`, PID `1162116` and invocation `1dda810d81a3403abc7bd36f1852e7b0`, verified that same active unit, recorded it, and ran the fixed PID1 UID 1000 PostgreSQL attestor before completing startup. The later restart used a new unit and immutable record, `Type=exec`, and a bounded identity poll. This recovery did not restart the original unit or assert that its earlier unrecorded database observation was retained.

Bridge receipts are retained: install `/tmp/sfactory-identity-admin-8d_7m98n`, initial failed start `/tmp/sfactory-identity-admin-dmli628y`, existing-unit recovery `/tmp/sfactory-identity-admin-99z2jj8b`, publication `/tmp/sfactory-identity-admin-1yllac5_`, restart `/tmp/sfactory-identity-admin-j6pd1exr`, and stop `/tmp/sfactory-identity-admin-ti3bjgeu`. The restarted and initial units were independently observed inactive with MainPID 0 and no job; the owned PostgreSQL root was absent after success. Root synthetic authorization and intent records remain retained. The final helper source SHA was `4246882e9c8e9bcd5592e98ec88538f02ed210b0a432ac0cf8c72fefe153c21f`; the startup recovery module was `a7773c895b82e545ad5bb3054a420c3996e8dd4e95db28fbcdcd8bfccb8dcada`.

This test does not prove deployed production admission, a real evidence producer, human approval, or finalization of the real failed generation. The synthetic SDK shares host loopback with trusted UID 1000: PID/socket/control-system attestation narrows accidental listener substitution but does not pin the later TCP connection. The lost-ack case closes after the first HTTP response byte, not at the exact commit boundary. The earlier variant fixture predates mandatory authorization and must not be used as proof for this gate.
