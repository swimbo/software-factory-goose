# Actual execution under a live group leader

The live-leader capture spike is not directly compatible with the current execution tool launcher. `execution::supervise` gives its shell a new process group. A disposable test launched the actual locally built `execution --tool-request` beneath a directly owned live group leader, using a fixed policy-admitted shell script with a two-second delayed marker. The unsignalled positive control produced the marker. In the stop case, the test observed the synthetic shell's process group differed from the leader's, confirmed the marker was absent, signaled and reaped the owned live leader group, and then observed the shell's delayed marker. The shell PID was used only for a group observation, never as signal authority. The finite test process was allowed to exit; no orphan PID was signaled.

`cargo build -p execution --locked --offline`, strict Clippy for the example, and `cargo run -p watchdog --example leader_execution_boundary --locked --offline` passed. Here `CONFIRMED GAP` is the expected negative-control result, not a successful containment result. The experiment ran twice; the final run also verified the distinct groups.

An integrated design must give a trusted external owner control of every admitted tool root or deliberately change group ownership while preserving sole wait, cancellation, full bounded output/masking, and fail-closed handling of leader death. Merely wrapping the current execution binary does not do that. The observation does not establish a remedy for `setsid` escape, cross-UID authority, guardian loss or independent teardown; production activation remains blocked. No existing service, account, VM, credential, or unrelated process was touched.

## Inherited-group fixture

A test-first experiment adds `execution` feature `fixture-inherited-group` and the explicit fixture-only `--fixture-inherited-tool-request` argument. It refuses unless its direct parent is the observed live process-group leader. In this mode the actual `ShellBoundary` and masking logic run, but the shell inherits the leader's group. Execution waits only for its own direct child and never claims to stop the group; the outer leader owns that responsibility. The old default `--tool-request` still creates a separate shell group and the same example reproduces its escape.

The example verifies masked split-secret stdout and stderr on normal completion, and uses a separate silent delayed-marker command as an exact no-stop positive control. For that command it observes the inherited shell's group matches the owned leader, stops and reaps the leader group, and observes the marker absent afterward. The same command in default separate-group mode produces its delayed marker after outer stop. The fixture's first inherited-mode run failed before the feature existed; after the change the focused comparison and all 49 execution tests passed, as did strict execution and example Clippy. A separate integration test verifies that a process which is its own group leader cannot invoke the fixture path without a direct leader parent.

This is not an authenticated launcher: same-UID processes can impersonate the parent or manipulate the group, the argument is reachable in a binary built with the fixture feature, and the private marker used for the test is not a protected result channel. A leader death, `setsid` escape, blocked spawn, SIGKILL races, output release after group termination, real Goose wiring, separate identities, and crash recovery remain unproved. The fixture's direct-child timeout/termination handling does not stop the complete group; only its test leader does. Do not deploy or use this feature as a security boundary. `run_goose` remains blocked.
