# NUC live fixture recovery helper

The synthetic Goose/relay/journal fixture reached its hold point with two sealed, distinct owned Docker roots in the existing worker slice. Killing the exact task-owned user unit's main process with SIGKILL caused systemd to invoke `nuc_live_batch_recovery.py` as ExecStopPost. That helper stopped the owned roots, verified the same worker cgroup was `populated 0`, and durably created its recovery receipt. The test used the fixed task-owned helper and the existing `nuc_goose_batch_systemd.py` fixture via `nuc_live_recovery_spike.py`. No provider or credential was used. The disposable unit and fixture roots were removed after verified recovery; the existing two task slices remain.

The fixture's Python tests also verify that missing manifests and failed cleanup cannot produce a recovery receipt. A separate NUC fixed-executor test passed after enabling 1 MiB by two-file Docker log rotation and ended with the worker slice empty. The read-only candidate option has local negative tests but has not been independently tested against an adversarial container on the NUC.

This proves a synthetic owner-loss path, not host manager or Docker daemon loss, authenticated independent brake integration for both roots, live provider execution, immutable candidate finalization, or production containment. The launch wrapper's `systemd-run` outcome can be ambiguous; its durable unit record and batch root must be retained and the exact unit inspected rather than launching again. The host user and Docker daemon remain trusted. Shared-slice runs require host-side serialization and a verified empty slice before the next run.
