# Two-root NUC Docker ownership fixture

`clean-room/tests/fixtures/docker_batch_guardian.py` is a fixture-only host authority for exactly two trusted roles, `goose` and `executor`. For each it fsyncs an intent before Docker create and commits a full-ID, unique-label and worker-slice-inode manifest while the container is stopped. `seal()` rechecks both distinct, labelled roots and the slice before either `start()` is allowed. A start is recorded before Docker is invoked, so an ambiguous start cannot be replayed as a fresh launch. Stop obtains the shared nonblocking file lock, commits admission closure, reconciles both roots and records each removal before reading `populated 0` from the same worker slice. A created root without a full-ID manifest can only be removed non-force after exact name, label, unique ID, slice and stopped-state checks; absent or ambiguous roots remain errors.

`python3 clean-room/tests/fixtures/test_docker_batch_guardian.py` passed three mocked tests: both roots must be sealed before start; stop removes both, is idempotent only with receipts and denies subsequent admission; an injected ambiguous create can be reconciled without signalling; and an unapproved create option is rejected before a Docker operation. These mocks do not establish host isolation or process death behavior.

The owned NUC test `python3 clean-room/tests/fixtures/nuc_docker_batch_spike.py` passed twice. It prepared and started two benign, networkless, nonroot, capability-dropped roots, killed and reaped the directly owned launcher, and used a second Batch instance to remove the exact roots and observe the existing task-owned worker slice `populated 0`; subsequent admission was denied. `python3 clean-room/tests/fixtures/nuc_docker_batch_spike.py manager` also passed: an exact random transient user unit owned both roots, systemd sent SIGKILL to its main, and its `ExecStopPost` invoked batch cleanup and wrote a recovery receipt before the independent observer checked `populated 0`. The anchor, two worker containers and transient user unit were removed; the same two previously documented empty root-owned slices were reused. No actual Goose, provider, standing service or existing workload was used in these tests. The harness retains its task-owned records and reports their path if cleanup is ambiguous.

This is a trusted bootstrap API, not an untrusted request interface or production containment service. Its fixed specs and mount paths must come from an independently protected trusted catalogue; it does not itself prove their provenance. It does not yet supply the bounded private input channel for a precreated executor, actual relay integration, independently authenticated brake, protected distinct host identities, same-user tamper resistance, all-path cgroup migration denial, power-loss recovery or user-manager/Docker-daemon failure recovery. The nonblocking lock returns unresolved if an admission operation is still active; Docker create/start calls and outcome ambiguity prevent a bounded independent stop claim. Output release, orphan reconciliation after a remove-before-receipt crash, and policy revalidation remain fail-closed. Production remains disabled.
