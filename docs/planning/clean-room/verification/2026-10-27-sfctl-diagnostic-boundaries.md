# sfctl diagnostic boundaries — 2026-10-27

`sfctl` now refuses identifiers containing URL path metacharacters, limits gate kinds to the existing promotion and grant route namespaces, disables automatic redirects and inherited environment proxies, and requires parseable JSON before treating a successful HTTP response as success. Normal colon-separated task IDs remain accepted. Non-success HTTP responses remain failures and retain their diagnostic body.

The actual CLI binary was tested against isolated loopback HTTP fixtures. Test-first controls reproduced a successful exit on malformed JSON, a cross-origin 307 redirect being followed, and traversal through a task ID. All seven CLI tests passed after the change. `cargo clippy --offline --locked -p sfctl --all-targets -- -D warnings` passed. The first redirect test did not fully read request headers and therefore saw a connection reset instead of exercising the redirect; correcting the fixture reproduced the failure before the fix. An early path test was interrupted because its fixture did not answer an unexpected request; its corrected fixture then reproduced the failure.

Response bodies are now limited to 1 MiB, whether a Content-Length is supplied or the response is chunked; the limit is enforced before any response body is printed. An oversize test initially failed, then passed for both successful and error HTTP statuses with declared lengths and chunked encoding. A bounded multi-chunk JSON response and the existing error diagnostics also passed. The CLI suite now passes nine tests; strict scoped Clippy passed.

These are diagnostic client protections, not authenticated runtime or action confirmation. The CLI's submit shape does not implement the durable intake contract; operator approval, budget, independent stop, and denial have no verified production transport here. Valid JSON alone does not prove that a remote operation occurred. HTTP endpoints have not been established as trusted local private ingress. No privileged route was enabled.
