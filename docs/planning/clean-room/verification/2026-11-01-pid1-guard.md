# PID1-owned guard and generic Root launch component qualification

The watchdog child previously shared the supervisor service cgroup even with a separate session. Root start now creates one independent, fixed-policy PID1 transient service before any Docker mutation. A durable grant-bound guard intent precedes the sole StartTransientUnit dispatch with fail mode; unknown acknowledgement cannot rearm. Verified readiness binds configuration/source hashes, grant, boot, owner PID/start identity, guard PID/start identity, cgroups and systemd invocation. Root checks the actual PID1 unit and live process before Docker create and again before start. The guard is outside both supervisor and worker subtrees; it has no owner-lifetime dependency, no restart, a finite runtime/stop budget, private networking and fixed memory/CPU/PID limits. ExecStopPost provides the same cleanup after a main-process crash. It creates no inference, spending or evaluator authority.

Root configuration schema 2 requires explicit guard_program, supervisor_program and systemd_library paths with their SHA256 pins, in addition to existing Python, worker and recipe inputs. Paths must be the reviewed installation with Root-owned nonwritable ancestors. The native context authenticates PID1 through the private bus and bounds method calls. Both harness profiles now include the guard source. No production configuration, catalog or approval was synthesized or installed.

Fresh native owner-loss and guard-main-crash replays use the actual Root constructor, prepare/start and guard programs. A public 120-slot catalog, registry approval and owner replies are explicit synthetic fixtures; this is not a real paired suite or production bootstrap. In owner loss the entire supervisor service cgroup is killed; the guard remains alive while owner acknowledgement is held, and the exact worker is frozen/removed. In main crash PID1 signals only the guard main process; ExecStopPost performs cleanup while the supervisor remains alive. Both obtain the exact synthetic owner acknowledgement. These native receipts retain fixture checkpoint 6f8d; the final fixture only relocates its observer deadline assertion to every iteration, including valid/null JSON reads. That bounded source-review correction does not change either production program, whose hashes match the native receipts. Kernel limits are 268435456 memory bytes, 32 PIDs and cpu.max 100000 100000. The real wallet revocation/restart proof remains separately qualified by the preceding milestone, not joined to this fixture.

Native work found and fixed the long relay pathname defect and an incorrect D-Bus property interface: ControlGroup belongs to Service, not Unit. Untrusted group-writable staged source was correctly refused; its fixture directory mode was corrected. A later native observer also caught a started marker before its write completed; bounded reads now wait for complete JSON instead of treating existence as completion. No inference was resent or attempt rearmed.

The attempted pidfd signal was refused by the controller's existing Docker signal policy; qualification instead uses authenticated PID1 KillUnit(main), preserving that policy. Killing the entire guard cgroup also killed the newly spawned stop-post process; that broader guard-group failure is not qualified. Whole-supervisor-group loss and guard-main crash are the two proved cases. Broader daemon/host-loss and combined guard failure with unknown queued Docker work remain open.

A leftover unstarted container from an earlier failed fixture was retired only after strict actual Root inspection of image, labels, containment and mounts, Running=false and PID=0; state evidence was preserved.
