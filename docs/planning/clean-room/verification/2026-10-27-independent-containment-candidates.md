# Independent containment candidates

The current host is Darwin; the prior owned-child `setsid` test already demonstrates that process-group cleanup misses an escaped session. Apple's [launchd plist documentation](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5) describes cleanup of processes remaining in the job's **same process group** when the job dies. That is independent of the job but does not establish cleanup of the escaped child. This is a documentation assessment, not a test of a launchd job. No job or service was installed.

A candidate for a different environment is a task-owned Linux cgroup v2 subtree. The [Linux kernel documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html) specifies that `cgroup.kill` kills processes in the subtree recursively, handles concurrent forks, and protects the kill operation against migrations; `cgroup.events` reports whether the subtree contains live processes. These are kernel interface semantics, not evidence that the current host provides the interface or that a chosen deployment has configured it safely. `populated=0` says nothing about processes that escaped before membership was established or moved out beforehand, nor about later admission.

A meaningful implementation needs an independent, persistent authority outside the workload cgroup that creates and retains the identity of each protected subtree, places the workload inside before any untrusted instruction can run, prevents worker-controlled migration outside, closes admission on stop, invokes `cgroup.kill`, and observes `populated=0` on the same authenticated subtree. A still-operational authority or service manager must act after the original guardian dies, and recovery must quarantine ambiguous state rather than reuse recorded PIDs. The worker must not be able to submit external jobs or otherwise create work outside the subtree. The subtree and its ancestors must be protected against replacement and unauthorized writers; the brake and any failover authority need separately tested permissions. A cgroup is not by itself filesystem, network, credential, or kernel isolation.

Before adopting this design, use a fresh disposable Linux environment with an independently controlled cleanup path and positive no-kill controls. Verify hostile `setsid` and nested groups, concurrent fork and migration attempts, supervisor kill and pause, launch and stop races, denied or failed writes, observer failure, restart with ambiguous state, and no readmission until observed empty. Prove both termination and the negative control, with bounded cleanup of every test-owned workload even if the authority under test fails. No Linux VM, container engine, account, privileged service, or existing workload was created or touched in this assessment. The local production gate remains closed; no implementation is claimed or activated.
