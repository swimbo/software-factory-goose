# Latched guarded-release admission fixture

`watchdog::guarded_admission` now connects the reusable guarded-release fixture to the existing durable recovery latch. A caller constructs one immutable local fixture command specification; creating its launcher exclusively creates and syncs the private root's unresolved marker before spawning. `launch` consumes the specification before attempting spawn, so both a completed launch and a spawn failure refuse a second launch through that instance. Another launcher on the same marked root also refuses; the component never clears the marker. The actual inherited-group execution guarded-release example uses this API, with a separate disposable private lane for each test case.

The admission test first failed because the API did not exist. Five focused tests passed: a guarded frame with same-instance and same-root replay denial, a preexisting marker preserved without spawning, a failed spawn permanently consumed, an eight-way same-root reservation race with one winner, and an owned supervisor killed after its finite child had started followed by same-root readmission refusal. The surviving synthetic child was allowed to finish naturally; no persisted or orphan PID was signaled. Strict watchdog all-target/all-feature Clippy passed, as did the actual inherited-group guarded-release fixture.

This is not production launch authorization. Trusted callers can still use the lower-level fixture `FixtureGroup::launch` directly, choose a different root, replace same-UID files, or supply an arbitrary trusted command at setup. The path canonicalization is not executable sealing, and the root lacks proven ACL, ancestor, identity and same-UID protection. The latch does not stop existing work after owner death, establish escaped-descendant containment, survive all power-loss cases, or provide a verified recovery/clear procedure. The example's test lanes are separate temporary roots and do not prove a stable deployed root binding. No VM, service, account, credential, or unrelated process was touched.

## Admission snapshot and root ACL checks

Two test-first controls showed the original admission accepted an executable replaced or rewritten after approval and a replaced working directory. The fixture now snapshots no-follow executable metadata and bounded SHA-256 content, plus working-directory identity, and rechecks both after consuming the single-use launch and immediately before spawn. It rejects changes detected during hashing. A separate test showed a mode-0700 latch root with an extended ACL was accepted; the latch now rejects an extended ACL using the open directory descriptor before marker creation (and checks both access and default POSIX ACL xattrs on Linux). All eight focused guarded-admission tests passed, including those negative controls.

These are pre-spawn checks, not an executable seal or protected launch identity. The executable and cwd are reopened by path during spawn, so same-UID mutation or directory substitution after the recheck can still race execution. Ancestor protection, filesystem ACL changes after inspection, immutable binary storage, ownership binding across restart and alternate roots remain unproved. The Linux ACL branch was implemented but not tested on this macOS host. The earlier limitations and production block remain in force.
