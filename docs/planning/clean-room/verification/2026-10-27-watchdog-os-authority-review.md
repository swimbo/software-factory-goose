# Watchdog OS authority: review proposal, not provisioning approval

Status: no accounts, services, privileged helpers, credentials, or production listeners created. Existing production broker policy still rejects root and overlapping identities. Same-UID fixture results cannot close this gate.

## Exact missing authority on this Darwin host

The current process can spawn and signal its own disposable children. Configuring a different UID is not permission to assume it. Arbitrary `setuid`/`setgid` transitions require superuser authority; changing supplementary groups also requires it. The child setup must set the complete reviewed supplementary-group list, GID, and UID in that order, verify every result, and fail before exec on any error. A nonroot watchdog cannot achieve that by merely filling `ApprovedLaunch.uid/gid`. [Apple setuid/setgid](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/setuid.2.html), [Apple setgroups](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/setgroups.2.html).

Spawn authority alone is insufficient. After a child assumes a distinct UID, a nonprivileged parent with a different UID normally cannot send SIGKILL. Parenthood and Unix peer authentication do not grant that permission. A supervisor needs matching signal identity or appropriate privilege for every owned group member. Zero-signal checks are observations, not permission or cleanup proof. [Apple kill](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/kill.2.html).

Wait ownership must accompany spawn ownership. Rust `Child::try_wait` reaps an exited child; dropping `Child` neither waits nor kills it. The adapter may receive pipe data and a result, but cannot retain a second waiter or reconstruct ownership from a numeric PID. The registry reserves the leader PID until its group signal attempt and never sends another nonzero signal after reaping. [Rust Child](https://doc.rust-lang.org/std/process/struct.Child.html).

## Proposed path for a subsequent architecture/security review

1. Select an OS supervision boundary before account provisioning. One option is a very small privileged supervisor behind a nonroot authenticated broker frontend; it would own spawn, exact credential transition, signalling, and reaping together. Another is an OS service manager with equivalent immutable launch, containment, identity and ownership guarantees. Neither is implemented or approved here. Running the existing HTTP watchdog as root is not the proposal.
2. Produce a reviewed role matrix with fixed IDs for watchdog frontend, privileged supervisor if selected, trusted adapter, worker/Goose/tool identities, operator and independent brake. Explicitly exclude ordinary identities from brake authority. Validate real UID/GID/supplementary groups and protected socket-directory ownership/ACLs using read-only checks before enabling anything.
3. Define a trusted launch publisher linked to authoritative claim/lease/deadline and policy eligibility. Admit exact protected executable content, argv, cwd, environment, IO and family once; callers select only opaque IDs. The model cannot publish launch specs. Current metadata checks are not atomic executable sealing and must be strengthened before adversarial use.
4. Keep independent stop-only authentication and credential delivery separate from spawn permission, model context, argv and logs. UID proves account identity, not human presence or MFA. Stop must continue with control-plane, journal, database and worker unavailable.
5. Test fresh disposable distinct accounts only after explicit provisioning authorization: spawn and signal denials, group membership, stdin/stdout/stderr, cancellation, dead worker, escaped `setsid`/`setpgid` descendants, supervisor SIGKILL/restart, ambiguous acknowledgements and PID reuse. A persistent OS containment boundary is required if descendants can escape groups. Never replay saved numeric PIDs after restart.

## Current fixture boundary

`broker_capture_fixture` is opt-in and same-UID. It reads a private local synthetic catalogue before serving, exposes no admission route, and owns a maximum of three approved roots. Capture is bounded to 1 MiB per UTF-8 stream with no partial forwarding; stdin/environment have separate bounds. It is complete-result polling, not a general duplex MCP transport. The real MCP protocol adapter is copied unchanged, but its `run_worker` function is replaced by an exact synthetic alias-to-catalogue lookup. This does not prove execution policy, output masking, durable receipts, distinct accounts or production authentication.

Pinned Goose 1.49.0 creates a distinct MCP group by default. The lifecycle fixture requires observed adapter/Goose group equality before tool launch and fails closed otherwise. A narrow restricted-mode inheritance patch now passed the bounded actual-Goose fixture and ordinary-isolation control; see [lifecycle evidence](2026-10-27-goose-broker-lifecycle.md). Even inheritance cannot contain intentionally escaped descendants, and changing ordinary Goose grouping globally is out of scope.

Darwin-specific capture observation: a zombie-only group can yield EPERM before the retained leader is reaped. The fixture does not interpret EPERM as successful signalling. It reaps an already-observed exited owned leader after the single signal attempt and releases output only after observing ESRCH for the group; it never retries a nonzero signal after reap. This is consistent with XNU's zombie filtering in `killpg1`, but remains host-tested evidence rather than a portable permission rule. [Apple XNU source](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c).
