# Relay candidate and public canary plan

The uninstalled `clean-room/deployment/relay/` candidate contains a systemd-activated server, fixed protocol and root-peer clients. The server requires named descriptors for a root:root 0600 per-generation scope, exact root catalogue, launch-consumed record, and versioned provider binding; the existing bo:0600 credential; and a root:2001 0660 callback listener. Root descriptor metadata and the exact catalogue, provider-binding and consumed-grant digests are checked. The scope is trusted as root-authored: the actual launcher has not yet proved that it derives this scope and binding from the journal grant, catalogue, recipe, boot and cgroup. The evolving journal grant includes intent and queue IDs and its catalog digest is a full qualified Catalog fingerprint; whether that digest equals these raw catalogue bytes must be reconciled before adoption. The consumed-record path is not selected, and no candidate unit is installable as written.

Scope schema 2 explicitly pins the canonical normalized initial envelope (`goose-turn-context-v1`): exactly two messages and the fixed write_files-only schema, 16,384 output tokens and streaming. The user prompt is retained verbatim; the only removed portion is the exact trailing UTC turn context, which must contain a timestamp within 120 seconds and working directory `/work/task`. Duplicate keys, context injection and other shapes fail. This is a new versioned contract, not an interpretation of the earlier raw-byte digest; actual Goose profile compatibility remains unproved. The state machine forces provider model `auto`, validates returned model identity against the root scope, parses bounded SSE, admits only the fixed two-file payload, checks the exact continuation, and fsyncs per-generation inference/writer markers before side effects. Ambiguous outcomes stay fenced. Linux callback checks kernel peer UID2001 and server UID2000. UID2000 retains the ability to alter its own fence directory; same-UID compromise is outside what these markers prove.

The transport candidate uses an inherited read-only credential descriptor and a direct fixed `127.0.0.1:8080` connection, checks root-bound network-namespace device/inode before and after the call, rejects redirects and ambiguous/oversized HTTP framing, and never uses proxies. The inherited credential is read only during the fenced call and is not intentionally put in argv, environment, logs or worker replies; echoed credential bytes are refused. The connection timeout is an idle socket timeout, not independently proven as an absolute wall-time bound. Netns inode matching does not prove Docker container, image or PID identity; the proposed root guard must check those and closure around every effect. No actual provider request or credential access has occurred.

The per-generation root broker client proposes `/run/software-factory-goose/writer/<generation>.sock`, root:2000 mode0660, under a root-owned non-writable parent. It verifies kernel peer UID0. `guard` responses must bind the generation, grant, catalog, provider-binding digest and namespace identity; `write_files` carries only the two typed files. The unregistered root broker candidate verifies fixed Docker inspect metadata, root closure, boot/cgroup identity and freeze state; it writes a permanent intent, then publishes root-owned request and ready files to a fixed input directory, and validates a bounded UID2001 writer receipt with both content digests. The fixed writer reads once, writes only the two named files using anchored exclusive operations, never executes them, and produces the receipt. A temporary-directory two-party test exercised those actual operations and replay denial; ownership metadata was simulated. A real child SIGKILL after request publication left the durable intent and request without ready, and a fresh broker object refused replay. The broker validates a strict root-authored writer binding including exact handoff directory identities. The root broker has no activated entry point. Its candidate verifies a versioned root writer-binding record, directory device/inode, a fixed Docker writer inspect shape and the same running PID in the generation cgroup; the UID2001 writer remains idle after its one result until stopped. Program provenance, seccomp and the actual root launcher/seal and mount binding are not yet proven. Closure races remain open. The guard call is not an atomic exclusion of a stop, and response-side model checks cannot prove an unapproved fallback did not incur a charge. These are activation blockers.

Thirty local Python tests passed, covering mocked authorities and provider/writer connections, bounded callback frames, a real localhost synthetic chunked HTTP response, a synthetic two-inference/write loop, a lost provider response, a stop observed after inference, 16 concurrent marker attempts producing one winner, and an owned child SIGKILL after marker fsync. SIGKILL is not power-loss or host-reboot evidence. UID, peer, root-descriptor metadata, manager, provider and writer behavior were simulated; no cross-UID socket, inherited descriptor, actual network namespace, Bifrost routing, writer execution or end-to-end integration was proved.

## Public-only canary plan for root review

Prepare exact source and units in `clean-room/deployment/relay/units/`. The public canary source has SHA-256 `7e74a19adb15fee937196d4c5e98dc0f0e1732c9d09379bfd42b29f04b20cfce`; its unit draft has SHA-256 `481e09ff61f6ba125d8abad28dfb15f9a1f205313b56bbd91bfe607955d863fa`. Root would create an exclusive root:root 0700 `/etc/software-factory-goose/openfile-public-canary` containing only public `public` and `expected` mode0600 files. `public` contains `SFACTORY-PUBLIC-OPENFILE-20261030` plus newline; `expected` is a root-produced JSON object with the current `/proc/1/ns/net` device and inode. The fixed unit uses `User=sfgoose-control`, `NetworkNamespacePath=/proc/1/ns/net`, and two named read-only OpenFile descriptors. It also checks that UID2000 can query the inherited files for absence of an access ACL, and emits only UID, fixed public digest and a namespace-match boolean. The create-only installer candidate `nuc_openfile_canary_install.py` (SHA-256 `489c71bf764353d8f47bcc5fba7f0434b27908d787bebcf7151f02ed7410e17e`) prepares public files and the disabled unit only; it never runs daemon-reload or starts the service. It requires a fixed mode0700 UID1000 source directory with mode0600 hash-pinned sources and refuses preexisting targets or a changed reviewed plan. The root bridge must see the host PID namespace for `/proc/1/ns/net`; this has not been verified. Review must validate ancestors, ACLs, no preexisting targets, source hashes, boot identity, create-only records and service-manager side effects before applying; a changed or partial plan fails closed and existing resources are preserved. This canary does not exercise the actual Bifrost namespace or provider credential.

[systemd 257 OpenFile documentation](https://www.freedesktop.org/software/systemd/man/257/systemd.service.html#OpenFile=) says the manager opens and passes the descriptors; [NetworkNamespacePath documentation](https://www.freedesktop.org/software/systemd/man/257/systemd.exec.html#NetworkNamespacePath=) says the configured namespace path is joined at process fork. The public canary must establish behavior on the NUC, not merely rely on documentation.

After that canary and separate root review, the candidate unit could use `NetworkNamespacePath` bound to the exact current Bifrost SandboxKey and PID1 `OpenFile` on the existing credential, avoiding a copy. The credential must remain out of worker mounts and diagnostics. Root must verify the live Bifrost CID/image/PID/SandboxKey/ns identity before and after effects. The parent callback directory must be UID2000:2000 0700; the socket root:2001 0660 is the only worker bind mount. Both relay and writer must live in the exact generation slice, with independent root stop, permanent admission closure and separate engine reconciliation. A socket unit may reactivate a failed service even with `Restart=no`; safe socket shutdown/reconciliation and any lost-start race remain explicit gates. The named run has no monetary caps; production defaults remain unchanged.

No host action, service installation, provider call, actual credential read, or worker activation was performed by this candidate.
