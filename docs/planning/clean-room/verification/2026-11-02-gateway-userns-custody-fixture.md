# User-namespace custody experiment

An isolated Linux x86-64 experiment found a potential post-exec boundary. A Root controller created a child user namespace, installed explicit same-number UID and GID mappings, dropped the target to UID 2007 with no effective, permitted, inheritable or ambient capabilities, and executed a synthetic target under no-new-privileges. The target's dumpability after exec was 1. An unconfined, capability-free host-namespace sibling with the same UID received EPERM from both `pidfd_getfd` on its listening socket and `ptrace`; the same attacker successfully performed both operations against an ordinary same-UID positive control.

The synthetic listener had owner UID 2007 and broker group 2008. The target saw those socket identities through the namespace mapping, a separate broker UID 2008 connected and observed the expected target PID and UID via `SO_PEERCRED`, and the Root controller could inspect the target executable. The fixture used a network-disabled disposable container, a temporary socket directory, disabled outer seccomp and AppArmor profiles for a meaningful attack control, and the host's existing Yama scope 0. It created no persistent namespace or host policy.

This does **not** qualify production custody. The fixture does not run the actual gateway barrier, Bifrost, Root supervisor, cgroup guard, route, credential or wallet; it does not prove namespace-map ownership, secure bootstrap, socket-transfer confinement, egress fencing, descendant cleanup or owner/daemon/host-loss handling. It maps root and the broker group for compatibility and must not be copied into production without analyzing namespace capabilities, map construction, identity exposure and lifecycle. Rehearse the actual helper and launcher with a validated map and the inherited descriptor filter before considering admission. Paid benchmark attempts remain **0/120**, with the candidate disabled and the existing spending and safety gates unchanged.
