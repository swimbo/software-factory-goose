# Reusable guarded-release fixture

The prior [trusted release example](2026-10-27-trusted-release-fixture.md) now uses the reusable feature-gated `watchdog::guarded_release::FixtureGroup`. It spawns its own group leader from a trusted fixture command and does not accept a caller-supplied PID. `complete` reads one bounded frame internally and returns its bytes only after the live owned group was signaled, its leader reaped, and group absence observed. Bad, oversized, incomplete, or timed-out frames trigger best-effort cleanup and never return frame bytes. A signal failure retains the unreaped leader and withholds the frame; the fixture has no persistent recovery service.

Test-first integration tests initially failed because the component did not exist. The final watchdog all-target/all-feature run passed 36 tests, including successful release, malformed/incomplete frames, dead leader, and an injected `EPERM` that preserves the live owned child. Strict Clippy passed. The actual inherited-group execution example also passed when invoked as `cargo run -p watchdog --features fixture --example trusted_release_fixture --locked --offline` after building execution with `--features fixture-inherited-group`: it exercised masked output, oversized frame, a timed-out child with no-stop positive control, and a dead leader.

This API exists only with the watchdog `fixture` feature. It accepts trusted `Command` input and does not authenticate a launcher, protect the same-UID frame channel against hostile processes, verify all descendants, or recover ownership after process death. Its cleanup and destructor cannot guarantee termination after an OS signal failure or a stuck process. `setsid` escape, cross-UID authority, loss of the guardian, actual Goose/tool broker wiring, and durable quarantine remain open; no production activation is implied.
