# NUC service-owned tool relay fixture

On `hermes-control` (Linux, service UID 1000), the task-owned harness ran a disposable loopback Restate service and a service-owned Unix socket. Kernel peer credentials rejected host UID 1000 and unrelated container UID 1002; UID 1001 sent the exact synthetic provider tool ID and arguments. The service launched the actual Linux `execution --tool-request` binary in a separate pinned Python-image container with UID 1001, no network, read-only root, no capabilities, no-new-privileges and bounded CPU, memory and PIDs. The host captured the execution response, bound it into the real unregistered `ConversationFixture`, and observed that forged continuation and repeated begin were rejected. Tool ID replay was refused before another execution. The response was synthetic `RELAY_OK`; no live provider, credential, or production route was used.

The exact output is `/tmp/sfactory-nuc-relay-journal-20261028.log` on the Mac, SHA-256 `e9b9a27593b11c7e70f46b234abbb0e4c2c8431d83595dc15e8aee32a7e937f1`. Harness source is `clean-room/tests/fixtures/{trusted_tool_relay.py,nuc_trusted_tool_relay.py,nuc_tool_relay_journal.py}`; three focused relay unit tests pass. NUC retained task-owned `/tmp/sfactory-tool-relay-code.f6O9xEoS` (34 MiB) with source, build log and Linux SDK fixture SHA-256 `cd38b969ce0dd003dd72bce292c4ee9c2cdf5f540da4b61d4a8cbfe6475db27c`. The isolated 1.5 GiB registry and 798 MiB build target were removed after the run. The pinned build container used offline locked Cargo dependencies; six missing exact crates were fetched into that isolated registry, with Cargo lockfile checksum verification. No fixture-labelled containers remained. Docker, Hermes gateway and Hermes dashboard reported active. Existing Stapled factory containers and their state/dispatch mounts were not touched.

This is not production authority: provider tool ID is injected by the trusted harness, not captured from actual Goose/provider SSE; the relay's replay state is process memory and does not survive restart; and Docker executor cleanup on relay death is not independently supervised. The MCP protocol bridge, actual Goose-to-relay connection, route snapshot and classifier charges, durable task/session provisioning, aggregate ledger migration, and live provider budget bounds remain unproved. The disposable journal's trusted bind endpoint is isolated from the network-none client, but is not itself a production authentication boundary.
