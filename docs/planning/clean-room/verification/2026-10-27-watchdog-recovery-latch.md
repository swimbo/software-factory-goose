# Disposable watchdog restart quarantine

The fixture watchdog now creates a `recovery-required` marker in its private test root before opening its brake socket or spawning children. Creation is relative to an opened no-follow directory and uses exclusive no-follow creation; the marker and directory are synced before startup continues. Existing markers reject startup. The fixture exposes no automatic clear, no persisted process identifiers, and no signal by persisted PID. A failed startup after marker creation is conservatively quarantined too.

The restart test first failed before implementation because the fixture had no latch mode. The completed test starts an owned fixture, waits for marker creation, kills and reaps that exact child through its live process handle, and verifies that another fixture refuses the same root. A separate test proves a pre-armed marker prevents the actual fixture server from creating a socket or child readiness file. An eight-way race admits one marker creator; symlink-marker and nonprivate-root tests reject startup while preserving the target. Tests remove only their own temporary roots and markers.

The all-features watchdog run passed 29 tests; strict all-target/all-feature Clippy passed. This establishes process-crash persistence and startup quarantine only in a same-UID disposable fixture. It does not establish that work from the old owner stopped, and it does not authorize another run with a different root. The marker can be manipulated by a same-UID adversary, ancestor/ACL protection and deployed identity are unverified, directory replacement and power-loss recovery are unproved, and no independent procedure exists to reconcile or clear it. No VM, existing service, account, or credential was touched. Escaped-descendant containment and owner-loss teardown remain open.
