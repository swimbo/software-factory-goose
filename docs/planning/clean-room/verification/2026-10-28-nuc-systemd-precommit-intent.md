# NUC precommit recovery intent fixture

The systemd/Docker fixture now commits a private mode-0600 intent **before Docker create**. It contains the random token, expected label, worker-slice name and slice inode; the fixture fsyncs the intent file, atomically renames it, and fsyncs its directory. Only then does it create the container, initially stopped. The full-ID manifest is committed with the same sequence before the launch gate opens. The local ordering test observes intent file fsync, intent-directory fsync, create, manifest file fsync, manifest-directory fsync, then launch. This is an ordering check, not a power-loss durability test.

Two final NUC runs of `python3 clean-room/tests/fixtures/nuc_systemd_docker_recovery_spike.py precommit` killed the exact transient unit main after Docker create returned and before the full-ID manifest was committed. The external test verified that the label-matched container was in Docker's `created`, non-running state and that no full-ID manifest existed. The manager's `ExecStopPost` read and validated the committed intent, inspected the deterministic task-owned name and unique label, required the expected slice and a full 64-character ID, and required exactly one matching labelled container. It then used **non-force** `docker rm`; it never signalled a target lacking a committed full-ID manifest. The independent observer checked removal and `populated 0` on the same worker-slice inode, `6882200`. Both runs passed; [the final log](2026-10-28-nuc-systemd-docker-intent-precommit-repeat.log) records the result. A separate [normal-mode run](2026-10-28-nuc-systemd-docker-intent-normal.log) still passed after the change.

The [six local control tests](2026-10-28-nuc-systemd-intent-tests.log) cover fsync ordering; missing or tampered intent; missing or tampered manifest and wrong full identity; absent, running, exited, wrong-slice, duplicate-label and invalid-ID precommit cases; and an injected start racing non-force removal. Invalid or ambiguous cases return an error without a kill or cleanup mutation. The racing-start mock verifies that removal failure is reported and no signal follows. Docker's non-force removal refuses a container that is running at removal time; it does not provide an atomic conditional check against another engine actor starting and then stopping the container between the separate inspection and remove operations.

The actual test reuses the two task-owned slices previously documented; no new root slices were created. The fixture units, anchors and containers were removed. An unavailable Docker engine, missing/ambiguous container, mismatched manifest, running container without a full manifest, or failed remove remains quarantined; no absent object is represented as a successful reconciliation. This does not prove actual daemon loss, systemd-manager loss, power-loss durability, same-UID/engine tamper resistance, reliable restart recovery or complete worker containment. Production remains fail-closed. This supersedes only the specific pre-manifest crash gap described in [the earlier fixture note](2026-10-28-nuc-systemd-docker-recovery.md).
