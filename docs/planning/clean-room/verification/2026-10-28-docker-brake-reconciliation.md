# Docker brake fixture reconciliation — 2026-10-28

The disposable Docker brake backend previously marked a cleanup attempt used before executing an unbounded Python child, so a slow operation could outlive the HTTP timeout and all later requests returned conflict even after success. It now tracks idle, pending, verified and unknown states. A concurrent identical target observes pending; after the single original attempt completes, retries observe verified only after successful cleanup and the fixture proof. Failure, timeout or panic remains unknown and never automatically reissues cleanup. A pre-existing cleanup result is refused as ambiguous rather than reused or deleted.

The fixed cleanup child runs with a 45-second fixture deadline in its own process group; on timeout, direct-child ownership is checked before attempting group SIGKILL and bounded reaping. Signal or reap failure remains unknown. The HTTP timeout does not cancel the running blocking cleanup task; a later request can observe its eventual state while the process stays alive.

Test-first local example tests initially failed to compile before the state machine existed. `cargo test --offline --locked -p watchdog --features fixture --example docker_brake_fixture` passed 2 tests: concurrent delayed success returns pending then verified with one cleanup invocation, and a real timed-out sleep returns unknown without retry. `cargo clippy --offline --locked -p watchdog --all-targets --all-features -- -D warnings` passed. No NUC fixture or Docker action was run for this change.

This is only an in-memory fixture: controller crash loses its status and a running daemon operation may outlive a killed CLI. Group signaling does not prove escaped descendants, Docker daemon cancellation, or verified container absence. A failed group signal retains unknown outcome; owner-loss recovery, durable reconciliation, independently provisioned authentication and production brake authority remain separate gates.
