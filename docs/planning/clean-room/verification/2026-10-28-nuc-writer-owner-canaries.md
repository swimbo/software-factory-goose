# NUC task writer ownership canaries

`nuc_writer_owner_spike.py` ran three no-provider cases with a task-owned systemd user unit, two fixed owned Docker roots and the task-specific writer. Before launch and after cleanup of each case it checked the separately retained original create's full ID, exact name, label, Created/PID 0, slice and daemon identity. It did not start, remove or rename that original object.

- **Success:** the fixed Python writer produced exactly `hello.py` and `test_hello.py`, without bytecode or other candidate entries. Killing the owner main caused its ExecStopPost to clean the owned roots; the same cgroup inode was observed `populated 0` and a repeated Batch writer invocation was denied.
- **Partial:** a fixture-only `sitecustomize` hook paused the real writer after its first link. Killing the owner then led to the same exact cleanup and replay refusal. The hook-created marker and partial candidate are synthetic controls, not production code.
- **Lost acknowledgment:** the writer returned after both files were present, then the owner was killed before a durable tool-result receipt existed. The owned roots were cleaned and Batch replay refused. This test has no actual provider fence or evaluator, so it does not prove either would withhold the complete-looking candidate.

The first preliminary run failed: using `systemctl kill --kill-whom=all` killed the newly started ExecStopPost control process, leaving recovery unresolved. The operator separately stopped only its exact owned batch and verified the worker slice empty; `/tmp/sfactory-writer-owner-3depu4dq` remains as evidence. That run also showed the imported contract emitted `__pycache__` inside the candidate; the fixed writer argv now includes Python `-B`, and the subsequent success case verified the exact two-entry set. The corrected canary kills only the owned unit's main process, allowing systemd to perform its configured control-group stop and recovery.

These cases validate fixed interpreter path/import, local Batch one-shot reservation and task-owned manager cleanup in this fixture. They do not establish actual Goose/provider binding, fsynced tool-unknown quarantine, evaluator rejection of the two ambiguous cases, failed cleanup refusal, production identity, or host/daemon-loss recovery. No live provider request was made. The retained original Docker create remains a conditional inert name fence, not proof that the timed-out request completed cleanly.

A later guarded rerun added an owned cleanup-failure control and shell-mode refusal. Before the writer call, the writer-kind executor rejected `exec_once` without consuming its writer reservation. In the cleanup-failure case, the test injected failure only into that fixture's Docker kill operation. ExecStopPost produced no recovery receipt and the worker slice remained populated; a separate exact-owner Batch cleanup then succeeded, and the same inode reported `populated 0`. All four cases retained the original create fence unchanged. This does not test evaluator withholding of an ambiguous candidate or production Docker failure.

A final rerun inspected each running executor before invocation and confirmed both fixed writer and contract bind mounts had the expected host sources and container destinations with `RW=false`. All four canaries passed again, and the retained-original guard remained intact.

After the fixed role limits changed, all four guarded cases ran again with both Goose and executor roots running. Their Docker `HostConfig.Memory` values and corresponding live cgroup-v2 `memory.max` files independently matched 512 MiB and 128 MiB, respectively. Mount and cleanup controls passed and the original guard remained intact. These idle fixture processes do not establish that actual Goose can process a fragmented 8 MiB stream without OOM.
