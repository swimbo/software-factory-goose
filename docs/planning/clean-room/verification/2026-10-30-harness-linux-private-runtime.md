# Native Linux private spending runtime — 2026-10-30

**Passed: disposable native x86_64 UID/private-journal fixture. Candidate disabled; paid benchmark runs 0/120.** This proves one runtime boundary, not production activation, native Goose/evaluator integration, provider billing or Phase 11A completion.

The fixture built the current spending journal and ingress source offline on the NUC using the cached Rust image, exact direct dependency versions from the repository lockfile, a read-only public Cargo registry and a fresh target directory. Build limits were two CPUs, 3 GiB and 500 seconds. The binary SHA-256 is recorded with source hashes and Cargo manifest/lock hashes in the adjacent JSON receipt.

The service ran in a fresh ext4-backed chroot in its own `network=none` container. Root administration used UID 0, the broker UID 2000, collector UID 2002, service UID 2004 and worker UID 2001. Each role client used a **different** `network=none` container and received only the frontend Unix socket directory. The worker could not reach the service container's loopback SDK or Restate ports. A separate negative probe mounted the private backend directory read-only and demonstrated filesystem refusal for both worker and broker identities.

Verified against the actual Rust ingress and actual Restate journal:

- Kernel UID roles override forged `x-uid: 0`/`x-role: root` headers. Worker, collector and root cannot reserve as the broker; broker cannot initialize or claim receipts.
- The actual `PrivateSpendingClient` Python implementation reserved and began a call as UID 2000, verified the service peer UID and refused an administration method. Its broker container used its own ext4 chroot, without the service backend directory.
- Repeating a reservation charges once; dispatch begins once. Unknown dispatch state, denied daily admission and generation ownership survive a SIGKILL of only the owned Restate process.
- Replacing the backend socket returns 503 through the stale ingress. The fixture retains the old socket inode under a private retired name, making replacement detection deterministic. Explicitly restarting the owned ingress pins the replacement without replacing the journal.
- A conflicting generation manifest is refused before legitimate replay can recreate claims. Root reinitialization with zero opening spend is refused.
- The fresh synthetic owner has a $3 opening reservation and three $0.60 reservations, leaving $0.20 of its $5 daily allowance. Another $0.60 call is denied. Settling a $0.60 reservation to two synthetic microUSD does not admit a fresh $0.30 task: day-only refunds would incorrectly admit it. A new attempt for the settled task requesting $0.20 is denied at its permanent $0.75 task cap even though the daily bound would allow exactly $5. Neither midnight nor a new task budget was simulated as an allowance reset.

The worker and fixed HTTP role clients retained read-only roots, no capabilities, no-new-privileges and a 16-PID limit. The protected Python broker client used a separate owned ext4 chroot bind for trusted bootstrap, then dropped to UID 2000 without retained capabilities; it had no service backend mount. Only trusted chroot controllers received the capabilities needed for their owned setup. The service controller additionally needed to signal its own cross-UID children. These capabilities were not retained by the dropped-UID service children or worker clients. The service was bounded to two CPUs, 1 GiB and 512 tasks; the first 128-task fixture limit correctly exposed Restate thread exhaustion and was adjusted for the trusted service, without changing worker limits.

The strict filesystem checks were preserved. An initial `/tmp` stage failed because the NUC's `/tmp` is tmpfs. The final stage uses `/var/tmp` ext4; no overlayfs or world-writable ancestor exception was added. A fixture-only module-loop name shadowing issue was corrected; its newly created container was removed, and final execution used the recorded unique fixture name. All owned test containers were removed and their absence checked. Existing factory services, users, credentials, routes, volumes and journals were untouched.
