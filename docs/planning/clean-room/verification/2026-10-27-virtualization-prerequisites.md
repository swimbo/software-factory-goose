# Virtualization prerequisite and recovery audit

**Result: containment spike incomplete; VM not started.** macOS 26.4 (25E246), arm64, Darwin 25.4.0. `tart`, `vfkit`, and `qemu-system-aarch64` were not on PATH. `xcrun --find swift` identified the Xcode toolchain. A workspace and `/Users/bo/.cache` filename inventory found no task-owned Linux kernel, initramfs, ISO, qcow2, or img. This is not a host-wide claim that no images exist; existing VMs and their storage were not inspected or started.

`python3 clean-room/tests/fixtures/virtualization_config_probe.py` compiled a temporary Swift executable, ad-hoc signed it with `com.apple.security.virtualization`, and validated an otherwise empty, networkless Virtualization configuration with a dummy kernel path. It reported `virtualization_supported=true` and `configuration_validated=true`; codesign displayed the entitlement. The temporary directory was removed by the fixture. No VM object was created or started. Validation does not verify that the dummy file is a bootable kernel, that guest isolation works, or that a separate stop authority exists.

Apple's [VZVirtualMachine documentation](https://developer.apple.com/documentation/virtualization/vzvirtualmachine) describes an object configured and started by its app and requires the entitlement. [Stop documentation](https://developer.apple.com/documentation/virtualization/vzvirtualmachine/stop%28completionhandler%3A%29?language=objc) says stop applies to a running or paused VM and calls back after success or failure; it is destructive to guest state. [Entitlement documentation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.virtualization) says configuration validation checks availability of the required entitlement. None of these sources establishes an independent controller that can take over a VM after its owner hangs or dies, nor an independently queryable terminal state after owner loss. No such authority was found in this audit; this is a gap in the evidence, not proof that the platform lacks one.

The public [Alpine aarch64 netboot directory](https://dl-cdn.alpinelinux.org/alpine/v3.22/releases/aarch64/netboot-3.22.0/) provides candidate kernel and initramfs files; a read-only HTTPS HEAD to its kernel returned 200. It was not downloaded or executed. No task-owned, authenticated and pinned guest image or independently observable cleanup mechanism was established. In particular, killing a VZ owner and observing only its PID disappear would not prove the VM and guest workload stopped. Therefore no owner-kill test, guest workload, host-access or network-denial assertion was performed. The previously recorded `process_group_escape.py` result remains the negative native process-group baseline.

To proceed, first specify and verify a task-owned independent lifecycle authority or an authoritative host observation of termination, obtain and verify a pinned guest image, and construct a bounded fixture with independent teardown. Then run the positive boot and stop controls, escaped and suspended workload checks, host/network negative controls, and owner-pause/owner-kill/blocked-launch recovery controls from the [spike plan](../decisions/2026-10-27-os-supervision-boundary/spike-plan.md). Until those pass, neither VM containment nor production runtime activation is established.

## Owner-loss research

Apple Developer Technical Support forum guidance in [VM execution ownership and crash reclamation](https://developer.apple.com/forums/thread/848542) says that the system is expected to clean up an unexpectedly terminated application's VMs, and that the identities and lifetime of helper processes are implementation details, not a reliable VM-liveness contract. A [follow-up on guest teardown](https://developer.apple.com/forums/thread/850709) says there is no guaranteed cleanup timeline or public successor-process handle to verify that the previous guest has finished. These are staff forum statements, not a formal bounded-teardown API guarantee. The follow-up discusses macOS 26.6 while the tested host reports 26.4; page timestamps are relative, so chronology and applicability to this host are uncertain. No experiment was run on that basis.

The public [VM state](https://developer.apple.com/documentation/virtualization/vzvirtualmachine/state-swift.enum) and [delegate](https://developer.apple.com/documentation/virtualization/vzvirtualmachinedelegate) report state via the owning VM object. A [saved-state restore](https://developer.apple.com/documentation/virtualization/vzvirtualmachine/restoremachinestatefrom%28url%3Acompletionhandler%3A%29) restores a stopped object from a previously saved file; it is not described as reattaching to a live VM. The [Mac machine identifier](https://developer.apple.com/documentation/virtualization/vzmacmachineidentifier) identifies virtual Mac hardware and is not documented as a handle for controlling or querying a live Linux guest. Process exit notification can establish owner death only, while missing heartbeat or helper-process disappearance cannot prove guest teardown. A live-owner stop callback and state are useful for a positive stop case but do not supply a bounded independent recovery path when that owner or its queue stalls. Accordingly no safe owner-loss experiment with guaranteed task-scoped cleanup was identified here; the ambiguous state remains quarantined.
