# G03 protected holdout-store reader

Date: 2026-10-27. Bounded evaluator-library component only. No users, groups, standing directories, endpoints or services were created or changed.

The reader enforces a configured store owner matching the actual effective UID, distinct non-root generator/evaluator/store identifiers, canonical no-symlink directory traversal, safe ancestor ownership/modes/ACLs, and exact store mode0700. Each read revalidates the root identity and current effective principal. The only selector is a canonical lowercase SHA-256 digest; no caller path is accepted. Files are opened relative to the pinned directory descriptor with `O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK`, preventing symlink following, descriptor inheritance and FIFO-open blocking. Regular manifests must be owner-only0600, owned by the store UID, single-linked and ACL-free.

Reads are capped at128KiB plus one detection byte. The reader checks stable descriptor/path identity and metadata, recomputes the expected digest, then invokes the strict fixture-manifest parser. Both parse and filesystem failures produce the same static opaque error. Returned manifests have no Debug/Serialize implementation exposing scenario bodies.

Primary local API evidence: the macOS CommandLineTools SDK `usr/include/sys/acl.h` declares `acl_get_fd_np`/`acl_free` and `ACL_TYPE_EXTENDED=0x100`; its `usr/share/man/man3/acl_get_fd.3` describes descriptor ACL retrieval and required cleanup. A disposable-file probe observed null/ENOENT for absent ACLs. The implementation accepts that absence only, rejects allocated ACLs and all other failures, and frees allocated ACL memory. Tests add actual ACL grants to disposable fixtures to establish that safe POSIX modes alone do not pass.

Test-first: tests initially failed for the missing reader API. After implementation and a syntax correction, eight filesystem fixtures passed. Two additional fixtures then passed: FIFO/directory refusal without blocking, and protected-manifest loading followed by a real Seatbelt scenario that cannot read a synthetic secret file in the store. Final focused result: **10 tests passed**.

Remaining boundary: R1 explicitly makes uid_store different from uid_val. A store-owner0700 directory cannot be read directly by the evaluator UID. This component must run on the store-owner side; authenticated private transfer and production runner ownership are not implemented. The fixtures use the actual current UID as store owner and synthetic other identifiers, without proving account existence or cross-UID denial. The digest must originate from authoritative task/store configuration, not a generator request. Same-owner hostile races and privileged host compromise are outside this trust boundary; content hashing and anchored descriptors do not replace distinct OS identities, mandatory access control or durable evidence provenance.
