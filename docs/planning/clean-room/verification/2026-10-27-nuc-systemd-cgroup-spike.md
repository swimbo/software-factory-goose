# NUC transient-unit containment spike

On authorized `hermes-control` (`nuc-hermes`), read-only inventory found Debian Linux 6.12, cgroup v2, an accessible user systemd manager whose overall state is degraded, and no pre-existing `sfactory-*` units. The existing services, containers, accounts, and data were not modified. The test creates only random `sfactory-<UUID>.service` transient user units and private temporary fixture files; `KillMode=control-group`, a finite runtime, and a finite stop deadline are set. Cleanup verifies the random unit description and executable before stopping that exact unit and collects only the fixture unit. It does not clear other failed-unit history.

Run with `ssh -o BatchMode=yes hermes-control python3 - < clean-room/tests/fixtures/nuc_systemd_cgroup_spike.py`. The test's worker forks a child that calls `setsid`; the child records its own `/proc/self/cgroup` and must match the unit cgroup. A no-kill control emitted its delayed marker. The external controller asks systemd to SIGKILL the fixture unit's main process by unit name, rather than signalling a saved numeric PID. The observer independently holds the unit's `cgroup.events` descriptor and requires `populated 0`; the delayed marker must remain absent.

The first run observed `populated 0` and no marker. The second, tightened run confirmed child membership and no marker, but the observer received `ENODEV` because systemd removed the cgroup before the next read; it **failed** the required empty observation. One successful observation is not a reproducible gate. A disappeared cgroup, absent marker, signal acceptance or inactive unit is not treated as independently observed `populated 0`. A persistent task-owned observation boundary or another authoritative independent teardown proof is required. No retry or longer timeout is treated as a repair.

Read-only permission inspection showed `bo` owns the user manager cgroup and its `cgroup.procs` and `app.slice` directory. This makes same-UID migration authority an explicit concern; no migration attempt into the existing shared user hierarchy was made. Until a separate identity or protected delegated subtree is demonstrated to prevent migration before and during teardown, this is **not a hostile-workload containment boundary**. Same-UID control of the user manager, external job submission, host-manager death, network/filesystem isolation and crash recovery also remain unproved. No production activation occurred.
