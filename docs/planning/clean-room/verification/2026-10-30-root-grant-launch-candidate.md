# Root grant and launch candidate: review only

The production-oriented root grant preparation and launch wrappers are source/build candidates. They are not installed, exposed on a root launch socket, or used for an engine effect. The earlier synthetic Docker deadline success is recorded separately in [root deadline evidence](2026-10-30-root-deadline-candidate.md).

`sfactory_root_grant_prepare` loads a root-only per-generation launch catalogue and exact canonical recipe; checks the existing root stop catalogue, boot, cgroup2 and inode; fsyncs a create-only request intent; and contacts only the fixed real grant socket using a bounded connect and request. A root peer credential reflects the systemd socket creator and is not proof of the server's process identity. The concrete attestor additionally checks root-protected unit, executable and config hashes; the fixed unit's manager-reported current PID, start time, role, capabilities, command, namespace join and cgroup; root anchor self-observations; and the exact socket identity. It relies on trusted root/systemd manager state and does not assert independent `/proc/PID/exe` or cross-UID namespace inode attestation. Any failed or ambiguous request retains its intent and must not automatically retry the journal.

The complete typed reservation, root launch catalogue and fixed recipe are bound by a domain-separated digest and the full reservation is fsynced in a create-only root record. The recipe accepts only the root-provisioned worker/writer image and program hashes, the fixed Goose binary hash and a pregrant relay scope **template** hash; the final scope includes the grant and launch-catalogue binding after grant issuance. It does not accept request-selected executable paths, commands, mounts or environment. Generation closure is checked before/after reservation and around launch effects.

The root launch wrapper accepts only a generation and invokes only the fixed root-owned, hash-pinned helper phases `verify`, `arm`, `create`, `verify-created` and `start`; it validates strict JSON and the same primary full ID. The helper must itself fence the two container creations, all writer/broker/relay/Goose starts and every uncertain engine reply. The grant-bound deadline adapter validates the complete stored binding and root cgroup, durably records timer intent, and only returns an armed result after actual manager unit and monotonic-wake checks. The Rust live-deadline verifier rechecks the fixed root kernel-stop command and manager timer before launch effects.
