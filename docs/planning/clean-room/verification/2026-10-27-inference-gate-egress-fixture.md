# Inference gate and egress canary

The disposable Restate replay fixture now runs a separate, synthetic Python inference gate and loopback provider. The gate keeps Restate and provider URLs in its own configuration, accepts only a bounded exact request shape and one of three fixed fixture catalog IDs, derives the authority binding from fixed catalog bytes, and retains the `begin` response inside the trusted fixture process. It rejects an exposed `/begin` route, duplicate JSON keys, forged begin data, changed payloads and unknown IDs.

A separate synthetic caller ran under a temporary macOS Seatbelt profile allowing outbound TCP only to the fixture gate. Direct connections to both the provider and the Restate ingress failed with `EPERM`; the same endpoints were reachable outside that sandbox as positive controls. Ten concurrent calls for one catalog ID produced exactly one provider request. After the synthetic provider dropped a response, a retry was refused and the provider still recorded one request. A previously untouched catalog ID then produced exactly one request. Responses to the caller contained only an outcome, not a reusable begin response. The full disposable replay fixture passed twice, including the separate launcher crash and journal-restart controls.

This is a same-UID local canary, not deployed authorization. The worker profile tests the two specified direct TCP endpoints and does not prove comprehensive host isolation or escaped-descendant containment. The loopback gate has no kernel peer authentication and any local process that reaches it can select any of its three fixed IDs; its catalog and provider mapping are synthetic. A compromised gate can still reuse a begin result or contact the provider directly. No actual Goose, Bifrost, protected credential, real pricing, durable task-to-call admission, response streaming or provider-side billing was tested. The experiment does not authorize production activation or resolve the existing-ledger migration requirement.
