# Candidate gateway descriptor-transfer filter

The pinned pre-exec helper now installs an inherited seccomp filter before reporting readiness. It rejects message syscalls that can transfer descriptors, ioctl and selected alternate dispatch or process-inspection syscalls; it validates the syscall architecture and rejects x86-64 x32 aliases. The Root checks also require seccomp mode 2. This is one custody layer, not evidence of complete isolation; the [Linux kernel documentation](https://docs.kernel.org/userspace-api/seccomp_filter.html) describes seccomp filters and their architecture requirements.

A network-disabled x86-64 Linux fixture confirmed an unfiltered SCM_RIGHTS transfer and an unfiltered ioctl control, then verified that a filtered synthetic gateway and its descendant could not send descriptors. It also checked selected alternate syscall denials, a killed x32-alias probe, ordinary local TCP and Unix streams, and kernel peer UID. An unfiltered x32-alias control exited normally. A separate [PID1 receipt](2026-11-02-gateway-transfer-filter.json) exercised the filtered synthetic target in the real guarded cgroup and verified fencing after supervisor loss.

The ARM64 target cross-compiled but the ARM64 filter did not run. The real Bifrost router and its dependencies have not been tested under this filter; denying ioctl and message syscalls can affect compatibility. Exclusive gateway UID, access by outside processes, descriptor transfers through unexamined mechanisms, production egress fencing, and handed-socket cleanup remain unqualified. The filter does not enable live admission or the candidate; no paid calls occurred. The earlier test showed CPython needs close-on-exec flags set before ioctl is denied, so the helper now sets them before installing the filter and before waiting at the gate.
