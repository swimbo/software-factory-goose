# Batch fixed-executor fixture

`Batch` now has an optional, trusted-bootstrap candidate directory. It requires a canonical, host-owned directory under an owned mode-0700 parent, records its device/inode in the executor intent and manifest, rejects `.git`, symlinks, filesystem crossings, special files and multiply linked regular files, and rechecks the binding. Only the executor receives that exact candidate as writable `/work`; other explicit bind mounts remain read-only and caller-selected Docker flags remain forbidden. These checks are fixture safeguards, not an atomic defense against a same-UID host adversary or proof of an immutable candidate.

`exec_once(payload)` requires the sealed catalogue, the exact labelled running executor, its batch-owned start receipt, a matching slice and candidate binding, and a durable one-shot exec reservation. It invokes only `docker exec -i <verified-id> /execution --tool-request`; payload bytes cannot alter Docker argv. Input and stdout are each bounded to 64 KiB and the directly owned Docker CLI child has a deadline. Stop intent is committed independently of the family lock. A concurrent stop while exec is in flight returns unresolved, withholds the output when detected, and requires subsequent container cleanup. Killing a timed-out Docker CLI does not prove that the engine's in-container exec has stopped. The last stop-intent check and delivery are separate operations; this is not a linearizable output-revocation guarantee.

`python3 clean-room/tests/fixtures/test_docker_batch_guardian.py` passed 13 tests, including path substitution, `.git`/symlink/privacy rejection, fixed argv, one-shot replay rejection, refusal of an externally started executor without its receipt, actual bounded subprocess output/deadline behavior, and a mocked in-flight brake race. `python3 clean-room/tests/fixtures/nuc_docker_exec_spike.py` passed twice on the authorized NUC. It precreated and sealed both owned roots, started the fixed idle executor, sent a bounded synthetic tool request to the actual execution binary, observed `EXEC_OK` both in the bounded response and a task-owned candidate file, killed/reaped the owned batch launcher, and recovered both exact containers before observing the existing worker slice `populated 0`. No actual Goose, live provider, standing service, account or user data was used. The fixture slice was empty afterward.

The writable candidate can still be modified by running executor processes or descendants. Do not evaluate, finalize, stage or commit it as an immutable result while those roots are live. First close admission, stop both roots, independently verify the subtree empty, then create an immutable snapshot and bind evaluated file hashes to any committed blobs. That snapshot/finalization workflow is not implemented by this fixture. The fixed `/execution --tool-request` path does not establish an isolated task-check launcher; do not run the task check directly on the host. Same-UID host tampering, concurrent engine activity, full migration denial, durable journal integration, independent authenticated brake, daemon/manager loss and actual provider integration remain open. Production stays fail-closed.
