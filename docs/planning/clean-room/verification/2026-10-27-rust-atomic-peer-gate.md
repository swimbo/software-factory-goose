# Unregistered Rust atomic peer gate

The new Rust `atomic_peer_gate` connects kernel Unix peer credentials and a trusted fixed catalog to the existing `AtomicInferenceFixture` through the protected `UnixRestateBackend`. The public policy requires distinct non-root service and worker UIDs, binds entries to the configured worker, checks canonical task/call IDs and exact payload digest, and limits catalog and payload sizes. Requests can select only a matching catalog task and call ID; they cannot provide lease, digest, amount, provider destination, or a begin acknowledgement. The gate calls the journal's exact `prepare` and `begin` handlers before invoking its trusted provider implementation, and returns no begin token or provider body. It is not registered by the production entrypoint.

The unregistered atomic fixture's begin response changed from an empty body to JSON `true`, so the existing strict Unix backend can decode its acknowledgement without broadening its parser. This is an incompatible handler change for any previously registered fixture deployment; replay of old in-flight handler executions was not tested. The disposable fixture starts with fresh state.

Two focused Rust tests passed for missing/wrong peer metadata, task mismatch, spoofed extra fields, changed catalog payload and unavailable authority; denied requests made no provider call. An explicitly ignored Rust integration test is invoked only by the disposable Restate replay fixture: it serves the gate on a private temporary Unix socket, uses the actual kernel peer UID and a protected Unix relay to real Restate, and uses a synthetic in-process provider counter. A different expected UID rejects the actual peer despite a spoofed header. Three concurrent authorized calls produced one provider call; subsequent revocation prevented a second catalog entry from reaching the provider. The complete disposable replay and strict all-feature/all-target control-plane Clippy passed.

The first integration attempt used ten concurrent calls and observed 503 from saturation of the existing relay's eight-connection limit. This is an unavailable/unknown result, not an authorization success or a 409; the deterministic contention test was reduced to three callers to remain within that fixture limit. A separate test asserts an unavailable authority does not invoke the provider. The normal suite leaves the real-service test ignored; the replay fixture explicitly runs it using its owned temporary relay and journal.

This establishes a reusable local adapter, not production readiness. The real-service test intentionally uses the same OS UID through a private test-only policy constructor; the public constructor rejects that configuration. No second account, production socket lifecycle/ACL, authenticated catalog producer, existing claim/budget namespace migration, actual Goose, Bifrost, model response stream, daily budget or provider credential was verified. The provider implementation and catalog are trusted code; a compromised service can bypass them. Revocation after begin can still precede a later external send, and cancellation/reconciliation of an already dispatched call remains unresolved.
