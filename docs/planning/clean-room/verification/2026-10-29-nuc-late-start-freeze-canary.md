# NUC late-start freeze canary: unresolved

A task-owned root bridge and newly generated systemd slice exercised one late Docker start using `clean-room/deployment/nuc_barrier_canary.py`. The bridge had a read-only container root, no network, a single host-root bind, host PID and cgroup namespaces, and only `SYS_CHROOT` and `DAC_OVERRIDE`; it was an administrative test mechanism, not a proposed worker configuration. The fixed root code was embedded in the reviewed command. No retained pre-existing container, service or slice was intentionally mutated.

The no-freeze positive control ran a static payload whose first observable payload operation created its private marker. After an exact closed record was fsynced, the new slice was frozen and its same inode reported `frozen 1`. A separate late Docker start was issued. During five seconds of sampling no late marker or thaw was observed, and the start client had not returned. The canary killed only the new test subtree while keeping the freeze in place. The Docker start client then returned nonzero. **Outcome: unknown, not pass.** A nonzero client result does not establish the daemon's accepted operation is resolved, and sampling cannot prove a transient thaw did not occur between observations.

Afterward, read-only inspection showed the new slice `sfactorya8b2e0eadc6d47e8aa46a6999436f0b1.slice`, inode 7546233, loaded and active with `frozen 1` and `populated 0`; its marker directory contained only the positive marker. The uniquely labelled late container `8cb7d67b7696ccbbdf68f7a724d7eae15a48ce4f0a110cde3d0b6b303793af6a` was Created. The exact root-owned intent, manifest, closure and result records remain under `/tmp/sfactory-barrier-leqm9isi`; the exited bridge `04aae9f6c6a43623c11764cc9637a7e87b39cce7eaf465ec6872e33d0c93d96e` is retained. Do not thaw, remove, retry or infer daemon-side cancellation from these observations. The prior separately retained original create is not part of this canary.

Two setup findings preceded the canary. Docker reported capability names with `CAP_` prefixes; the first bridge was verified unstarted and removed non-force with a durable cleanup receipt. A separate root bridge with an isolated PID namespace could not connect `systemctl` to the host system bus (`No data available`) even with `SYSTEMD_IN_CHROOT=0`; it failed before task intent and was removed by exact identity with a receipt. A fixed read-only bridge with host PID namespace succeeded in querying the existing daemon and original guard. This is consistent with, but does not independently prove, the systemd peer-PID explanation. The host PID namespace was used only for the privileged bridge, not worker containers.

No independent authenticated brake, supervisor restart, Docker daemon loss, escaped-descendant migration denial, or production containment was proved by this result. No shared service was restarted, and no live provider call was made.

A later read-only inspection showed the late container's Docker state still Created/PID 0, with a stored OCI runtime creation error reporting that the init PID pipe reset. The queried event window contained its create event and no start event. This is consistent with the owned subtree kill during initialization; it does not by itself prove the daemon has no remaining work or justify thawing or removing the retained resources.

## Exact-ID removal source audit

At the deployed Docker commit `3ce5872`, [`ContainerStart`](https://github.com/moby/moby/blob/3ce5872/daemon/start.go#L21-L69) validates state and then [`containerStart`](https://github.com/moby/moby/blob/3ce5872/daemon/start.go#L90-L123) takes the shared container/state mutex, rechecks removal/dead, and holds it through task creation/start and error cleanup. [`ContainerRm`](https://github.com/moby/moby/blob/3ce5872/daemon/delete.go#L25-L55) sets `RemovalInProgress` under that same mutex; [non-force cleanup](https://github.com/moby/moby/blob/3ce5872/daemon/delete.go#L80-L89) rejects a running container, marks it dead under lock, and deregisters its ID. A start already holding the mutex completes before removal can mark it; a stale start pointer subsequently sees removal/dead. This supports a conditional exact-ID removal fence on this pinned daemon, not a claim that an expired client cancels server work.

The proposed criterion, before changing the retained state, is: keep the same subtree frozen, revalidate the exact owned full ID/name/label/slice and Created/PID 0, receive a successful non-force remove response for that ID, verify exact-ID absence, then independently observe the same cgroup inode `frozen 1` and `populated 0`. Failure, timeout or conflict remains unknown. [Start error cleanup](https://github.com/moby/moby/blob/3ce5872/daemon/start.go#L206-L228) logs certain lower-level task deletion errors, so removal and 404 alone do not prove absence of every possible containerd/kernel orphan or recovery after daemon/host failure. The separately retained original container is outside this operation. No removal or thaw was performed as part of this audit.

## Subsequent scoped reconciliation

The exact late container was revalidated against its root-owned manifest under the unchanged daemon ID/PID/commit and while the same slice inode was frozen and empty. Non-force removal by its full ID returned success; exact-ID absence and the same inode's `frozen 1`, `populated 0` were then verified. A root-owned receipt was fsynced. Only after those checks, the exact recorded anchor and unique slice were stopped and slice absence verified. The exited canary bridge was then revalidated and removed non-force; a separate private receipt was fsynced. The separately retained original `sf-owner` container remained untouched and its guard matched. See `/tmp/sfactory-barrier-leqm9isi/reconcile-late.json`, `reconcile-slice.json`, and `bridge-cleanup.json`; the fixed cleanup bridge's user-readable receipt is `/tmp/sfactory-barrier-h62qr3bu/outcome-received.json`.

This resolves the task-owned late ID for this pinned daemon under the source-audited serialization conditions; it does not retrospectively make the original freeze observation a pass or prove all lower-level or daemon-loss recovery.

## Improved observed-child canary

A fresh, unique test passed the bounded observed-child scenario using the same fixed administrative bridge and no additional capabilities. Its positive static payload produced the private marker. For the late full ID `deae193c3ebb517e4d5e1d625705747ff2ea129c9e5ffca6af9b4c9a3ebb0e9f`, the exact Docker scope inode 7550726 was sampled with `frozen 1` and `populated 1` beneath the frozen parent inode 7550474. During five seconds of sampling, no late first-observable-operation marker or parent thaw was observed, and the Docker start client remained pending. The task-owned cgroup was then killed; the start client returned 1. The initially uncertain start was reconciled by same-daemon non-force full-ID removal, exact-ID absence, and same-parent frozen/empty verification before stopping the exact anchor and unique slice. The bridge was removed, the retained original guard remained unchanged, and the user-readable receipt is `/tmp/sfactory-barrier-kn5ggnvu/outcome-received.json`.

This passes the one measured scenario. Sampling does not prove there was never a transient thaw between observations; it does not cover an independently forwarded request with lost acknowledgment, supervisor or daemon death, worker migration escape, authenticated braking, host reboot or production deployment.
