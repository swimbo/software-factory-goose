# Evaluator boundary

`verify_worktree_evidence` accepts a completed zero-exit receipt as an expected full commit SHA. It requires a clean Git-root checkout, tracked root `Cargo.toml` and `Cargo.lock`, and a restricted local Git configuration. It scans committed blobs rather than receipt text, exports the exact commit, and runs actual `cargo check` and `cargo test --all-targets --frozen --offline` in a new Seatbelt-restricted directory. It checks the original revision and cleanliness again afterward. Missing dependencies, unsupported inputs, failed canaries, or unavailable isolation fail closed. `verify_worktree` retains the prior verdict-only API.

The runner permits reads of system/compiler files and its snapshot, writes only in its disposable directory, denies network access, clears inherited environment, and uses a fresh Cargo home. It runs host-read/write and loopback-denial canaries before Cargo; a loopback positive control prevents treating an unavailable network client as proof. Timeout is 120 seconds per check; the process group is killed after exit or timeout. Build output is discarded rather than returned to the worker.

Local fixture verification on 2026-10-26: `cargo test -p evaluator` passed 5 unit tests and 8 integration tests. Integration tests execute successful, failing-test, and type-error crates in Seatbelt; a build-script fixture checks denied host read, host write, and loopback access. Tests also exercise clean/exact-SHA binding, committed-content scanning, malicious Git filter rejection, bare fast-forward promotion and stale-base refusal.

`promote_verified_commit_to_ref` imports exact raw objects into an operator-configured **bare** repository and advances the explicitly approved branch with `git update-ref --no-deref <target> <new> <expected-old>`. It refuses symbolic target refs, changed source/base and non-fast-forward ancestry. `promote_verified_commit` remains a compatibility wrapper selecting the current HEAD branch; action-bound adapters must use the explicit-ref API. Neither helper authenticates an operator or establishes that a verdict passed; the caller must obtain durable exact-SHA evidence and human approval before calling it. No working checkout or remote is updated.

Limits: this is a local restricted-runner proof, not R1 production readiness. Separate generator/evaluator/store UIDs, holdout access isolation and a production canary remain unproven. There is no SAST engine. Secret detection remains a deliberately small literal heuristic. Source symlinks and submodules are rejected. External crates require vendored offline sources; the operator's Cargo registry and credentials are not exposed. The current macOS runner requires rustup's active toolchain and `/Library/Developer/CommandLineTools`; other platforms fail closed. Host resource quotas, inherited-descriptor auditing and hostile process-group escape resistance still require further hardening before running adversarial workloads.

`holdout::PrefilterSession` is a bounded in-process collector for R2. A trusted evaluator supplies an exact candidate SHA, SHA-256 manifest digest and complete scenario count (1–1000). The session issues opaque correlation handles and accepts exactly three uniquely indexed observations per scenario. Unknown, duplicate, cross-session, revision or manifest mismatches invalidate the attempt permanently. Missing/cancelled/unavailable runs produce incomplete feedback, not an outvotable negative result. Complete observations must pass every scenario's 2-of-3 gate and the all-runs 90% threshold. Finalization consumes the collector; generator feedback contains only coarse status and fixed opaque IDs, never internal digests, vote counts or raw runner text.

The collector does not compute/authenticate the manifest, execute scenarios, authenticate result producers, persist results or prove holdout-store isolation. Its report alone is neither a promotion verdict nor evidence of actual execution. The trusted manifest loader, production scenario runner/store and durable integration remain outstanding; do not connect worker-supplied votes directly to this API. Local tests on 2026-10-27 cover completeness, the threshold, duplicate replacement, foreign/cross-revision observations, unavailable outcomes and exact feedback serialization.

`holdout_runner::run_fixture_holdouts` now supplies a bounded **local trusted-fixture** execution adapter. Its immutable manifest is SHA-256 hashed and parsed with strict fields/version, at most 32 scenarios, 8 KiB scripts and 128 KiB total input. Each scenario executes three times from independent exact-commit snapshots, inside the existing Seatbelt profile after host/network canaries. A fixed `/bin/sh -s` receives the trusted script over stdin, never a shell command-line argument or a candidate-tree scenario file. Environment is cleared. Only a successful process returning exactly `{"passed":true}` or `{"passed":false}` (JSON whitespace allowed) provides a vote. Unknown fields, malformed output, nonzero exit, timeout or excess stdout/stderr produce unavailable evidence and opaque incomplete feedback. Script/result text never enters feedback or error messages.

Scenario subprocess limits are 10 ms–5 s per run, 64 bytes–16 KiB per output stream, and a 30-second cumulative execution budget. The runner kills the ordinary process group and waits boundedly for the direct child; this does not establish hostile group-escape resistance or a supervisor-death watchdog. Git/toolchain/canary preparation is outside that execution budget and retains trusted local-fixture assumptions; source export caps files/blob bytes but is not a complete hostile-repository resource boundary. The adapter remains unregistered, requires a caller-authenticated manifest, and proves neither hidden-store access control nor distinct generator/evaluator/store UIDs. A production holdout runner/store and durable integration are still gated.

`holdout_store::ProtectedHoldoutStore` now supplies a read-only macOS store-owner reader. It requires three configured distinct non-root UIDs and verifies that the actual effective UID is the configured store owner. A canonical absolute root is traversed through no-follow directory descriptors; ancestors must belong to root/store, deny group/world writes, and have no extended ACL. The store itself requires exact mode0700, store ownership and no ACL. Only `<expected-sha256>.json` is opened relative to the pinned directory descriptor, with no-follow, close-on-exec and nonblocking flags. Manifests require mode0600, store ownership, one hard link, no ACL, at most128KiB, stable identity/metadata during reading, exact SHA-256 match and the strict fixture schema. Errors disclose no paths or content. It never creates or changes standing paths.

R1's distinct evaluator UID cannot directly read the store's mode0700 directory. This reader therefore belongs in a store-owner process. The canonical macOS path corresponding to planned `/var/holdout` is normally `/private/var/holdout`; configured roots containing symlink components are refused. Local filesystem fixtures use the actual current owner and synthetic other UID values, so passing tests do not establish deployed account separation. Ten local tests cover symlinks, hardlinks, unsafe modes, real ACL grants, root replacement, FIFO/directory refusal, digest tampering, oversized/invalid manifests and a real sandboxed scenario denied access to its source store.

`holdout_transfer` supplies an unregistered connection-level Unix protocol. `ManifestServer::new` loads one exact manifest through the protected store reader as the store owner. `ManifestClient::new` requires the actual evaluator UID and an independently resolved expected digest; it receives no filesystem path or store-reader capability. Both constructors require three distinct nonroot configured principals, and calls recheck the process role. Each actual Unix connection's kernel peer UID is authenticated before any protocol bytes; request bodies cannot assert identity. A versioned request selects only the configured digest. A four-byte big-endian length prefix caps requests at256bytes and manifest responses at128KiB before allocation. A total10ms–5s deadline bounds network reads/writes including partial headers/bodies. The client rehashes and strictly parses the response and rejects trailing bytes or a peer that never finishes. Errors are fixed text with no scenario content. Only existing opaque `GeneratorFeedback` may cross into a generator context.

The transfer API binds no listener and enables no endpoint. Protected socket provisioning, descriptor access, account membership/existence checks, concurrency limits, service lifecycle/revocation, durable authoritative manifest selection and cross-UID runtime proof remain deployment/integration gates. A server retains an immutable selected manifest until dropped; startup filesystem loading is outside the network deadline. Same-account private protocol fixtures prove framing and actual peer checks, while the public store server rejects that same-account topology. No public test bypass exists. Tests do not prove a generator cannot steal an evaluator-owned descriptor on an improperly configured host, and local principal trust does not imply human presence or MFA.
